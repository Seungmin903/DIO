# 공유 다이어리 API

Jira S15P31F106-324~333의 기존 공유 구현에 이메일 초대를 확장했다. 새 테이블은 만들지 않는다. 합의된 diary_members의 별칭·사진 컬럼 2개와 FK/인덱스를 V16으로 추가한다. 프론트 화면은 변경하지 않는다.

## API 목록

| Method | Endpoint | 동작 |
|---|---|---|
| PATCH | `/api/v1/diaries/{diaryId}/membership` | 내 즐겨찾기·마지막 페이지 UUID·다이어리별 별칭·사진 수정 |
| GET | `/api/v1/diaries/{diaryId}/members` | 멤버·계정 닉네임/사진·현재 인원/최대 인원 |
| DELETE | `/api/v1/diaries/{diaryId}/members/{userId}` | 본인 나가기·소유자의 강퇴, 204 |
| POST | `/api/v1/diaries/{diaryId}/transfer-owner` | 소유권 양도만 처리, 기존 소유자는 편집자로 유지, 204 |
| GET | `/api/v1/diaries/{diaryId}/invites` | 현재 링크와 보낸 이메일 초대 목록 |
| POST | `/api/v1/diaries/{diaryId}/invites` | 링크 발급·재발급, 201 |
| POST | `/api/v1/diaries/{diaryId}/invites/email` | 이메일 직접 입력 초대, 202 |
| DELETE | `/api/v1/diaries/{diaryId}/invites/{inviteId}` | 보낸 초대 취소, 204 |
| GET | `/api/v1/me/invites` | 로그인한 수신자의 받은 이메일 초대 목록 |
| GET | `/api/v1/invites/{token}` | 수락 전 정보 조회. 이메일 초대는 지정 수신자 로그인 필요 |
| POST | `/api/v1/invites/{token}/accept` | 링크/이메일 초대 수락, 200 |
| POST | `/api/v1/me/invites/{inviteId}/decline` | 수신자의 이메일 초대 거절, 204 |

검색 API·별도 재발송 API는 없다. 업무 API 12개와 다이어리 전용 사진 조회 GET을 Swagger의 ‘공유 다이어리’에서 확인한다. 공개 일반 링크 미리보기를 제외하면 로그인 accessToken을 Bearer로 전달한다. 이메일 초대 미리보기는 같은 GET 경로를 사용하지만 반드시 수신자 계정으로 로그인해야 한다.

초대 미리보기는 보관함과 같은 형식의 `coverColor`, `coverStyle`, `cover`를 반환한다. 저장된 표지 설정이 없으면 `cover`는 null이다. `pageSize`는 삭제되지 않은 첫 페이지의 크기에 따라 `portrait` 또는 `landscape`이며, 페이지가 없으면 `landscape`다. 표지 이미지 파일에는 기존 미디어 접근 권한이 적용된다.

## 멤버 정책

- OWNER/EDITOR만 지원한다. 소유자를 포함해 최대 4명이다.
- 소유자·편집자 모두 링크/이메일 초대 생성·조회·취소가 가능하다. 강퇴만 소유자 전용이다.
- 내 상태 수정은 favorite와 lastOpenedPageId(UUID)를 받는다. 한 항목 이상 필요하고 null은 변경하지 않는다. 마지막 페이지는 해당 다이어리의 삭제되지 않은 페이지여야 한다.
- 별칭·사진은 해당 diary_members 행에만 저장한다. 계정 프로필을 수정하지 않는다. member_color는 작업자 커서 색상 전용이며 신규 멤버에 랜덤 색을 배정하고 기존 색은 유지한다.
- 다른 멤버가 있으면 소유자는 newOwnerUserId로 후임을 지정하고 나가야 한다. 양도만 원자적으로 처리하고 기존 소유자는 EDITOR로 남는다. 나가려면 별도 DELETE members/{본인 ID}를 호출한다.
- 혼자 남아도 공유 상태를 유지하고 재초대할 수 있다. 마지막 멤버가 나가면 다이어리·페이지·요소·획·이력·알림·연결·초대를 영구 삭제한다. 원본 미디어/S3 객체와 계정은 보존한다.
- 강퇴·나가기는 기존 작업과 작성자 참조를 유지한다. 강퇴 시 기존 공유 링크도 무효화한다.

## 링크 초대

1시간 유효. 재발급하면 이전 LINK만 즉시 무효화하고 이메일 초대는 유지한다. 다이어리 전체 기준 최근 5분 3회 생성 가능하며 취소/무효 이력도 계산한다. 429는 Retry-After를 반환한다.

## 이메일 초대

발송 본문:
```json
{"email":"friend@example.com"}
```

- 가입된 활성 회원만 수신자 ID로 지정한다. 이메일은 trim·소문자로 정규화한다. 미가입·비활성·이미 참여한 회원은 초대와 알림 이벤트를 추가하지 않는다.
- 성공 안내는 202 `{"message":"가입된 이메일이라면 초대가 전달됩니다."}`로 통일한다. 이는 본문 공통화이며 응답 시간이 완전히 같다는 보장은 아니다.
- 공통 202는 정상 처리 시의 안내다. 알림 이벤트 처리에 장애가 나면 초대·알림·처리 이력을 함께 롤백하고 예외를 전파하여 5xx로 실패를 알린다. 전달되지 않은 초대를 성공으로 응답하지 않는다. 이벤트를 발행하지 않는 미가입·비활성·기존 멤버 요청은 이 장애 경로를 거치지 않으므로, 장애 시 응답 차이나 응답 시간까지 가입 여부를 숨긴다는 보장은 없다.
- 요청 제한은 성공 횟수가 아닌 시도 횟수다. 서버 인스턴스의 메모리 제한은 DB 롤백과 독립적이므로 알림 장애로 롤백된 요청도 다이어리·정규화 이메일 기준 5분 3회 및 요청자 전체 분당 20회 예산에 포함한다. 서버 장애 후에도 횟수를 환급하지 않으며 한도를 소진하면 Retry-After 안내 후 다시 요청한다. 롤백된 초대 행은 DB의 실제 생성 이력에는 남지 않는다.
- 같은 다이어리·수신자에게 대기 중인 초대가 있으면 중복 발송하지 않는다. 재발송 전용 API는 없다.
- 같은 다이어리·수신자 기준 최근 5분 3회 발송을 허용한다. 소유자/편집자가 바뀌어도 같은 예산이며 취소·거절·전송 실패 이력도 포함한다. 다른 수신자와 LINK 예산은 독립적이다.
- 대기 초대는 7일 후 만료된다. 정원은 수락 시 다시 확인하며, 만원이면 409이고 초대는 대기 상태로 남는다.
- 수신자만 정보 조회·수락·거절 가능하다. 수락 후 다시 나가도 과거 이메일 초대를 재사용할 수 없다. 링크로 먼저 참여하면 대기 중 이메일 초대도 수락 처리한다.
- 초대 취소/거절은 이미 참여한 멤버를 내보내지 않는다. 처리된 이메일 초대의 다른 상태 변경은 409, 같은 취소·거절 재요청은 204로 처리한다.
- 이메일 주소로 가입 회원을 지정한다. 초대 저장 후 기존 InvitationConfirmedEvent를 같은 트랜잭션에서 전달하고 알림 모듈이 앱 내 DIARY_INVITE 알림을 생성한다. 이벤트 처리 실패 시 초대와 알림을 함께 롤백한다. 커밋 후에는 SMTP로 앱의 ‘받은 초대’를 안내한다.
- 휴대폰 잠금화면 등에 표시하는 푸시 전송은 알림 담당자의 별도 연결 범위다. 이번 변경은 푸시 발송을 추가하지 않고 기존 알림 이벤트 계약을 유지한다.

## 스키마를 변경하지 않는 저장 규칙

기존 diary_invites의 invite_type을 다음 값으로 사용한다. 이 규칙은 공유 도메인 내부에서만 처리하고 API에서는 inviteType=EMAIL과 status를 구분해 반환한다.

| DB invite_type | API 상태 |
|---|---|
| EMAIL | PENDING |
| EMAIL_ACCEPTED | ACCEPTED |
| EMAIL_DECLINED | DECLINED |
| EMAIL_CANCELLED | CANCELLED |
| EMAIL_FAILED (과거 저장 데이터만 조회 지원) | DELIVERY_FAILED |

EMAIL 계열은 기존 invitee_user_id를 수신자로 사용한다. accepted는 use_count=1, 취소/거절/실패는 revoked_at도 기록한다.

이메일 초대는 보낸 뒤 7일이 지나면 만료된다. 새 초대는 expires_at에 생성 시각 + 7일을 저장한다. V28 이전에 만든 초대는 expires_at이 `9999-12-31T23:59:59Z`로 남아 있다. 이 값은 초대 토큰 서명에 들어가므로 바꾸지 않고, 생성 시각 + 7일과 expires_at 중 이른 시각을 실제 만료 시각으로 본다. 만료 판정은 서버(JVM) 시각 기준이다.

아래 응답은 초대 행이 남아 있는 동안의 동작이다. 행은 보존 기한이 지나면 삭제되며, 삭제 뒤 동작은 "보존 기한과 삭제 뒤 동작"에 따로 적는다.

- 만료는 아직 응답하지 않은 대기 초대에만 적용한다. 만료된 대기 초대를 조회·수락하면 410 `INVITE_EXPIRED`를 반환하고, 상태는 `EXPIRED`다. 이미 수락한 초대는 만료로 보지 않으므로, 행이 남아 있는 동안 같은 링크를 다시 열면 멤버로 남아 있을 때 `alreadyMember=true`로 응답한다.
- 대기 중(`PENDING`·`EXPIRED`) 이메일 초대와 공유 링크는 응답의 expiresAt에 실제 만료 시각을 담는다. 수락·거절·취소·전송 실패한 이메일 초대의 expiresAt은 null이다.
- 알림 목록에서는 만료된 초대의 상태를 `PENDING`으로 유지하되 canOpen=false로 내려 열 수 없게 하고, 처리할 알림 수에서도 뺀다.

### 보존 기한과 삭제 뒤 동작

초대 정보는 개인정보라 7일만 보관한다. 이메일 초대 행은 retention_until이 지나면 정리 작업이 영구 삭제한다.

| 초대 상태 | retention_until | 410·`EXPIRED`·`alreadyMember`가 보이는 기간 |
|---|---|---|
| 대기 중 | 만료 시각(생성 + 7일) | 만료 뒤 다음 정리 전까지(최대 1시간) |
| 수락·거절·취소 | 처리 시각 + 7일 | 처리 후 7일과 다음 정리 전까지 |
| V28 이전 초대 | 생성 시각 + 7일(백필) | 배포 후 첫 정리에서 이미 지난 행은 상태와 관계없이 삭제 |

- 정리 작업은 1시간마다(첫 실행은 시작 15분 뒤) 500건씩 최대 20번 나눠 지운다. LINK 초대는 대상이 아니다.
- 삭제된 초대 링크를 조회·수락하면 상태와 관계없이 404 `INVITE_NOT_FOUND`("사용할 수 없는 초대 링크예요.")를 반환한다. 이미 참여한 멤버도 같은 응답을 받는다. 다이어리 참여 자체는 diary_members에 남아 영향이 없다.
- 보낸·받은 이메일 초대 목록에서도 해당 항목이 사라진다.
- diary_invites를 외래키로 참조하는 테이블은 없다. 초대 ID를 들고 있는 알림 처리 이력(invitation_notification_receipts)은 같은 배치에서 지운다. 사라진 초대를 가리키는 DIARY_INVITE 알림은 수신자 알림으로 남고, 목록에서 invitation=null(앱 표시 `UNAVAILABLE`, 열 수 없음)로 내려간다.
- InvitationConfirmedEvent 처리 때 원본 조회가 비면 이벤트 발생 시각으로 구분한다. 이메일 초대는 빨라야 생성 7일 뒤에 정리되므로, 발생 후 7일이 안 됐으면 아직 커밋 전이거나 안 보이는 경우로 보고 재시도 예외를 던진다. 7일이 지났으면 보존 기한 뒤 삭제됐을 수 있어 재시도하지 않는 예외로 끝낸다. 지금은 초대를 만든 트랜잭션 안에서 동기로 발행하므로 7일 뒤 처리는 지연·재전달 경로를 추가할 때만 생긴다.

### 배포 순서

V28은 retention_until을 기본값 없는 NOT NULL로 추가한다. 현재 배포(`docker compose up -d --force-recreate`)는 기존 백엔드 컨테이너를 내린 뒤 새 컨테이너가 Flyway를 실행하므로, 이 열을 모르는 구버전이 마이그레이션 뒤에 INSERT하는 구간이 없다. 롤링·무중단 배포로 바꾸면 열 추가(기본값 포함)와 NOT NULL 승격을 두 번의 배포로 나눠야 한다.

토큰 원문은 DB에 저장하지 않는다. 기존 ID·다이어리·생성/만료 시각을 HMAC 서명하고 SHA-256 해시를 저장한다. 비밀키 교체 후 기존 이메일 대기 초대에 다시 발송하면 이전 초대를 취소하고 새 키로 발급한다.

## 목록 응답·호환성

두 목록 모두 page=0, size=20이 기본이고 size는 1~100이다. 생성 시각과 ID의 내림차순으로 조회한다.

GET `/diaries/{diaryId}/invites`는 기존 최상위 available/token/inviteUrl/expiresAt 필드를 유지하고 linkInviteId(공유 링크 취소용 ID)와 emailInvites를 추가한다. emailInvites와 GET `/me/invites`는 items/page/size/hasNext/totalElements를 반환한다.
각 이메일 항목에는 inviteId, diaryId, diaryTitle, inviterUserId/닉네임, recipientUserId/닉네임/이메일, status, createdAt, expiresAt, token, inviteUrl이 있다. 이메일/토큰 정보는 해당 다이어리 멤버 또는 수신자에게만 반환한다. 토큰은 현재 유효한 대기 초대에만 제공한다. 받은 목록에서는 전송 실패 항목을 제외하고 보낸 목록에서는 실패도 확인할 수 있다.

## 설정·연결 범위

- SHARING_INVITE_SECRET: 별도 32바이트 이상 Base64 비밀키. 같은 환경의 서버 인스턴스끼리 동일하게 설정한다. JWT/이메일 인증 키를 재사용하지 않는다. 미설정은 링크 기능 503이며 다른 기능의 기동은 유지한다.
- SHARING_INVITE_BASE_URL: 공유 링크에 표시할 주소 접두사. 기본 상대 경로 `/invite/`를 허용한다. 이메일 주소로 회원을 지정하는 초대에는 절대 URL 설정이 필요하지 않다. 외부에서 링크로 앱을 열려면 실제 라우팅 주소를 별도로 설정한다.
- 새 회원 초대의 안내 메일은 가입·비밀번호 재설정과 동일한 SMTP 설정(SIGNUP_MAIL_FROM·SPRING_MAIL_*)을 사용한다. 발신 주소가 없으면 앱 내 알림만 저장한다.
- 기존 AUTH_JWT_SECRET·CORS·신뢰 프록시 설정 유지. dev/prod Compose는 위 공유 변수들을 이미 전달한다.

최신 develop의 인증된 다이어리 생성 API가 owner_user_id와 소유자 멤버를 저장한다. 공유 기능과 다이어리/페이지 권한은 같은 diary.domain.DiaryMember 및 DiaryMemberRepository를 재사용한다. 소유자 없는 기존 비회원 행은 요청자 소유로 임의 연결하지 않는다. 새로 로그인해서 POST /api/v1/diaries로 만든 다이어리는 수동 SQL 없이 초대를 테스트할 수 있다. 강퇴된 계정의 페이지 접근 차단과 양도 후 기존 소유자의 편집 권한 유지도 통합 테스트한다. 기존 프론트 공유 화면과 앱 내 초대 알림 연계를 유지한다. 실제 휴대폰 푸시 전송은 별도 담당 범위다.

## 검증 명령

- H2: `./gradlew test --tests "com.f106.DIO.sharing.SharingTests" --tests "com.f106.DIO.sharing.EmailInviteTests"`.
- 실제 PostgreSQL: 별도 폐기용 dio_sharing_qa DB를 만들고 DIO_SHARING_POSTGRES_URL=`jdbc:postgresql://127.0.0.1:포트/dio_sharing_qa`, DIO_SHARING_POSTGRES_PASSWORD를 설정한 뒤 `./gradlew sharingPostgresTest`.
- 전용 이름/루프백이 아니거나 환경변수가 없으면 거부한다. 개인/공용 DB로 폴백하지 않는다. 테스트는 고유 사용자/다이어리를 생성하며 개인 DB를 초기화하지 않는다.
- CI의 백엔드 기본 테스트는 새 회원 초대에서 SMTP가 정확히 한 번 호출되고 미가입·비활성·이미 참여·차단 관계·중복 요청에는 추가 호출이 없는지 검증한다. 발신 주소가 비어 있을 때의 SMTP 미호출도 확인한다. 별도 격리 PostgreSQL 공유 테스트는 초대 생성·중복·수신자 권한·알림 저장을 검증한다.

초대와 앱 내 알림을 같은 트랜잭션에 저장한다. 커밋 뒤 전용 실행기에서 메일을 한 번 시도한다. 메일 실패 또는 대기열 포화는 서버 로그에 남기며, 저장된 초대·앱 내 알림과 API 응답에 영향을 주지 않는다. 기존 EMAIL_FAILED 행의 조회 호환성은 유지한다.

## 다이어리별 별칭·사진 (확정 명세)

- 명세 경로 `PATCH /api/v1/diaries/{diaryId}/membership`을 사용한다. 잘못 사용했던 `/profile` 수정 경로는 제거한다.
- `POST /api/v1/diaries/{diaryId}/transfer-owner`로 경로/동작 변경. 예전 양도 후 나가기 경로는 유지하지 않는다.
- `nickname`: 한글·영문·숫자·밑줄 2~12자, NFKC 정규화. 중복 허용. 필드를 생략하면 유지, 명시적 null이면 계정 닉네임으로 복원.
- `memberProfilePhotoId`: 본인이 이 프로필 기능으로 업로드한 유효한 이미지 ID를 선택할 수 있다. 생략하면 유지, 명시적 null이면 계정 사진 자동 사용. 다른 사람의 사진 ID·삭제된 사진·일반 에셋의 임의 저장 경로는 사용할 수 없다.
- 별도 사진이 없거나 사용 불가하면 현재 계정 사진을 반환한다. 계정 사진도 없으면 profilePhotoUrl=null이며 프론트가 기본 아이콘을 표시한다. 계정 사진을 나중에 바꾸면 계정 사진을 사용 중인 다이어리에도 반영된다.
- 별칭·사진을 바꿔도 커서 색(memberColor)은 바뀌지 않는다.

JSON 예시:
```json
{"favorite":true,"nickname":"여행친구"}
```
계정 프로필로 되돌리기:
```json
{"nickname":null,"memberProfilePhotoId":null}
```

사진 파일은 새 업로드 경로 없이 같은 PATCH의 multipart/form-data로 전송한다. `profile` 파트는 application/json 메타데이터이고 `photo` 파트는 JPEG/PNG 파일이다. 사진은 5MB·1600만 화소 이하만 받고 기존 계정 사진 검증기와 EXIF 방향 보정·512px 이하 PNG 변환을 재사용한다. profile JSON에는 파일 업로드와 memberProfilePhotoId를 동시에 지정하지 않는다(명시적 null도 동시 지정으로 간주).

예시:
```bash
curl -X PATCH "$API/api/v1/diaries/$DIARY_ID/membership" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -F 'profile={"nickname":"여행친구"};type=application/json' \
  -F 'photo=@profile.png;type=image/png'
```

응답에는 기존 상태 필드 외에 nickname(최종 표시값), memberNickname(직접 설정한 값), memberProfilePhotoId, profilePhotoUrl, memberColor, usingAccountPhoto가 있다. 멤버 목록에도 같은 프로필 정보를 반환한다.

### 저장·조회·권한

- 파일은 기존 프로필 저장소 설정(MEDIA_STORAGE=local/s3, 동일 버킷/디렉터리)을 재사용하고, 메타데이터는 기존 media_files에 등록한다. signup_profile_photos의 사용자당 1개 제약을 변경하지 않는다.
- media_files.storage_key는 기존 규칙의 객체 키만 저장한다. 임시 URL·클라이언트 파일 경로·버킷 주소를 저장하지 않는다. 기존 media_files 컬럼 값 IMAGE/UPLOAD/PHOTO/READY를 사용한다.
- 다이어리 전용 사진 응답 URL은 `GET /api/v1/diaries/{diaryId}/members/{userId}/profile-photo?v={사진ID}`다. 이것은 업무 기능 추가가 아닌 파일 조회 경로이며 현재 참여자의 Bearer 인증이 필요하다. 프론트 이미지 요청에도 인증 헤더를 전달해야 한다. v는 사진 변경 시 이미지 소스를 갱신하기 위한 버전 값이다.
- 계정 사진을 사용할 때는 기존 공개 계정 사진 URL을 그대로 반환한다. 별도 사진은 사진 주인이 나갔거나 조회자가 강퇴된 경우 읽을 수 없다.
- 이미지 처리·업로드·파일 조회는 DB 트랜잭션 밖에서 수행한다. 업로드 전 권한을 확인하고 저장 직전에 다시 확인한다. 중간에 강퇴되면 DB 저장을 거부하고 새 업로드 파일 정리를 시도한다. 계정 사진과 다른 다이어리 사진은 수정하지 않는다.
- 사진 교체 시 기존 media_files 행/원본은 자동 삭제하지 않는다. 다른 다이어리에서도 같은 이미지를 사용할 수 있으므로 기존 미디어 삭제·보관 정책을 따른다. 매번 새 파일 ID로 등록해 다른 다이어리의 파일 내용을 덮어쓰지 않는다.
- 일반 미디어와 마찬가지로 환경의 저장소·버킷을 전제로 한다. local에서 S3 또는 다른 버킷으로 전환한다면 기존 다이어리 프로필 파일도 별도 이전해야 한다. 기존 계정 사진 마이그레이션은 signup_profile_photos만 처리하므로 다이어리 사진까지 자동 이전된다고 가정하지 않는다.

### V16 적용

기존 V1~V8 파일은 수정하지 않는다. V16은 member_nickname VARCHAR(30) NULL, member_profile_photo_id UUID NULL만 추가하고 media_files FK를 ON DELETE SET NULL로 연결한다. 기존 회원/다이어리/파일 데이터는 삭제하지 않는다. 이미 동일 컬럼을 추가한 DB에는 IF NOT EXISTS로 대응한다. 기존 사진 참조가 잘못되어 있다면 FK 검증에서 실패하므로 데이터를 임의 삭제해서 진행하지 않는다.

### 기존 프론트 화면 연결 (2026-10-28)

- 로그인 세션에서는 `sharingApi.js`가 기존 공유 창의 멤버 조회·강퇴·본인 나가기, 링크 조회·생성·재생성·붙여넣기 확인·수락, 받은 이메일 초대 조회·수락·거절, 별칭·프로필 사진 수정을 호출한다. 방문자 모드의 미리보기는 유지한다.
- 서버 주소·인증 헤더·토큰 갱신은 기존 `authService` 설정을 재사용한다. 새 프론트 환경변수나 DB 변경은 없다. 사진 업로드는 기존 사진 변환기를 재사용하되 JSON 파트 이름을 `profile`로 전달한다. 가입의 기본 `signup` 파트는 유지한다.
- 전용 사진은 인증 fetch 후 메모리 이미지로 표시한다. 별칭 중복 확인은 서버 정책에 맞춰 형식 확인으로 표시한다. 받은 초대는 알림과 별도 데이터이며 읽음·삭제 API가 없어 해당 버튼과 읽음 표시는 숨긴다. 일반 알림 창은 기존 연결을 유지한다.
- 이메일 발송·보낸 초대 취소는 2026-11-01에 연결했다(`POST /invites/email` · `GET /invites`의 `emailInvites` · `DELETE /invites/{inviteId}`, 소유자 · 편집자 모두). 초대 메시지(멘트) 입력은 서버 계약에 없어 두지 않는다 — 받은 초대 카드는 `OO님의 초대`와 상태만 보이고, 더 볼 내용이 없어 `더보기`(상세 진입)는 뺐다.
- 받은 초대 흐름(2026-11-01, 드라이브 · 애플 메모 · 드롭박스 · 노션 비교 검토 반영):
  - 회원도 게스트와 같은 디자인의 받은 초대 목록(SharingHub)을 쓴다. 연결 검증용 `AuthenticatedNotificationDialog`는 앱에서 더 쓰지 않는다. 목록은 서버 알림(`/notifications`, 읽음 · 삭제 있음)이고, 서버 알림에 없는 다이어리 제목 · 보낸 사람은 `/me/invites`에서 찾아 채운다(`describeInvites`, 실패하면 `다이어리 알림`으로 둔다).
  - 확인 화면은 프로필 설정 하나: 카드 `수락` · 알림에서 연 초대 모두 곧장 프로필 설정(별명 · 사진, 계정 값으로 미리 채움) → `수락하고 참여하기`. 상세 화면은 정원 가득 안내에만 쓴다.
  - 수락하면 공유 설정에 머물지 않고 그 다이어리를 바로 연다(회원은 서버 다이어리 id로 연다). 프로필 저장만 실패했으면 공유 설정에 남는다.
  - 받은 초대 버튼 이름은 `거절`(확인 창 `초대를 거절할까요?`). 거절하면 알림도 지운다.
  - 게스트는 좌측 바 `받은 초대`를 눌러도 로그인 안내(`받은 초대`)부터 본다.
- 소유권 양도는 이후 [공유 API 프론트 연결](./sharing-api-frontend-integration.md)에서 소유자의 참여자 관리(`소유권 양도` → 확인 창 → `POST /transfer-owner`)로 연결했다. 마지막 열람 페이지 기록은 대응하는 입력/화면 연결이 없어 추가하지 않았다. 내보내기 허용 설정은 서버 명세에 없어 실제 공유 창에서 숨긴다. 혼자 남은 소유자 나가기 UI도 추가하지 않았다.
- 현재 기본 보관함/편집기는 기기 저장 문서를 사용한다. 서버 다이어리 목록·내용을 로컬 빈 사본으로 대신 만들지 않는다. 서버 UUID와 실제 참여 권한이 있는 다이어리만 공유 관리가 가능하다. 초대 수락 후에는 공유 설정을 표시하며 서버 문서 열기는 보관함/편집기 담당자 연결 이후 진행한다.
- 프론트 검증: 공유 HTTP 계약·세션 폐기·사진 처리·기존 공유 화면과 인증 회귀 테스트, Expo 웹 export를 실행했다. 실제 기기의 서버 연결·SMTP·S3 발송/저장은 별도 확인이 필요하다.

최신 develop의 V9~V14를 보존하기 위해 공유 프로필 변경은 V15로 재번호했다. 기존 로컬 DB에 예전 공유 V9를 이미 적용했다면 Flyway 이력 확인이 필요하며, 이 병합은 로컬 DB나 이력을 자동 변경하지 않는다.

최신 develop(78a3138) 병합 검증: H2 공유·배포·회원 HTTP 테스트 58개 통과(별도 PostgreSQL 테스트 29개는 H2 태스크에서 제외). 전용 PostgreSQL 공유 테스트 29개, 프론트 HTTP 계약·공유·회원 회귀 49개, Expo 웹 export 통과. 회원 보관함의 기존 공유 진입점을 실제 공유 런타임에 연결했으며 CI의 양쪽 테스트 작업을 보존했다.

추가 develop(cac026f)의 V14 만료 인덱스를 보존하고 공유 프로필 마이그레이션을 V15로 재번호했다. 기존 공유 V9/V14를 이미 적용한 로컬 DB는 이력을 별도로 확인해야 한다.

### 초대 거절 대기 중 삭제 처리

다이어리 잠금 대기 중 초대 행이 삭제된 경우에 한해 JPA refresh의 EntityNotFoundException을 기존 INVITE_NOT_FOUND(404)로 변환한다. 취소·수락 상태 재확인을 위한 refresh는 유지하며 다른 예외는 변경하지 않는다. PostgreSQL에서 요청의 실제 잠금 대기를 확인한 뒤 별도 트랜잭션으로 초대를 삭제하는 경합 검증을 추가했다. DB 구조·API 경로·다른 공유 기능은 변경하지 않는다.

삭제 경합 보완 검증: 거절 단위 테스트 4개와 전용 PostgreSQL 테스트 2개 통과. 실제 잠금 대기 후 초대 행 삭제 시 INVITE_NOT_FOUND(404)를 확인했으며, 비수신자의 잠금 없는 404 처리를 재검증했다.


### 초대 전달 방식 변경

`POST /api/v1/diaries/{diaryId}/invites/email`은 가입된 활성 회원에게 새 초대가 생성되면 앱 내 알림과 안내 메일을 보낸다. 메일은 DIO 앱의 ‘받은 초대’ 확인을 안내한다. 미가입·비활성·이미 참여·차단 관계·중복 요청에는 새 초대나 메일을 만들지 않으며 공통 202 응답을 유지한다.

안내 메일의 ‘DIO에서 초대 확인하기’ 링크는 `dio://member-invites/{inviteId}`로 설치된 DIO 앱을 연다. 로그인 전에는 초대 ID를 메모리에 보관하고 로그인 후 해당 계정의 받은 초대에서 조회한다. 조회할 수 없는 초대는 상세 정보를 표시하지 않으며 ‘계정 바꾸기’로 다시 로그인할 수 있다. 메일 앱에서 이 링크를 열 수 없으면 DIO 앱의 ‘받은 초대’에서 직접 확인한다.


### 공유 화면 API 연결 보완 (2026-11-02)

- 공유 요청도 인증 모듈의 `getAuthHeaders`를 사용한다. 개발 서버의 Basic 접속 인증과 사용자 JWT를 함께 전달하며 기존 인증 범위 검사를 유지한다.
- 기존 이메일 초대 입력란과 버튼을 서버 모드에서도 연결한다. 발송·보낸 목록·취소는 기존 `/invites/email`, `/invites`, `/invites/{inviteId}` API를 사용한다. 새 화면이나 API는 추가하지 않는다.
- 상대 초대 주소 `/invite/{token}`은 현재 API 서버를 기준으로 절대 주소로 표시·복사한다. HTTPS 배포 서버에서는 HTTPS 주소가 되며, 서버가 지정한 별도 초대 주소는 유지한다. 로컬 HTTP 서버를 HTTPS로 임의 변경하지 않는다.
- 앱에 붙여넣어 확인하는 기존 초대 방식은 유지한다. 브라우저에서 초대 안내 페이지를 열거나 앱을 자동 실행하는 라우팅은 별도 연결이 필요하다.
