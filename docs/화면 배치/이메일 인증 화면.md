# 회원가입 이메일 인증 화면

Jira S15P31F106-308 화면 구현, S15P31F106-309 실제 발송·인증 API 연결. 아래 308 검증 기록의 임시 인증·미연결 설명은 당시 상태다. 현재 앱 동작은 마지막의 309 연결 절을 따른다.

- 이메일·비밀번호 입력 다음에 이메일 인증 화면을 표시한다. 소셜 가입은 기존 흐름을 유지한다.
- 인증번호 받기 → 숫자 6자리 입력 → 인증 확인 → 다음 순서다. 이전 화면에서 이메일을 변경하면 인증 상태를 초기화한다.
- 개발 모드에서는 임시 인증번호 `123456`으로 확인한다. 메일을 발송하지 않으며 서버 가입 토큰을 만들지 않는다. 배포 모드에는 임시 인증을 제공하지 않는다.
- 임시 응답 기준 유효 시간은 3분, 재전송 대기는 30초다. 백그라운드에서 돌아와도 실제 경과 시간으로 만료를 판단한다. 실제 정책은 API 연결 때 서버 응답을 따른다.
- 잘못된 번호·만료·요청 실패를 표시하고, 입력 수정 시 오류를 해제한다. 요청 중 연타와 화면 종료 뒤 늦은 응답은 무시한다.
- 기존 로그인 카드·입력칸·버튼과 키보드 회피를 재사용한다.

## 검증

- `node --test tests/email-verification.test.js tests/auth-state.test.js tests/auth.test.js`
- `node tests/auth-screens-browser.cjs` (Metro 8096): 기존 가입 흐름과 인증 입력·완료 화면 확인.
- 실기기: 가입 입력 → 인증번호 받기 → 틀린 번호 → `123456` → 다음, 재전송 대기·만료, 이전 화면에서 이메일 변경, 키보드 표시 시 입력칸 확인.

실제 메일 수신은 개발 서버에서 확인하며 최종 가입 완료 통합 검증은 310번 범위다.

2026-10-27 검증: 전체 단위 테스트 686개 통과, 최종 UI 관련 테스트 18개 통과. iOS·Android·웹 배포 번들 생성 성공. 브라우저에서 기존 로그인·가입 흐름과 인증 오류 화면을 1280×800, 390×844, 320×568, 844×390에서 확인했고 가로 넘침·페이지 오류가 없었다. 실기기 키보드는 별도 확인이 필요하다.

후속 실기기 피드백: 인증 완료 후 다음 단계는 서버 가입 요청을 호출하지 않고 프로필 화면으로 이동한다. 시간·재전송은 입력칸 아래 한 행에 배치하고 오류를 바로 아래 표시한다. 실제 가입 초안 준비·서버 토큰·가입 완료 연결은 309번에서 함께 연결해야 한다. 관련 테스트 19개 통과.

인증 완료 상태는 입력칸·남은 시간·재전송·개발용 번호 안내를 숨기고, 공용 체크 아이콘(64 원 배경 안 28 아이콘)과 완료 안내·다음 버튼을 표시한다. 인증 성공 시 키보드를 닫는다.

## 리뷰 보완

- 배포 모드에 인증 서비스가 주입되지 않은 경우 회원가입 진입에서 준비 중 안내를 표시하고 로그인 화면을 유지한다. 비활성 발송 버튼만 있는 인증 화면으로 보내지 않는다. 개발 모드의 화면 확인은 유지한다.
- 이메일 가입 가능 여부 확인은 현재 UI 경로에서 호출하지 않는다. 309번에서 발송 전 email-availability 확인, 가입 초안 준비, 실제 인증 서비스 주입을 함께 연결해야 한다.
- 명시적 테스트 fixture에만 메모리 가입 초안 준비 어댑터를 주입해 인증 → 프로필 → 가입 완료 안내 → 로그인 성공의 브라우저 회귀 검증을 복원했다. 제품 화면에서 실제 서버 가입 요청을 기다리는 동작은 추가하지 않았다.

## 추가 리뷰 보완

- 주입한 인증 서비스의 prepareSignup은 필수 함수다. 누락되면 오류를 표시하고 프로필 진입을 막는다. 성공·실패·누락·중복 제출을 단위 테스트로 검증한다. 주입 서비스가 없는 개발용 화면 확인만 서버 가입 초안 없이 다음 화면을 표시한다.
- 시간 표시 계산은 verificationTime으로 분리했다. 임시 인증 모듈은 __DEV__ 조건 내부 require로만 불러오고, 실제 서비스가 있으면 개발 중에도 임시 인스턴스를 만들지 않는다. 안내의 임시번호도 개발 전용 모듈에 둔다.
- 관련 테스트 24개 및 브라우저 인증·가입 완료·정상 로그인·배포 게이트 검증 통과. 운영 웹 export 성공, 배포 JS에서 createVerificationPreview 구현 미포함 확인.

운영 산출물 최종 점검: expo export --platform all --no-bytecode 성공. iOS·Android·웹 3개 JS 번들 모두 createVerificationPreview 구현 미포함 확인. 관련 단위 테스트는 최종 24개 통과.

## 비동기·응답 경계 점검

- 가입 준비 중 뒤로가기 시 navigate가 job 요청 번호를 갱신하고 run이 이전 성공·실패를 무시한다. 기존 코드에서 재현되지 않은 지적으로, 지연 응답 회귀 테스트를 추가해 동작을 고정했다.
- 발송 응답 expiresIn은 유한한 양수, retryAfter는 유한한 0 이상 숫자여야 한다. 계산한 마감 시간이 안전한 정수 범위를 벗어나는 응답도 오류로 처리한다. 잘못된 응답은 상태에 적용하지 않고 재시도를 허용한다.
- null·undefined·문자열·비정상 message 예외에는 기본 안내를 표시한다. 가입 준비 결과의 provider와 이메일도 검사해 다른 계정이나 불완전한 응답으로 이동하지 않는다.
- 발송·검증·가입 준비의 화면 종료 및 지연 응답, 응답 오류 후 재시도를 점검했다. 관련 테스트 30개, 전체 테스트 698개 통과.

## 추가 종합 점검

앱 동작 추가 변경 없이 회귀 검증을 확장했다. 이전 이메일 요청의 완료가 새 요청의 로딩을 해제하지 않는지, 화면 종료 후 가입 준비 응답을 무시하는지, 확인·재전송 연타를 직렬 처리하는지, 재전송 실패 후 입력 유지 및 성공 재시도 시 초기화하는지 확인했다. 브라우저에서 뒤로가기 → 이메일 변경 → 인증 화면 재진입 시 발송 전 상태로 초기화되는 흐름도 확인했다. 관련 테스트 34개와 브라우저 시나리오 통과. 실제 메일·서버 통합은 309번 범위로 유지한다.

## 309 이메일 인증 API 연결 (2026-10-28)

- 실제 앱의 AuthScreen은 authService의 인증 어댑터를 기본 주입한다. 개발·배포 모두 서버가 발송한 번호를 사용하고 임시 번호로 대체하지 않는다.
- 발송 전 이메일 가입 가능 여부를 확인한다. 인증 성공 후 같은 서비스의 토큰과 이메일을 확인하고 가입 초안을 준비해 프로필 화면으로 이동한다.
- 서버의 expiresIn·resendAfter를 각각 유효 시간·재전송 대기로 표시한다. 발송 제한의 Retry-After도 적용한다. 이메일 변경·화면 이탈 후 늦은 응답으로 인증 상태를 복원하지 않는다.
- 수동 확인: 실제 이메일로 발송 → 메일 수신 → 잘못된 번호 오류 → 올바른 번호 인증 → 다음에서 프로필 진입. 재전송 대기와 이전 화면에서 이메일 변경 후 초기화도 확인한다.
- 단위 검증은 frontend에서 `pnpm test:auth`. 실제 메일 전송 성공 여부는 SMTP 설정과 팀 개발 서버 상태에 따라 별도 확인한다.
- 초기 검증 기록: 인증 단위 테스트 71개·웹 배포 export 통과. 임시 H2와 브라우저에서 발송·오입력·정상 인증·프로필 진입을 확인했다. 이때 사용한 신규 Java 테스트와 전용 Node QA 스크립트는 이후 프론트 작업 범위를 지키기 위해 MR에서 제외했다.
- 후속 검증: 개발 서버 Basic 접근 인증 처리를 추가한 뒤 인증 단위 테스트 75개 및 Android JS 번들 생성 통과. 사용자가 Android 태블릿에서 개발 서버 접속 인증 → 실제 메일 수신 → 받은 번호로 인증 완료 → 다음 → 프로필 입력 화면 진입을 확인했다. 최종 가입 완료·로그인 통합 검증은 별도 태스크에서 이어간다.
- 리뷰 보완: authService 헤더 변수의 기존 선언을 확인하고 모듈 초기화 테스트를 추가했다. 인증 단위76개와 웹 export 통과. 신규 Java 통합 테스트·전용 Node QA 스크립트는 MR에서 제외하고 Nginx 설정 변경도 원복했다. 개발 Nginx의 웹 CORS 제약은 남아 있다. Android 태블릿에서 확인한 앱 동작은 변경하지 않았다.
