# 스티커 선택·필기 많은 페이지의 렌더링 개선

기준: 2026-11-02 · `fix/fe/canvas-render-performance` · 최신 원격 develop에서 최적화만 분리한 변경이다.

## 원인과 수정

- 스티커 선택/드래그의 `stillIds`/`fadeIds`까지 필기 캐시 전체를 해제해 `CompletedStrokeLayer → 모든 PageObject → CompletedStrokeLayer`로 트리를 바꾸던 문제를 수정했다. 실제 필기가 변형되는 경우만 원본 경로로 전환하고, 비필기 요소의 조작은 기존 필기 묶음·순서를 유지한다. 자르기의 전체 흐림 효과는 기존 원본 경로를 유지한다.
- 네이티브 읽기 모드에서도 기존 완성 획 묶음을 사용한다. 썸네일과 내보내기는 캐시를 켜지 않으며 원본 데이터·편집 이력은 바꾸지 않는다.
- 읽기에서 32획 이상인 정적인 페이지는 유휴 시간에 현재·인접 페이지의 표시 이미지를 순서대로 준비한다. 전환 미리보기와 최종 Canvas가 같은 로컬 URI를 재사용하므로 이미 준비한 다음 페이지의 수백 개 SVG를 두 트리에서 다시 만들지 않는다. 준비 전·실패 시에는 기존 벡터를 표시한다.

## 품질·자원 관리

- 이미지 최대 3장, 한 장 4,194,304픽셀·한 변 4096 이하. 3장의 원시 RGBA 환산 상한은 약 48MiB이며 앱 전체 PSS나 실제 GPU/디코더 메모리 상한을 뜻하지 않는다. 준비 중 임시 surface와 캡처가 별도로 존재한다.
- 현재 표시 배율×기기 PixelRatio 이상으로 캡처할 수 있는 경우에만 사용한다. 예산을 넘는 확대는 낮은 해상도 이미지를 늘리지 않고 원본 벡터로 돌아간다.
- GIF·동적 위젯·플래너 페이지, 유형이 아직 확인되지 않은 미디어가 있는 페이지는 이미지로 고정하지 않는다. 기존 표시·재생을 유지한다.
- 페이지 참조나 목표 해상도가 바뀌면 이전 이미지를 재사용하지 않는다. 전환/확대 중 새 준비를 멈추며, 한 번에 하나만 생성한다.
- 읽기 종료·화면 종료·백그라운드·메모리 경고 시 정리한다. 취소한 뒤 늦게 도착한 결과도 해제하고, 준비 실패는 원본 표시로 대체한다.
- 이 캐시는 임시 표시용이며 서버 동기화나 TTF/PNG/PDF 내보내기 경로를 변경하지 않는다.

### 왼쪽 페이지 목록에서 편집 페이지 선택

목록의 직접 선택은 읽기 이미지 캐시를 사용하지 않는다. 기존 네이티브 썸네일과 본문은 각자 `InkStrokeContent`/`FeltStrokeContent`를 마운트하면서 같은 완성 획의 정밀 윤곽을 다시 계산했다. 렌더 인스턴스의 `useMemo`는 페이지를 떠나면 재사용할 수 없었다.

`completedStrokeGeometry`에서 불변 완성 획 객체별 윤곽 문자열을 공유한다. 썸네일→본문 및 재방문 시 재사용하고, 지우개·굵기·재질 수정으로 객체가 바뀌면 다시 계산한다. 실시간 입력·간략 지우개 미리보기는 섞지 않는다. 최대 2,048개 객체와 경로 문자열 400만 문자(UTF-16 본문 약 8MB, 객체와 엔진 부가 메모리는 별도)로 제한하며, 초과해도 기존 정밀 계산으로 표시한다. 좌표·센서·색·불투명도·문서 저장 데이터는 변경하지 않는다.

완성 획은 사진·폰트용 `ObjectContent` 훅을 거치지 않고 동일한 `StrokeContent`로 표시한다. 위치·회전·반전·외부 투명도 래퍼는 유지한다. 현대 만년필·붓펜·펠트펜이 사용하지 않는 일반 중심 경로 계산도 생략한다. 네이티브 SVG 마운트 비용 자체를 모두 제거한 것은 아니다.

검증: 정밀 경로 동등성·객체 변경·예산과 관련 필기 회귀 35건 통과. `node tests/sidebar-page-lag-browser.cjs`로 실제 웹 편집기에서 500획 페이지를 왼쪽 목록으로 5회 선택하고 전체 획 표시와 문서 JSON 보존을 확인했다. PC 단일 실행의 클릭→마운트 관측값은 181/157/147/138/130ms이며, 수정 전 대비 실측이나 휴대폰 성능 수치로 해석하지 않는다. 결과와 스크린샷은 `.expo/sidebar-page-lag-qa/`에 기록한다. Android·iPad Expo Go 실기기 반응 속도는 별도 확인이 필요하다.

재현 명령: `pnpm test:render-lag`, `pnpm qa:sidebar-page-lag`, `pnpm qa:render-lag`. 별도 Metro를 사용할 때는 `EXPO_QA_PORT`로 포트를 지정한다. 웹·Android·iOS export는 `pnpm exec expo export --platform all --output-dir .expo/performance-export`로 확인했다. 네이티브 기기 런타임 검증과 구분한다.


### MR !298 충돌 해소 (2026-11-03)

검증: 필기 기하·읽기 캐시·선택·읽기 탐색·iPad 준비/점진 표시·텍스트 측정·영역 지우개·스포이트 관련 70개 테스트 통과. PC Edge 실제 편집기에서 500획 페이지의 왼쪽 목록 5회 이동, 읽기 이미지 URI 재사용과 문서 불변, 스포이트 및 390×844 / 844×390 화면 검사를 통과했다. 실행 로그는 `outputs/canvas-performance-publish/merge-*.log`에 보관한다(저장소 외부 로컬 산출물). 실제 Galaxy/iPad의 성능·메모리·발열은 새로 측정하지 않았다.

### 읽기 이미지 오류 폴백 고지 명시

MR !298의 이미지 오류 WARN에 한정해 `ReadingPageContent`의 벡터 폴백에 `showBackground={true}`를 명시했다. 기존 `StaticPage` 기본값에도 의존하지 않고, Canvas가 배경을 이미지에 맡긴 상태에서도 속지·템플릿을 포함한 전체 페이지를 복원한다. 읽기 전환도 같은 폴백을 사용한다.

### 완성 획 굽기를 보이는 범위로 좁힘 (2026-11-10)

편집 중 펜·지우개가 끊기는 원인을 재어 보니 유리펜 그리기가 아니라 **완성 획 굽기**였다. 굽기 값은 거의 전부가 GPU→CPU 읽어오기이고 **픽셀 수에 정비례**한다(실측 32ns/px: 2,400만 px 767ms). 그때까지는 페이지 전체를 확대 배율로 구웠기 때문에 확대 3배에서 `4236x5648 = 2,400만 px`가 되고 한 번에 `FULL 300~1,716ms`가 걸렸다. 화면에 보이는 것은 그중 14%뿐이었고, 확대를 조금만 바꿔도 `이어굽기=전부`로 다시 구웠다. 같은 크기의 GPU 표면(최대 96MB)을 들고 있어 기기가 메모리 부족으로 앱을 종료하기도 했다(전체 7.83GB 중 5.87GB 사용).

`bakeWindow`로 **보이는 범위에 30% 여유를 붙이고 160 단위 격자에 맞춘 창**만 굽는다. 창 안에 온전히 들어온 획만 굽고(`bakedIn`), 창 테두리에 걸친 획은 굽지 않고 벡터로 그린다(`atEdge`) — 둘 다 하면 같은 획이 두 번 그려져 반투명 잉크가 진해진다. 창이 바뀌면 지난 그림을 그 자리에 그대로 두고 멈춘 뒤 한 번만 다시 굽는다(확대율이 바뀔 때 쓰던 "늘려 쓰기"와 같은 방식). 썸네일·내보내기는 보이는 범위가 없으므로(`visible === null`) 종전처럼 페이지 전체를 굽는다.

창 밖은 **페이지 전체를 낮은 해상도(상한 300만 px)로 한 장 구운 바탕**으로 메운다. `Viewport`는 손가락으로 밀거나 확대하는 동안 캔버스를 다시 그리지 않고 transform 으로만 옮기므로(손을 떼야 한 번 확정한다), 바탕이 없으면 창 밖으로 민 자리가 손을 뗄 때까지 비어 보인다. 바탕은 **미는 동작이 시작될 때만** 굽고(멈출 때마다 구우면 글 쓰고 손 뗄 때마다 약 90ms가 더 붙는다) 획이 바뀌지 않으면 다음 밀기에도 그대로 쓴다. 또렷한 창 그림 **아래**에 깔고 창 안쪽은 `invertClip`으로 잘라 내, 반투명 잉크가 두 번 곱해지지 않게 한다.

같은 판에서 유리펜 그리기의 프레임마다 다시 만들던 것들(uniform 45개, 입자 셰이더, 블러, 런타임 셰이더 필터, 붓 7개, 도장마다 만들던 `Float32Array`)을 획 단위로 캐시했다. 이후 PC 연결 상태의 실기 로그에서 `[유리펜]` 6ms 이상 프레임이 한 줄도 찍히지 않았다.

검증: 굽는 창·창 안팎 가리기·창 밖 바탕 판단은 `src/editor/skia/bakeDelta.js`의 순수 함수로 두고 `tests/bake-delta.test.js`에서 확인한다(여유·격자·밀기 허용 범위·페이지 경계 자르기·`bakedIn`/`atEdge`/`notBaked`/`coversPage`, 바탕을 또렷한 그림 아래에 깔고 창 안쪽을 잘라 내는 층 순서). 전체 단위 검사 3,099건 중 3,083건 통과이며, 실패 16건은 이 변경 이전부터 있던 것들이다(`packingLayout` 미구현, Spring 계약, 원격 스티커 팩, 읽기 이미지 복원, 팔레트 브라우저). 실기(SM-X510) 재측정 결과는 아래 `유리펜 기하` 절에 함께 적는다 — `[굽기] 읽어오기`가 `2277x2846`(창 768x960)처럼 화면 크기로 찍히고 `FULL`은 19~160ms로, 종전 300~1,716ms에서 내려왔다. 다만 확대 배율을 바꿀 때마다 `이어굽기=전부`로 창을 다시 굽는 것은 그대로 남아 있다(40~160ms).

### 유리펜 기하: 곡선 보간과 외곽선 만들기 (2026-11-10, 실기 측정)

창 단위 굽기와 붓·셰이더 캐시를 넣은 뒤 실기(SM-X510, 개발 빌드 + `EXPO_PUBLIC_PENCIL_PROFILE=1`)에서 다시 재니, 쓰는 중 프레임 값이 거의 전부 **기하 다시 만들기**였다. 캐시는 의도대로 동작해 `uni`·`필터`·`입자`는 획 첫 프레임을 빼고 0으로 찍혔고, 굽기는 손을 뗀 뒤에만 일어나 쓰는 중에는 걸리지 않았다.

`[유리펜]` 줄을 `표본[도장 · 솎기 · 쓸기 · 파싱]`으로 쪼개 보니 **도장 찍기(`glassDabs`)와 쓸기 외곽선 문자열(`ballSweepPath`)이 반반**이었고, 둘 다 도장 수에 정비례했다(도장 171개 6ms → 1,509개 39ms).

고친 곳은 세 군데이며, 모두 그리는 결과를 바꾸지 않는다.

- `sampleCurve`의 안쪽 고리는 **내는 간격의 네 배로** 잘게 돌면서(표본 넷 중 셋은 버린다) 표본마다 카트멀-롬 클로저와 좌표 객체를 새로 만들고 있었다. 계수를 구간마다 한 번만 구하고, 남길 표본에서만 객체를 만들도록 바꿨다. 무작위 획 40개·74,330칸 비교에서 **최대 차이 0**(비트까지 동일).
- `smooth`(창 평균)는 `O(n × r)` 단순 박스 필터였다. 누적합으로 바꿔 `O(n)`. 같은 창의 평균이라 결과는 같고, 실측 상대 차이는 6.4e-14다.
- `polygonPath`는 좌표를 **두 번** 반올림하고(넓이 계산용 객체 배열 한 벌 + 글자로 쓸 때 또) `join`용 문자열 배열까지 만들었다. 한 번만 반올림하고 중간 배열을 없앴다. 무작위 다각형 20만 개에서 **내는 글자가 완전히 동일**. 이 둘(`smooth`·`polygonPath`)은 유리펜뿐 아니라 볼펜·붓펜·펠트펜·점선 획에도 함께 걸린다.

실기 전후(같은 굵기 32, 도장 약 1,500개인 긴 획):

| 단계 | 전 | 후 |
| --- | --- | --- |
| 도장(`glassDabs`) | 16ms | 5ms |
| 솎기(외곽선 간추리기) | 1ms | 1ms |
| 쓸기(`ballSweepPath` 문자열) | 15ms | 10ms |
| 파싱(`MakeFromSVGString`) | 1ms | 2ms |
| 프레임 전체 | 39ms | 22ms |

도장 2,000개까지 늘려도 25~31ms로, 전이라면 45ms를 넘던 길이다. 이어서 짧은 획과 다른 펜들을 재 보니 더 큰 것이 나왔고, 그쪽은 아래  절로 이어진다.

남은 자리는 기록해 둔다. ① `쓸기`가 이제 단독 최대 비용이다 — 외곽선 800점이면 꼭짓점 약 3,000개, 글자 11만 자를 매 프레임 만든다. 문자열을 건너뛰는 `Skia.Path.MakeFromCmds`가 있으나 명령마다 작은 배열을 넘기는 구조라 더 느릴 수 있어 재봐야 한다. 획 앞부분의 글자를 얼려 두고 꼬리만 다시 만드는 쪽이 효과는 확실하지만, 획 끝 근처는 고임(`poolEnd`)과 끝맺음 때문에 값이 계속 바뀌므로 얼리는 여유를 잘못 잡으면 이음매가 보인다. ② 확대 배율을 바꿀 때마다 창을 통째로 다시 굽는다(`이어굽기=전부`, 40~160ms). ③ 굽기의 GPU→CPU 읽어오기는 픽셀 수에 비례하지 않는 고정 비용이 커서(926x1234에 94ms, 2277x2846에 83ms), 크기를 더 줄이기보다 **굽는 횟수**를 줄이는 쪽이 낫다.

`[유리펜]` 줄의 단계별 쪼갬(`표본[도장 솎기 쓸기 파싱]`, 외곽선 점수, 글자 수)은 그대로 남겨 두었다. 기본은 꺼져 있고 `EXPO_PUBLIC_PENCIL_PROFILE=1`로 Metro를 띄울 때만 찍힌다.

### 완성 획을 타일 격자로 (2026-11-10, 실기 측정 + 다른 앱 조사)

짧은 획과 다른 펜들까지 재 보니, 한 프레임 값보다 **훨씬 큰 것**이 따로 있었다. 획이 쌓인 페이지에서 확대 배율을 바꾸면 화면의 모든 획을 다시 래스터화했다 — `FULL ms=436.5 획=195 이어굽기=전부 ball:71 calligraphy:74 taperBrush:50`, 그중 GPU 읽어오기는 19.4ms 뿐이다. 같은 `전부`인데 71획은 20ms, 123획은 589ms로 갈렸다. 값은 획 **수**가 아니라 **어떤 펜이냐**에 달렸다(획 하나를 구워 넣는 값: 점선 0.5ms · 연필 0.65ms · 유리펜 3.9ms).

그림·필기 앱들이 이 문제를 어떻게 푸는지 찾아보니(Vellum PR #23, sanenotes #624, pdf-drawing-tool #44/#93, ink-notes #292, notate #52, infinitecanvas.cc 35강) 네 가지가 공통이었다. ① 완성 잉크를 **256px 타일**로 굽고 **닿은 타일만** 다시 굽는다. ② 확대는 **옥타브 버킷**으로만 다시 굽고 핀치 중에는 직전 버킷을 늘려 보여 준다. ③ **LRU + 기기별 메모리 예산**. ④ 쓰는 중인 획은 **조각으로 얼려** 열린 조각만 다시 만든다. 우리 방향이 정반대는 아니었다 — 같은 계열인데 **한 장짜리**라 무엇 하나 어긋나면 전부 다시 그려야 했던 것이 차이였다.

바꾼 것:

- **타일 격자**(`src/editor/skia/tileGrid.js`). 페이지 좌표 256단위 칸. 타일은 **제 칸으로 잘라서** 그리므로 한 획이 이웃 타일에 걸쳐도 픽셀은 한 장에만 속한다 — 창 방식에 필요했던 "걸친 획은 굽지 말고 벡터로" 예외가 통째로 없어졌다.
- **한 번에 두 장씩**(`TILES_PER_PASS`), 남으면 60ms 뒤 이어서. 한 프레임에 다 구우면 그게 예전의 전부 다시 굽기다.
- **타일 안에서도 이어 굽기**. 덧붙기만 했으면 지난 그림 위에 **새 획만** 더 그린다(`TILE+`). 획이 **빠진** 칸(지우개·되돌리기)과 차례가 바뀐 칸은 지난 그림을 쓰지 않는다 — 쓰면 지운 획이 남아 보인다.
- **아직 못 구운 칸**은 지난 그림을 깔고 거기 없던 획만 벡터로 얹는다(다 얹으면 반투명 잉크가 두 번 곱해진다).
- **LRU 2,400만 px(≈RGBA 96MB)**. 기기 메모리 부족으로 앱이 죽은 적이 있다(7.83GB 중 5.87GB 사용).
- 앞서 넣은 **창 유지**(확대해 보이는 범위가 좁아지면 쓰던 창을 그대로)와 **배율 ¼옥타브 올림**은 타일 열쇠(칸 + 배율)로 흡수됐다. 올림이라 구운 타일이 늘 화면보다 촘촘해 줄여 그려지므로 흐려지지 않는다.
- **쓰는 중인 획의 조각 단위를 96 → 32점**(`PREVIEW_SEGMENT_POINTS`). 96이면 59점짜리 짧은 획은 조각이 하나도 안 닫혀 캐시가 전혀 안 먹었다. 조각은 네이티브 `PathBuilder.addPath`로 **한 경로에 묶어 한 번에** 채우므로 겹친 자리가 두 번 칠해지지 않는다.

실기 전후:

| 상황 | 전 | 후 |
| --- | --- | --- |
| 획 하나 더 쓰고 반영 | 창 전체 417~589ms | `TILE+` 2~23ms |
| 확대 눈금이 바뀜 | 전부 다시 120~245ms | 타일별로 2장씩 나눠, 한 번에 멈추는 구간 없음 |
| 타일 하나 처음 굽기 | — | 유리펜 50획이면 67~126ms, 형광펜 1획이면 2~5ms |

사용자가 실기에서 육안 확인했다(2026-11-10): 타일 경계의 이음매·잘린 자국, 반투명 잉크가 겹친 자리만 진해지는 것, 지운 획이 남는 것 — 모두 없었다.

남은 자리: ① **유리펜은 조각을 안 쓴다** — `drawParts`가 `parts.flatMap(...)`으로 획 전체를 넘기므로 32점 조각 변경이 안 먹는다(쓰는 중 185점에 17ms). 고임(`poolEnd`)과 끝맺음이 획 끝 근처 값을 계속 바꾸기 때문에, 얼리는 여유를 잘못 잡으면 이음매가 보인다. ② **지우개**는 획이 빠지므로 타일을 통째로 다시 굽는다. ③ **공간 인덱스**가 없어 타일마다 전체 획을 훑는다(`strokesInTile`). 다른 구현들은 이걸로 지우개가 훑는 획을 10,000 → 63까지 줄였다.

`makeNonTextureImage`로 GPU→CPU를 읽어오는 이유는 **표면 한 장을 돌려쓰기** 때문이다(텍스처에 매인 그림은 다음 굽기 때 치워져 죽는다). 타일은 한 장이 작아 타일마다 제 표면을 가질 수 있어 읽어오기를 통째로 없앨 여지가 있으나, 2026-11-09에 같은 것에 당한 적이 있어 이번에는 건드리지 않았다. react-native-skia는 v3에서 스냅샷이 GPU 이미지를 돌려주는 쪽으로 갔고 우리는 2.14.0이다.
