# 신고·차단 프론트 API 연동

## 기준과 범위

2026-11-04 확정 명세:
- [신고·차단 사용자 흐름](https://app.notion.com/p/40eaa7485fe180bf91daf53a3658a3d4)
- [테이블 및 API 명세](https://app.notion.com/p/api-40eaa7485fe180718b61c0524d834f7c)

이번 작업은 프론트 API 연동만 포함한다. 사용자 확인에 따라 서버 API·DB·메일·운영자 기능은 백엔드 담당자 범위로 남긴다. 기존 develop의 게스트 자동 진입, 보관함, 하단 탭, 로그인 게이트와 세션 복원은 유지한다.

## 확정 계약에 따른 화면 변경

- 신고 사유는 HARASSMENT, HATE_DISCRIMINATION, SEXUAL_CONTENT, THREAT_PRIVACY, CHILD_SAFETY, SPAM_FRAUD, RIGHTS_INFRINGEMENT, COLLABORATION_ABUSE, OTHER의 9종이다.
- 상세 설명은 최대 1,000자, OTHER일 때만 공백이 아닌 설명을 필수로 받는다.
- 증빙은 선택이며 PNG/JPEG 최대 3장·장당 5MiB다. 프로필 사진처럼 자르거나 리사이즈하지 않고 원본 바이트를 전송한다.
- 현재 멤버만 조회·신고·신규 차단 대상으로 제공한다. 확정 명세에는 과거 참여 이력 API가 없으므로 이전 참여자를 신고 가능한 것처럼 표시하지 않는다.
- 차단 목록은 계정 닉네임·차단 시각을 사용한다. 탈퇴한 사용자도 목록에서 차단 해제가 가능하다.
- 차단은 이메일 초대 발송·수락 제한이며 기존 다이어리 참여·권한·공동 작업을 변경하지 않는다. 링크 참여는 명시적인 확인 후 허용한다.

## 인증과 HTTP 경계

`SafetyProvider`는 로그인한 세션에 `createSafetyApi`를 연결한다. 게스트는 로그인 제한 상태, 개발 미리보기는 별도 샘플 어댑터를 사용한다. API 주소와 Authorization/X-DIO-Access-Token 및 개발 게이트웨이 Basic 인증은 기존 authService 설정을 재사용한다. 쿠키 전송·다른 출처 리다이렉트·응답 캐시를 허용하지 않는다.

401은 기존 인증 서비스로 한 번 갱신하고 같은 본문·동일한 신고 요청 ID로 재시도한다. 계정 변경 후 옛 요청을 새 계정 토큰으로 전송하거나 새 화면에 반영하지 않는다. 신고 내용·증빙·인증 토큰은 별도 영구 저장소에 기록하지 않는다.

| 작업 | 요청 | 처리 |
|---|---|---|
| 신고 접수 | POST /api/v1/reports | multipart의 report JSON + 선택 evidenceFiles 파일 배열. 201 최초 접수, 200 동일 요청 재시도 결과 |
| 차단 | PUT /api/v1/me/blocks/{userId} | JSON { diaryId }. 204 후 목록을 재조회해 계정 이름·원래 차단 시각을 확정 |
| 차단 목록 | GET /api/v1/me/blocks?page=0&size=100 | items/page/size/hasNext를 검증해 모든 페이지를 모음 |
| 해제 | DELETE /api/v1/me/blocks/{userId} | 본문 없음. 204 후 본인 차단 목록에서 제거 |
| 현재 멤버 | GET /api/v1/diaries/{diaryId}/members | 기존 공유 API의 사진 인증 경로를 재사용하고 blockedByMe·activeAccount를 전달 |

신고 JSON은 reportedUserId, diaryId, reasonCode, description, clientRequestId만 전송한다. 신고자 ID는 전송하지 않는다. 프론트 내부 식별자는 문자열로 유지하며 안전하게 표현 가능한 Long은 JSON 숫자로 전송하고 정밀도 손실이 생기는 값은 기존 숫자 문자열 형태를 유지한다.

신고 재시도는 같은 clientRequestId를 사용한다. 응답 유실 뒤에도 자동으로 새 ID를 발급하지 않는다. 실패 뒤에는 '처음 전송한 내용으로 되돌리기'로 사유·설명·사진을 복원하고 같은 ID로 재시도할 수 있다. 내용을 수정한 재시도가 REPORT_REQUEST_CONFLICT를 반환하더라도 최초 전송 내용은 유지한다. 신고 초안 폐기·성공·새 세션에서만 초안 ID와 최초 전송 내용을 초기화한다.

PUT 성공 후 목록 조회가 실패하면 성공을 꾸미지 않고 재조회 필요 상태를 표시한다. 목록은 실패 전 데이터를 보존한다. 서버 미구현·404·501·통신 실패를 빈 목록이나 접수 성공으로 취급하지 않는다.

## 초대 계약 확장

기존 수신 목록을 선택할 때 토큰 상세 GET /api/v1/invites/{token}을 다시 조회해 requiresBlockedMemberConfirmation을 확인한다. 링크 확인 응답도 같은 필드를 사용한다.

- 확인 필요: 차단한 멤버와 서로의 작업을 보고 편집할 수 있다는 안내를 표시한다. 사용자가 확인한 뒤에만 수락 요청에 acknowledgeBlockedMembers: true를 전송한다.
- 확인을 취소하면 참여시키지 않는다. 확인을 다음 초대에 재사용하지 않는다.
- 수락 시 409 / BLOCKED_MEMBER_CONFIRMATION_REQUIRED가 새로 발생하면 자동으로 true를 붙여 재시도하지 않는다. 다시 명시적 확인을 받아 수락한다.
- 이메일 초대 발송은 기존 공통 응답을 유지한다. 프론트가 상대방의 차단 여부를 추측해 노출하지 않는다.
- 이메일 대기 초대를 차단만으로 취소하지 않는다. 유효한 초대는 차단 해제 후 기존 정책에 따라 수락할 수 있다.

개인 다이어리 열기는 신고·차단 API 호출에 의존하지 않는다. 기존 공유 다이어리의 선택적 진입 안내는 멤버 응답의 blockedByMe를 사용하며 이 기기의 계정·다이어리별 다시 보지 않기 설정을 유지한다. 이 설정으로 새로 참여하는 초대의 필수 확인을 건너뛰지 않는다.

## 서버 담당자 연동 확인 항목

- 사용자 API 4개와 멤버 blockedByMe, 초대 requiresBlockedMemberConfirmation 및 acknowledgeBlockedMembers, 오류 코드가 위 계약대로 응답해야 한다.
- 서버에서 인증·현재 공유 멤버 관계·본인 신고/차단 방지·실제 파일 형식/크기·요청 해시 기반 중복 접수를 검증해야 한다.
- 차단 목록은 계정 이름을 사용하고 역방향 차단 관계를 노출하지 않아야 한다. 204 멱등 응답과 페이지 메타데이터가 필요하다.
- 이메일 초대 발송·수락 제한과 링크 참여 확인은 서버가 강제해야 한다. 기존 권한·참여·공동 작성물은 유지해야 한다.
- 신고 저장 완료 후 운영자 메일 전송이 실패해도 신고는 유지되어야 한다. 보관 기간·요청 제한 수치·메일 재시도 간격/횟수는 명세상 미확정이며 이번 프론트에서 임의 결정하지 않았다.

현재 develop에는 이 서버 구현이 없다. 이번 결과는 확정 계약에 맞는 프론트 구현과 로컬 HTTP 계약 검증이며, 실제 서버 접수·제재·메일 성공을 의미하지 않는다.

## 검증과 미리보기

- `pnpm test:safety`: 입력·페이지·차단·재시도·인증 격리·실제 multipart 전송·초안 ID 보존 검증. HTTP 검증은 테스트용 로컬 서버이며 실제 계정에 신고하거나 차단하지 않는다.
- `node --test tests/sharing-api.test.js tests/diary-sharing-state.test.js`: 초대 확인·취소·409 재확인·기존 공유 기능 회귀.
- `EXPO_PUBLIC_DIARY_SOURCE=mock-safety`로 Expo 개발 서버를 실행한 뒤 `DIO_SAFETY_QA_URL`을 지정해 `node qa/safety-browser.cjs`를 실행한다. 폰 412×892·태블릿 1280×800 화면을 확인한다. 종료 후 환경변수를 해제한다.
- 일반 앱 보관함·게스트·하단 탭은 `node qa/safety-base-browser.cjs`로 확인한다.
- 실제 서버와 실기기 키보드·갤러리·iOS 모달 조작은 서버 구현 후 별도 검증해야 한다.

### 이번 변경 검증 결과

- 신고·차단, 공유 초대, 게스트·인증·알림 관련 자동 테스트 187개 통과. multipart 검증은 테스트용 로컬 HTTP 서버에서 수행했다. 최초 신고 내용 복원·동일 ID 재시도 및 참여자 화면의 전체 차단 목록 선조회·기존 차단 보존을 포함한다.
- 신고·차단 미리보기와 일반 앱 모두 412×892, 1280×800 브라우저 검증 통과. 일반 앱의 게스트 자동 진입·최신 보관함·폰 하단 5개 탭을 확인했다.
- Expo Android·iOS·웹 번들 내보내기 통과. APK/Xcode 빌드나 실기기 첨부·전송 검증 결과는 아니다.
