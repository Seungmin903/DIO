# 이메일 입력 검증 계약

신규 가입·이메일 중복 확인·가입 인증은 신규 주소 형식 기준을 사용한다. 로그인·비밀번호 재설정·공유 초대는 기존 계정의 주소 형식 호환성을 위한 별도 조회 기준을 사용한다. 각 기준은 프론트·백엔드에서 일치시킨다. 프론트는 src/shared/emailInput.js, 백엔드 요청 DTO는 UserInput의 용도별 패턴과 normalizeEmail을 사용한다. API 경로·요청 필드·DB·기존 회원 데이터는 변경하지 않는다.

## 신규 가입 기준

- 앞뒤 ECMAScript 공백 문자 제거 후 소문자 변환. 내부 공백·제어문자는 허용하지 않는다.
- 정규화 결과 최대 254 UTF-16 코드 단위, @ 앞 최대 64 Unicode 코드 포인트.
- 일반 dot-atom 주소를 받는다. 로컬 부분의 문자·숫자 및 !#$%&'*+/=?^_`{|}~-와 구분용 점을 허용하며, 시작·끝 점과 연속 점은 거절한다.
- 도메인은 문자·숫자·내부 하이픈으로 구성한 1~63자 레이블이며 점으로 구분한 레이블이 최소 두 개 필요하다. 한글 도메인과 punycode 표기를 허용한다. domain의 연속 점·밑줄·레이블 양끝 하이픈은 거절한다.
- plus addressing과 사용자 선택 메일 서비스는 제한하지 않는다. 소문자 변환은 기존 DIO 계정 정책을 유지하며 점 제거·+태그 제거·NFKC·punycode 변환은 하지 않는다.
- 이 입력 정책은 RFC의 모든 특수 주소를 지원한다는 뜻이 아니다. 따옴표 로컬 부분·주석·IP 도메인 리터럴은 지원하지 않는다. 기존 DB의 값을 일괄 정정하거나 삭제하지 않는다.
- 형식 통과는 메일함 존재·소유 확인이 아니다. 가입 이메일 인증과 초대 수신자 확인은 별도로 유지한다.

기존에는 프론트가 연속 점 등 일부 주소를 통과시켜도 서버 @Email에서 거절할 수 있었다. 이제 별도 @Email 구현에 따른 차이를 없애고 같은 용도의 요청에서 공통 패턴을 사용한다. 프론트 auth 어댑터도 부적합한 입력을 전송 전에 거절한다. 화면 디자인은 바꾸지 않는다.

공통 사례: contracts/email-input-cases.json. Node와 Java Bean Validation에서 같은 정상·비정상·길이 경계·Unicode 공백 사례를 실행한다. frontend의 pnpm test:auth 및 backend의 gradlew test --tests '*EmailInputContractTests'로 검증할 수 있다.


## 기존 계정 호환성

로그인·공유 초대와 비밀번호 재설정의 발송·확인·완료는 신규 가입 패턴을 적용하지 않는다. 공통 공백 제거·소문자 처리와 최대 254자, 정확히 하나의 @와 비어 있지 않은 앞뒤 값, 내부 공백·제어/서식 문자 거절만 적용한다. IP 도메인 리터럴·도메인 밑줄·따옴표 로컬 부분 같은 과거 주소가 새 패턴 때문에 차단되지 않는다. 전체 RFC 구문을 재검사하지는 않으나 로그인 비밀번호 검증·계정 상태·재설정 이메일 인증·일회용 토큰·요청 제한은 그대로 적용된다. 계정 존재 여부는 별도로 검증하며 신규 가입에는 계속 엄격한 형식을 적용한다. 기존 DB 주소를 변경하지 않는다.

프론트 accountEmailError와 백엔드 UserInput.ACCOUNT_EMAIL_PATTERN이 조회 기준을 담당한다. 비밀번호 재설정 발송 DTO만 분리했으며 기존 JSON의 email 필드와 API 경로는 동일하다. 공통 JSON 사례의 valid는 신규 주소, accountValid는 기존 계정 조회 허용 여부다.

CI frontend-email-contract-test는 MR/develop에서 docs/contracts, 이메일 관련 프론트 코드·테스트, 백엔드 입력 규칙·DTO 또는 CI 파일이 변경되면 실행된다. frontend와 docs/contracts를 읽기 전용 마운트한 Node 24 컨테이너에서 테스트하며 패키지 설치·운영 비밀키 없이 실행한다. 공통 사례 변경은 백엔드 테스트도 실행한다.
