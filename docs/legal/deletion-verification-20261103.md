# 기존 삭제 기능 검증 및 배포 설정

검증일: 2026-11-03. 신규 API·테이블·컬럼·운영 코드 변경 없음. 실제 개발·운영 DB와 S3를 사용하지 않고 별도의 일회용 PostgreSQL 17 컨테이너와 테스트 저장소 대역을 사용했다. 실제 배포 설정은 변경하지 않았다.

## 실행한 검증

- 기존 단위·H2·설정 테스트 28건 통과: 미디어 삭제 실패 재시도·참조가 생긴 경우 보호·배치 상한·후보 굶김 방지, 휴지통 스케줄 활성/비활성, 인증 정리 경합, 탈퇴·공유 보존, 푸시 정리 시간 기준 등.
- 기존 postgresDiaryPurgeTest 전체: 실행 29건 통과, 조건부 9건 건너뜀. 실 HTTP 영구 삭제, 실제 FK 참조 그래프, 휴지통 30일 경계·복원 경합, 공유 파일 보존·JSON 참조 검사 포함.
- 추가 보완 뒤 미디어 SQL·휴지통 경합 재검증: 실행 12건 통과, 선택적 실행계획 진단 1건 건너뜀. 미디어 유예 24시간 정확한 경계·1마이크로초 전후와 멤버 사진 보호를 추가했다.
- pushPostgresTest의 정리 관련 12건 통과: 종료 시각 기반 30일 삭제, 진행 중 전송·잠금·다른 환경·영구 중복 방지 receipt 보존, 만료 세션과 등록 암호문 정리.
- 중복 재실행 제외 70개 테스트 통과. 별도 font348 전용 환경이 필요한 미디어 잠금·업로드 테스트 8건과 선택적 EXPLAIN 1건은 전체 실행에서 건너뛰었으며 통과로 세지 않았다.
- 실 S3에 대한 삭제 요청, 실행 서버의 환경변수·IAM, 다중 서버의 실제 배치 실행 상태는 확인하지 않았다. 30일 초대·알림 삭제처럼 없는 기능을 테스트 통과로 취급하지 않았다.

## 인프라 설정 — 기존 기능만 활성화

아래는 권장 전달값이며 이 문서 작성으로 적용되지 않는다. 파기 작업이므로 먼저 위 정책과 대상 범위를 합의하고 한 환경에서 실행 결과를 확인한다.

### 이미 Compose 전달 경로가 있는 설정

```ini
MEDIA_EXPIRY_CLEANUP_ENABLED=true
MEDIA_DELETE_RETENTION=PT24H
AUTH_SESSION_CLEANUP_ENABLED=true
AUTH_SESSION_CLEANUP_DELAY_MS=60000
AUTH_SESSION_CLEANUP_INITIAL_DELAY_MS=300000
```

미디어 기본 실행 간격은 1시간, 최초 실행은 시작 15분 후, 배치 최대 100건이다. 폴더·버킷이 실제 자료와 일치해야 하며 S3 객체 삭제 권한이 필요하다. 삭제 실패는 재시도하므로 DB 행 소실만 보고 물리 삭제 완료로 판단하지 않는다.

### Compose에 명시적 전달을 추가해야 하는 기존 Spring 설정

현재 dev/prod Compose에는 휴지통·푸시 대기열 정리 설정의 명시적 environment 전달이 없다. 호스트 .env에 임의 이름을 쓰는 것만으로 컨테이너에 들어가지 않는다. 인프라 담당자가 아래 기존 프로퍼티를 application 설정 또는 컨테이너 SPRING_APPLICATION_JSON 등에 전달해야 한다.

```json
{
  "dio": {
    "diary": {"expiry-cleanup": {"enabled": true, "delay-ms": 60000, "initial-delay-ms": 300000, "batch-size": 20, "lock-timeout-ms": 1000}},
    "push": {
      "cleanup": {"enabled": true, "delay-ms": 60000, "initial-delay-ms": 300000},
      "queue-retention": {"enabled": true, "delay-ms": 60000, "initial-delay-ms": 300000},
      "delivery": {"enabled": false}
    }
  }
}
```

기존 SPRING_APPLICATION_JSON을 통째로 교체하지 말고 필요한 키만 병합한다. 이것은 설정 예시이며 배포 파일을 자동 수정하거나 새 설정 기능을 만든 것이 아니다.

- 휴지통 정리는 30일 고정 계약이며 이 예시는 1분 주기·시작 5분 후·20건씩이다.
- 푸시 대기열 정리를 켤 때 dio.push.environment와 dio.push.app-id가 실제 기존 대기열 환경·앱과 일치해야 한다. PUSH_ENVIRONMENT/PUSH_APP_ID도 컨테이너에 전달돼 있는지 확인한다. 맞추려고 과거 데이터의 환경을 임의 변경하지 않는다.
- 푸시 정리와 외부 푸시 발송은 별개다. 정리 때문에 Expo 발송을 켤 필요는 없다. 예시는 발송 비활성을 유지한다.
- PUSH_REGISTRATION_CLEANUP_ENABLED는 application.yml에 매핑돼 있지만 Compose에 명시 전달이 없으므로 덮어쓸 때 전달 경로를 확인한다. 기본 true인 경우 새로 켤 필요 없다.
- 탈퇴 프로필 사진 정리는 별도 enable 스위치 없이 기본 5분 주기다. dio.user.withdrawal-photo-cleanup-ms로 간격을 바꿀 수 있지만 이번에는 변경하지 않는다.
- 없는 초대·알림·비활성 토큰 30일 정리는 환경변수를 추가해도 생기지 않는다. 신규 API·테이블 없이 기존 서비스에 정리 기능을 넣을지 해당 도메인 담당자와 별도 결정한다.

## 활성화 후 확인

1. 실제 컨테이너에 값이 전달됐는지 확인한다. 비밀값 전체를 출력하지 않는다.
2. 테스트 자료로 30일 이전 휴지통·24시간 이전 삭제 미디어가 정리되지 않는지, 공유 참조 파일이 남는지 확인한다.
3. Expired diary cleanup의 deleted/failed와 미디어 삭제·실패 로그, push retention 결과를 확인한다. 스케줄이 돌았다는 사실과 삭제 성공을 구분한다.
4. 실제 S3 객체 삭제 여부와 실패 큐의 재시도를 확인한다. 버킷 전체 삭제나 공유 원본 일괄 삭제는 하지 않는다.
5. 기존에 쌓인 만료 자료도 활성화 후 대상이 된다. 처음 켜기 전 대상 규모와 필요한 보존 예외를 점검하고, 중단 시 설정만 끄면 이미 삭제한 자료가 복구되지는 않는다는 점을 인지한다.

원본 Google 문서·기존 방침·기존 개발 자료는 변경하지 않는다. 이번 검증 결과는 개인정보처리방침 전체 정책이 구현됐다는 보증이 아니다.
