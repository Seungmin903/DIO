# 신고 자동 정리 배포·운영 전달서 (내부용)

기준일: 2026-11-05. 운영 책임자: 신승민. 공개 문서 8종에 포함하지 않는다.

## 구현과 적용 범위

문안 검토 기준은 [최종 문안 README](final/README.md)의 단일 기준을 따른다. 아래 자동 처리 설명은 별도 기능 `feature/be/report-retention-cleanup`의 최초 구현 `d2c43258` 및 보완 `ae000f4a`·`85bf7c6e`에 관한 것으로, 검토 기준 develop에는 아직 포함되지 않았다. 이번 문서 작업에서 기능 브랜치를 병합하거나 운영 데이터·설정을 변경하지 않았다.

- user_reports에서 상태가 RESOLVED·DISMISSED이고 resolved_at이 현재 시각보다 30일 이상 이전인 행을 정리한다. 생성일이나 메일 SENT 시각 기준이 아니다. 미처리 건은 제외한다.
- 신고 DB 행 삭제와 증빙 storageKey의 report_evidence_deletion_queue 등록은 같은 트랜잭션에서 처리한다. 원본·설명·history_json·알림 발송 상태·멱등 기록은 신고 행과 함께 삭제한다.
- 파일 삭제에 성공하면 대기열 행도 삭제한다. 실패하면 시도 횟수·시각·오류 유형을 기록하고 재시도한다. 대기 간격은 1·2·4·8·16·32·64분으로 늘지만 실제 재시도는 배치가 실행될 때 이루어진다. 기본 배치는 1시간 간격이다.
- 기본 신고 처리량은 트랜잭션당 최대 20묶음×100건이다. 파일 대기열은 실행 전·후 각각 최대 100건 처리한다. 적체·장애 시 30일 직후에 모든 DB·파일이 삭제됐다고 보장하지 않는다.
- 고정 문구만 보내는 신고 알림 메일은 신고 자료 삭제 대상이 아니다. 개인정보 포함 문의 메일은 별도 문의 파기 기준을 적용한다.

## 배포 설정 — 안전성 보완 전 명시적 비활성화

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| REPORT_RETENTION_CLEANUP_ENABLED | false | 보완본 기본값. 미설정 시 비활성, 배포·운영 승인 뒤 **true 명시 시에만** 활성화 |
| REPORT_RETENTION | P30D | 처리 완료 후 보관 기간 |
| REPORT_RETENTION_CLEANUP_DELAY_MS | 3600000 | 실행 완료 후 다음 실행 간격 |
| REPORT_RETENTION_CLEANUP_INITIAL_DELAY_MS | 900000 | 서버 시작 후 첫 실행 대기 |
| REPORT_RETENTION_CLEANUP_BATCH_SIZE | 100 | 묶음당 정리 건수(코드상 1~500) |

신고 메일 활성화 변수와 독립된 기능이다. MEDIA_EXPIRY_CLEANUP_ENABLED를 대신 사용하지 않는다. V32의 삭제 대기열·인덱스와 V33__add_report_retention_hold.sql의 법적 보존 컬럼·제약을 적용해야 한다. 환경 파일 값이 컨테이너에 전달되는지 실제 배포 구성에서 확인한다. 임의로 운영 보관 기간을 단축해 테스트하지 않는다.

## 배포 전 확인·운영 점검

1. 기능 브랜치 병합·배포 버전과 V32·V33 적용 결과를 확인한다. 문서 수정만으로 배포 완료 처리하지 않는다.
2. 운영자가 관리하는 시험 데이터로 미처리 건 유지, 30일 전 완료 건 유지, 30일 경과 완료 건 삭제, 증빙 삭제 성공과 실패 후 재시도를 검증한다.
3. 배치 로그의 reportsDeleted·evidenceFilesDeleted와 DB·파일 저장소 결과를 대조한다. 메일 발송 성공과 신고 처리 완료를 혼동하지 않는다.
4. 오래 남는 대기열·반복 실패·잘못된 증빙 메타데이터 경고를 점검한다. 보완본은 파싱 실패 시 신고와 원래 메타데이터를 보존하고 대기열을 만들지 않는다. 운영자가 실제 파일 위치를 확인해 복구한다. 위치를 확인하지 않고 임의로 []로 바꾸지 않는다.
5. 파일 삭제는 현재 MediaFiles가 선택한 저장소를 사용한다. 과거 provider가 다른 증빙이 있으면 동일 storageKey만으로 올바른 파일이 삭제되는지 확인한다.
6. 보완본은 user_reports.retention_hold=true인 신고를 제외한다. 운영자가 DB에서 retention_hold_reason·retention_hold_by·retention_hold_at과 함께 설정하며, 해제 시 네 필드를 함께 초기화한다. 이미 삭제·대기열로 넘어간 신고의 소급 보존 기능은 아니다. 설정·해제 SQL과 제약은 기능 브랜치의 docs/report-retention-operations.md를 따른다. 실제 담당자 권한·점검 절차를 확인한 뒤에만 활성화한다.

## 탈퇴 계정의 차단 관계

신고 배치는 user_blocks를 정리하지 않는다. 관련 계정 탈퇴를 확인한 경우 운영자가 해당 계정의 양방향 차단 관계를 수동 정리한다. 다른 활성 계정의 차단은 유지한다.

## 정책과 문서

공개 문구는 완료 후 30일 경과 뒤 정리 대상으로 삼고, 현재는 보관 필요성·법적 보존을 확인한 운영자 수동 정리로 통일한다. 자동 정리는 검증·배포된 범위에서만 이용한다고 안내한다. 30일은 DIO 운영 기준이며 법이 모든 신고에 일률적으로 정한 보관 기간은 아니다. 불필요해진 개인정보는 지체 없이 파기한다.

## 비활성 기간 수동 정리

1. 신승민이 매일 미처리·처리 완료 건과 보관 필요성을 확인한다. 30일 경과 완료 건은 법적 별도 보존 여부를 먼저 판단하고 불필요한 자료는 지체 없이 정리한다.
2. 삭제 전 신고 ID·비공개 증빙의 실제 저장소·키를 검증한다. 메타데이터가 깨졌으면 DB 행을 먼저 삭제하지 않고 복구·대조해 파일 위치를 확보한다. 사진·회원정보를 Gmail·MM·Git에 복사하지 않는다.
3. 별도 보존 대상은 근거·항목·종료일·접근권한을 지정해 안전하게 보관한다. 자동 제외 기능이 있다고 간주하지 않는다.
4. 파일 삭제 결과를 먼저 확인한다. 실패하면 해당 위치·최소 관리정보를 비공개로 보존해 재시도하며 신고 행만 먼저 없애지 않는다. 성공 뒤 해당 신고 행과 임시 사본을 정리한다. 삭제는 검토·발송 작업과 겹치지 않는 운영 절차로 진행한다.
5. 처리 건수·시각·담당자·실패 대응을 최소 범위로 기록한다. 장기 적체·복구 실패는 운영 책임자가 즉시 확인한다. 수동 정리 준비 없이 배치를 끄기만 하고 파기 의무가 끝났다고 보지 않는다.
