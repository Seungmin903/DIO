## 방법과 재현

최초 환경 준비 (frontend 폴더):

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
```

이후 한 명령으로 실행한다:

```sh
pnpm qa:media
```

- 합성 데이터 생성 → 현재 작업 트리의 Web 빌드 → 127.0.0.1 전용 서버 → 새 BrowserContext의 QA → PNG/JSON 저장 → 브라우저·서버 종료를 자동 수행한다.
- 기본 포트는 0(자동 빈 포트 배정)이다. `pnpm qa:media -- --port 8093`처럼 원하는 포트도 지정할 수 있다. 기존 서버/사용자 브라우저에 연결하지 않는다.
- `pnpm qa:media -- --skip-build`는 이미 생성한 dist를 사용한다. 결과에 이 사실을 기록하므로 HEAD와 실행 코드가 다를 수 있음에 유의한다.
- 결과와 fixtures/다운로드 PNG는 저장소 내부 `frontend/qa/.out/<실행별 ID>/`에 생긴다. 이 경로는 gitignore 대상이다. 각 실행의 report.json을 Jira 첨부 또는 MR 검증 자료로 공유하고 문서에는 요약을 남긴다. 기존 원시 결과 JSON은 최초 실행 기록으로 보존하며 매번 덮어쓰지 않는다.
- 독립적인 데이터 생성만 필요하면 `node qa/generate-media-fixtures.mjs`를 사용한다. 기본 출력은 `frontend/qa/.out/fixtures`이며 인자로 경로를 명시할 수도 있다.
- Playwright는 devDependency/lockfile로 고정한다. OS 선택기 자체는 우회하지만 실제 File을 앱 importer에 넘겨 디코딩·IndexedDB·자동 저장 경로를 검증한다.
- 저장 키와 IndexedDB 이름/버전은 `storageContract.js`를 앱과 QA가 함께 참조한다. 저장 데이터 모델이나 객체 저장소 구조가 달라지면 fixture/픽셀 오라클도 검토해야 한다.
- 변형 좌표는 가져오기·자동 저장 확인 후 고정 fixture로 테스트 문서에 넣는다. 편집 제스처 검증이 아니다.
- 진입 흐름: 보관함 `새 다이어리` → 이름 입력 → `다이어리 만들기`(바로 편집기 진입). 목록 키(`STORAGE_KEYS.diaries`)에서 다이어리 ID를 찾아 편집 문서 키(`STORAGE_KEYS.doc:<diaryId>`)를 정한다. 새로고침·새 탭 뒤에는 보관함의 `<제목> 열기` 카드로 다시 들어간다.
- 편집기 확대는 Ctrl+휠로 하고, `화면에 맞춤` 버튼이 나타나는지로 실제 확대 여부를 확인한다.
- 반환 결과에 `fatal` 또는 case `status: failed`가 있으면 CLI가 실패 종료한다. 부분 통과를 전체 통과로 해석하면 안 된다.

최초 실행은 외부 Playwright 실행기로 수행했고 다운로드 산출물은 작업 공간 tmp/qa-75-run2에 남겼다. 신규 실행은 위 CLI와 저장소 내부 .out 경로를 사용한다.

- 보강 검증: 최초 Chromium 설치 후 `pnpm qa:media`의 전체 빌드/자동 포트 실행 통과, `pnpm qa:media -- --skip-build --port 8093` 실행도 통과했다. 각각 가져오기1/1·복원3/3·PNG다운로드5/5·손상 배치 롤백1/1이며 자동화 테스트56개도 통과했다.
- 이번 CLI는 고정된 devDependency의 Headless Chromium156을 사용했다. 최초 기록의 외부 Chromium155와 실행 환경이 다르므로 성능 수치를 개선 전후 비교로 해석하지 않는다. 기존 JSON은 당시 결과로 보존한다.
- 브라우저가 아직 설치되지 않은 경우 CLI가 비정상 종료와 함께 최초 설치 명령을 출력하는 것도 확인했다. 결과와 오류 기록은 .out에만 생성된다.
- 저장 상수 공유 모듈 분리 후 Android 번들도 통과했다. 네이티브 실기기 검증을 대체하지 않는다.
