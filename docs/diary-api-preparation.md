# 다이어리 API 연결 준비 (237~241)

기준: develop f6f663b에서 시작한 feature/fe/diary-api-preparation. 229 팀 합의 전 사전 작업이며 실제 서버 연동 완료가 아니다. 237~241 사전 구현을 Draft MR로 검토하며 계약·조사 문서는 포함하지 않는다.

## 구조와 적용 범위

- `services/diaryApi.js`: 화면 모델과 요청 DTO 변환, list/get/create/update/trash/restore 경계. HTTP transport는 토큰·메서드·JSON·요청 키·204·오류를 처리한다. 앱에서는 목 transport만 연결한다.
- `services/diaryQuery.js`, `hooks/useDiaryQuery.js`: 조회 중 기존 데이터 유지, 오류/재시도, 이전 응답 무시·취소·reset.
- `services/diaryMutation.js`, `hooks/useDiaryMutation.js`: idle/saving/success/error/partial. 즉시 중복 실행 차단, 입력 스냅샷 보존, 동일 요청 키 재시도. 일괄 처리는 순차 단건 호출이며 실패 ID만 재시도한다. 성공 ID와 재시도 불가능한 실패도 결과에 남긴다.
- `services/mockDiaryTransport.js`: 인스턴스별 메모리 저장. 생성·수정·휴지통 이동·복원과 목록 분리, 버전 충돌, 처리 후 응답 유실·동일 요청 키 중복 방지. 앱 재시작 시 초기화한다.
- `screens/ConnectedDiaryLibrary.js`: 기존 목록·검색·카드를 재사용한다. 카드는 조회 전용이며 편집기로 들어가지 않는다.
- `screens/DiaryMutationPanel.js`: 개발용 생성/수정/일괄 휴지통/복원 검증기. 210·211·204의 실제 화면을 대체하지 않는다. 화면 담당 결과에는 공통 command/hook을 연결한다. 제목과 샘플 첫 페이지로 동작을 검증하며 전체 생성 옵션 UI를 구현하지 않았다.
- 기본 앱은 기존 로컬 경로다. EXPO_PUBLIC_DIARY_SOURCE=mock일 때만 검증 화면을 연다. 로컬 useDiaries/편집 문서는 마운트하지 않는다. 기존 검색 UI의 최근 검색어 저장은 별개로 유지한다.

## 실행과 확인 순서

이 작업 폴더의 frontend에서:

```powershell
$env:EXPO_PUBLIC_DIARY_SOURCE='mock'
npx expo start --web
```

1. 상단 ‘API 연결 검증 · 목 응답 · 샘플 데이터’를 확인한다. 폰에서는 가로 버튼 줄을 스크롤한다.
2. 조회: 정상 → 상세 열기/닫기 → 한 번 실패/재시도 → 계속 실패 → 빈 목록 → 상세 없음 → 정상/목록 새로고침. 조회 중 기존 목록이 남는다.
3. 목 생성: 제목 입력 → 저장 한 번 실패 → 요청 저장. 저장 중 저장/닫기가 비활성화되고 실패 후 입력이 남는다. ‘같은 입력 다시 저장’으로 성공하면 목록에 한 번만 나타난다.
4. 목 수정: 대상 선택 → 제목 변경 → 버전 충돌 → 요청 저장. 저장 정상으로 바꾸고 ‘입력 유지하고 최신 내용 확인’을 누른다. 입력과 최신 제목을 비교한 뒤 저장하면 목록이 갱신된다.
5. 권한 없음/복원 만료: 각각 오류 안내를 확인한다. 이런 오류에는 단순 재시도 버튼이 없다. 실제 권한 재검증은 서버 연동 후 확인한다.
6. 목 휴지통 이동: 여행 기록/함께 쓰는 일기 선택 → 선택 항목 처리 확인 → 일부 실패 → 요청 저장. 1개 성공/1개 실패 후 저장 정상 → 실패 항목 다시 시도. 이미 성공한 항목은 재전송하지 않는다.
7. 목 복원: 휴지통 목록에서 대상 선택 → 처리 확인 → 저장. 정상 목록에 복귀한다. 성공 전에는 화면에서 미리 삭제하지 않는다.
8. 응답 유실: 목 생성에서 선택 후 저장하면 서버 처리에 해당하는 메모리 변경 뒤 오류를 반환한다. 같은 입력 다시 저장으로 중복 생성 없이 결과를 확인한다.
9. 폼에서 저장하기 전 닫으면 요청을 보내지 않는다. 성공·부분 성공 뒤 목록 재조회가 실패하면 저장 상태와 목록 오류를 별개로 표시한다.

저장 실패 후 재시도하는 동안 입력을 잠가 동일 요청 키에 다른 입력이 섞이지 않게 한다. 충돌은 최신 데이터를 확인하고 새 요청으로 저장한다. 폼 닫기는 재시도 대기 입력과 요청 키를 유지한다. 계정 경계/unmount의 reset은 취소 신호를 전달하고 아직 전송하지 않은 항목을 중단하며 늦은 응답을 무시한다. 이미 처리된 서버 변경을 되돌리는 것은 아니다.

로컬 모드로 돌아갈 때 서버를 종료한 뒤:

```powershell
Remove-Item Env:EXPO_PUBLIC_DIARY_SOURCE -ErrorAction SilentlyContinue
npx expo start --web
```

## 241 영구 삭제·보관 만료 사전 작업

- `permanentlyDelete`는 DELETE /diaries/{id}?permanent=true를 호출하며 204를 허용한다. 기존 목 명령의 중복 차단·실패 ID만 재시도를 재사용한다.
- 목 영구 삭제 화면에서 휴지통 항목을 선택하고 ‘선택 항목 영구 삭제’를 누르면 공용 ConfirmDialog로 대상 수와 복원 불가를 확인한다. 취소하면 요청하지 않는다. 실패 시 항목을 유지하고 성공 응답 이후 목록을 재조회한다.
- 응답 유실은 같은 요청 키로 재시도한다. 서버 중복 처리 보장 합의가 필요하다. 404는 자동 성공으로 간주하지 않고 오류를 유지한 채 재조회한다.
- `expiresAt`, `retentionStatus`(RETAINED/EXPIRED), `canRestore`는 서버 응답 제안 필드다. 화면은 기기 시각으로 만료를 계산하지 않는다. 알려지지 않은 복원 가능 상태는 복원 불가로 처리한다.
- 목 서버 시각으로 삭제 시각 + 30일을 계산한다. 정확히 30일이면 EXPIRED이고 복원 요청은 410을 반환한다. 조회 시 만료 항목을 곧바로 지우지 않아 정리 대기 상태도 검증한다.
- 휴지통 화면의 ‘목 서버 30일 경과’는 개발용 서버 시계만 이동한다. ‘목 서버 만료 정리’는 서버 배치 완료를 흉내 내며 실제 API 메서드가 아니다. 실제 환경에서 클라이언트는 자동 삭제를 호출하지 않는다.
- 목록을 본 뒤 만료된 경우: ‘복원 만료’ 시나리오로 복원을 시도하면 410과 함께 목 서버 상태가 만료로 바뀌고 재조회에서 복원 불가를 표시한다. 단순 재시도는 제공하지 않는다.
- 실제 API 연결 시 휴지통 진입·앱 복귀·변경 완료 후 재조회, 인증/권한, 서버 필드/오류 코드, 배치 완료 후 제외 정책을 확정해야 한다. 기본 로컬 앱의 기존 보관 타이머는 수정하지 않았다.
- 241 로직 포함 테스트 33개 통과. 실제 DB 삭제·파일 참조 정리·서버 배치·iPad/Android 검증은 남아 있다.
- 241 포함 웹 QA: 1280×800 / 412×892 각각 14개 흐름 통과, pageerror 0. 영구 삭제 확인 취소·실패 유지·재시도 성공, 서버 만료 시 복원 선택 비활성 및 정리 후 빈 목록을 확인했다.


## 237~241 리뷰 수정

- 폼 닫기 `dismiss`와 계정 경계 `reset`을 구분한다. 재시도 대기 요청이 있으면 다른 작업을 열어도 기존 작업/입력을 복구한다. 새 요청 키로 덮어쓰는 `run`은 차단하고 동일 키 `retry`만 허용한다. 확인 성공 후에는 새 작업이 가능하다.
- 응답 유실 확인 방법: 목 생성에서 제목 입력 → 응답 유실 → 저장 → 실패 후 닫기 → 목 수정 클릭. 새 수정 화면 대신 이전 생성 요청을 보여준다. 저장 정상 → 같은 입력 다시 저장 → 닫기 후 목록에 하나만 생성됐는지 확인한다.
- 현재 보존 범위는 동일 계정의 검증 화면 인스턴스 내 폼 닫기/다시 열기다. 앱 재시작·계정 변경 간 영속 복구는 구현하지 않았다. 실 서버 연결 전에는 사용자별 보류 요청 저장·서버 결과 조회/중복 방지 계약을 확정해야 한다.
- 일괄 작업은 각 항목 전송 전 취소 신호를 확인한다. reset 직후 첫 요청이 아직 시작 전이면 첫 요청도 보내지 않는다. 진행 중 요청이 늦게 완료되더라도 다음 ID를 보내지 않는다. 토큰 조회 중 취소되면 fetch를 시작하지 않는다.
- 조회 조건과 signal을 마지막 옵션 객체 하나에 합친다. 목록 조건을 유지한 재시도와 상세 ID+옵션 호출 모두 취소 신호를 전달한다. 휴지통 새로고침 버튼은 클릭 이벤트가 조회 옵션으로 들어가지 않도록 인자 없이 실행한다.
- 수정 응답 ID가 요청 ID와 다르면 INVALID_RESPONSE 오류로 처리하며 성공 결과에 반영하지 않는다.
- 회귀 테스트 7개 추가, 총 40개 통과. 기존 테스트도 함께 실행했다.
- 리뷰 수정 후 목 웹 번들 성공. 브라우저 QA는 1280×800/412×892 각각 15개 흐름 통과, pageerror 0. 응답 유실 → 닫기 → 다른 작업 열기 → 이전 입력 복구 → 같은 키 재시도 → 단일 생성까지 확인했다.
