# 캔버스 대량 편집 요청 제한

Jira: S15P31F106-475. 프론트와 문서만 수정한다.

## 백엔드 기준

- `CanvasElementBatchRequest`: creates·updates·deleteElementIds·restoreElementIds 각각 최대 100개.
- `CanvasOperationRequest`: 동일 changes 계약을 사용하며 expectedVersions는 최대 200개.
- 모든 변경 종류를 합쳐 100개라는 뜻은 아니다. 생성100·수정100·삭제100은 개수 제한 안이다.
- 기존 propertiesJson 합계 4MiB 등의 다른 서버 제약은 그대로 유지한다. 이번 작업은 개수 경계 보완이다.

## 동작

1. 회원 편집기의 새 행동과 진행 중 제스처에서 서버로 보낼 요소 변경 수를 확인한다. 제한을 넘는 변경은 적용하지 않고 직전 문서·선택·Undo/Redo·대기 작업을 유지하며 종류별 100개 안내를 기존 토스트로 즉시 표시한다. 하단 저장 상태를 눌러야만 안내가 보이는 경로를 보완했다. 범위 안의 후속 행동은 기존 저장 경로로 처리한다.
2. 개인 elements/batch와 공유 canvas-operations, 저장 경로 준비에도 공용 검증을 적용한다. 초과 요청은 HTTP 쓰기 전에 거부한다. 미디어 준비 전에도 검사한다.
3. 이전 버전에서 저장된 초과 작업은 삭제·분할·성공 처리하지 않는다. 기기 journal의 현재 작업과 후속 큐를 보존한 채 동기화를 보류하고 이유를 안내한다. 로컬 오류에 HTTP 상태를 붙이지 않아 서버의 영구 거절로 분류해 큐에서 제거하는 경로에 들어가지 않는다.
4. 원격 요소 수신과 게스트 편집은 제한 대상이 아니다. 개인/공유 API 선택·명령 ID·정상 작업의 Undo/Redo 단위는 유지한다.

레이어 순서 변경은 선택 개수보다 많은 요소의 sortKey를 바꿀 수 있으므로 실제 변경 수가 100개를 넘으면 차단될 수 있다. 작업을 자동 분할하면 한 사용자 행동의 원자성과 이력 단위가 바뀌므로 이번 작업에서 분할하지 않는다.

## 기존 대기 작업의 한계

과거 초과 작업이 큐 맨 앞에 있으면 이를 임의로 건너뛰지 않으며 후속 전송도 보류된다. 재시작·재시도 시 작업과 기기 원본은 유지하지만 해당 큐를 자동 분할하거나 복구하는 UI는 제공하지 않는다. 오류 문구에 이후 편집도 서버에 저장되지 않고 기기에만 보관 중이며, 재시도만으로 해결되지 않아 별도 복구가 필요함을 명시한다. 폐기 확인·분할·내보내기 등의 복구 경로는 후속 범위로 남는다. 새 작업은 편집기 적용 단계에서 제한해 이 큐가 새로 생기는 것을 방지한다.

## 안내 반복 방지

- 같은 제스처에서 제한에 걸리면 제스처 ID로 한 번만 안내한다. 반복 이동 이벤트는 기존 state 참조를 유지하며, 토스트를 표시한 뒤에도 해당 제스처의 안내 완료 표시는 유지한다.
- 편집기에서 안내를 소비한 뒤 ID가 일치하는 오류만 지우는 액션을 보낸다. 다른 페이지·편집 비활성 상태의 지난 안내는 표시하지 않고 정리한다. 새 제스처는 다시 안내할 수 있다.
- 적용 전 차단은 서버 동기화 실패가 아니므로 훅에서 저장 상태를 error로 바꾸지 않는다. 실제 저장 큐에서 발생한 제한 오류는 기존 저장 오류 안내를 유지한다.

## 드래그 검사 비용 보완

- 좌표 x/y만 변경하는 제스처는 누적 대상 ID만 검사한다. 요소 ID 인덱스는 변경 불가능한 객체 배열을 키로 WeakMap에 캐시하며, 요청과 같은 소수 셋째 자리 반올림 기준으로 실제 변경 수를 센다. 원위치 복귀한 요소는 변경 수에서 제외한다.
- 본문·크기·기타 속성 변경이나 원격 문서 반영 후에는 전체 검사로 복귀한다. 제스처 완료 시 최종 작업의 전체 검사는 유지한다. 따라서 이 최적화가 캔버스 렌더링이나 reducer 전체를 O(1)로 만드는 것은 아니다.
- 측정 스크립트: frontend에서 `node qa/canvas-batch-limit-perf.mjs`. 텍스트 요소1,000개, 좌표 변경100이벤트, 준비1회 제외 측정3회의 이벤트당 중앙값을 출력한다. 실제 서버·화면·기기 FPS를 측정하지 않는다. 자동 성능 합격 기준으로 사용하지 않는다.

동일 PC Node에서 변경 전/최종 변경 후 측정:

| 1,000개 페이지에서 선택한 수 | 변경 전 ms/이벤트 | 변경 후 ms/이벤트 |
|---|---:|---:|
| 1개 정상 이동 | 8.514 | 0.106 |
| 101개 제한 차단 | 10.220 | 0.054 |

측정 환경과 실행 부하에 따라 값은 달라진다. 누적 대상의 제한 경계, 원위치 복귀·반올림, 비대상 요소의 본문 직렬화 생략, 다른 속성 변경 후 전체 검사 복귀를 검증했다. 사용자 실기기에서 일반 드래그와 초과 차단·단일 안내도 재확인했다. 실기기 FPS나 처리 시간은 측정하지 않았다. 최종 테스트 수는 아래 표에만 기록한다.

배열별 100/101, 혼합 총합300, expectedVersions 200/201, 개인·공유 API 차단과 정상 한 번 전송, 문서/선택/이력 보존, 제스처, 원격 수신·게스트 유지, 과거 큐 재시작 및 준비된 restore 요청 보존을 검증한다. 실제 편집기 훅에서 개인·공유 제한 안내와 후속 정상 쓰기도 확인한다.

제스처별 단일 안내, 소비 후 재안내 방지, 새 제스처 재안내, 오래된 소비가 새 알림을 지우지 않음 및 큐 차단 안내 문구도 검증했다. 사용자 실기기 재확인에서도 101개 이상 선택의 연속 드래그 중 단일 안내, 손을 뗀 뒤 새 드래그의 재안내, 다른 페이지 방문 후 지난 안내가 자동 재등장하지 않음을 확인했다.

자동 검증에서는 실제 서버에 대량 쓰기를 보내거나 백엔드 테스트를 실행하지 않았다. 아래 실기기 결과는 사용자 확인 기준이다.

## 실기기 확인

2026-11-03 사용자 확인 완료: 개인·공유 서버 다이어리에서 제한 초과 이동 차단과 토스트 안내, 제한 이내 이동 및 재진입 후 유지가 정상 동작했다. 앞서 안내한 생성·이동·삭제·실행 취소·다시 실행 흐름도 확인 완료로 보고받았다. 실제 요청 로그·모든 제한 조합의 실기기 측정은 별도로 수집하지 않았다.

- 서버 다이어리에서 소량 생성·이동·삭제와 Undo/Redo가 정상인지 확인한다.
- 테스트용 자료가 충분하면 101개 이상 선택 이동·삭제 시 안내가 나오고 기존 요소가 유지되는지 확인한다.
- 선택을 100개 이하로 줄여 다시 실행하면 저장되고 재진입 후 유지되는지 확인한다. 레이어 재정렬은 위의 실제 변경 수 제한과 구분한다.
