# 푸시 초대 연결 격리 구현

이 변경은 !227 기기 연결과 !222 초대 알림을 전제로 한다. 푸시 대기열 생성과 발송은 기본 비활성이며 실제 발송은 검증하지 않았다. 초대 알림은 같은 트랜잭션에서 범위가 지정된 outbox를 기록한다. V25는 환경·앱 범위를 추가하며 범위가 없는 기존 행은 자동 발송하지 않는다. 제출 전 최신 develop과 다른 MR의 migration 번호를 다시 확인한다.

## 기기 복구

최초 등록 요청 ID·입력과 기기 secret은 기기 안전 저장소에 보관한다. 같은 계정의 새 세션에서 무작위 요청 ID와 입력이 일치하면 이전 세션의 활성 여부와 무관하게 24시간 내 등록 응답을 복구한다. 응답 조회는 기존 연결을 변경하지 않고 이후 기기 secret을 사용해 새 세션을 결합한다. 삭제된 설치나 만료된 응답은 새 설치로 재시도한다. 동일 계정의 기존 설치가 차지한 토큰을 새 설치로 이전할 때 기존 연결과 대기 전달을 폐기한다. 다른 계정 소유 토큰은 회수하지 않는다. 따라서 다른 계정으로 재설치하며 이전 설치 secret을 잃은 경우 409가 남으며 이전 계정으로 복구하거나 별도의 검증된 회수 정책이 필요하다.

`GET /api/v1/push/installations/{id}/binding`은 인증 JWT와 `X-DIO-Installation-Secret`을 함께 요구한다. secret 보유자가 계정 전환 전에 연결 버전·기기 상태를 확인한다. secret·푸시 토큰·기존 계정 ID는 응답하지 않는다. 이를 사용해 BIND 응답 유실 후 버전을 다시 조회할 수 있다.

## 발송과 클릭

앱은 `EXPO_PUBLIC_PUSH_ENABLED=true`로 빌드했을 때만 OS 권한 요청·기기 등록을 실행한다. Android 채널을 만든 뒤 권한과 Expo 토큰을 요청하고 토큰 변경과 앱 복귀 시 갱신한다. 초대 푸시에는 초대 식별자만 넣고, 클릭 후 현재 로그인 세션과 초대 조회 결과를 검증해 기존 공유 화면으로 이동한다. 시스템 배너의 형태는 OS가 결정한다.

서버 outbox 활성화에는 `DIO_PUSH_OUTBOX_ENABLED=true`, 양수 `DIO_PUSH_OUTBOX_TTL_SECONDS`, 기존 `PUSH_ENVIRONMENT` 및 `PUSH_APP_ID` 설정이 필요하다. 잘못된 설정은 서버 시작 시 거부하므로 운영 정책을 결정한 뒤 함께 배포한다. 생산자와 워커는 application.yml의 같은 `dio.push.environment`, `dio.push.app-id` 설정을 사용한다. `DIO_PUSH_DELIVERY_ENABLED=true`가 없으면 워커와 Expo 게이트웨이는 네트워크 발송을 수행하지 않는다. 키링은 기존 !227 운영 절차를 따른다. Expo 강화 보안을 사용하는 경우 `DIO_PUSH_EXPO_ACCESS_TOKEN`을 비밀 관리 시스템으로 주입한다.

워커는 outbox를 환경·앱별로 분배하고 각 전달에 대한 현재 사용자·세션·연결 버전·토큰 버전과 초대·알림 상태를 재검증한다. 잠금 대기 후 세션과 대기열 만료도 다시 검사하며 이미 참여했거나 삭제된 다이어리의 초대는 취소한다. 일시 실패는 최대 6회 지수 간격으로 재시도하며 Expo 접수 ID와 접수 시각을 저장해 대기열 TTL과 별도로 최대 24시간 receipt를 조회한다. 별도 단일 스레드 스케줄러를 사용해 다른 예약 작업을 점유하지 않는다. 이전 토큰의 실패 receipt는 새 토큰을 비활성화하지 않는다. Expo 접수와 실제 기기 표시를 동일하게 취급하지 않는다.

분배 단계에서 항목 하나가 실패하면 같은 순회에서는 건너뛰고 다른 항목을 처리하며, 해당 항목은 다음 순회에서 다시 시도한다. 실패를 영구 취소하지 않는다. 분배 순회는 25건으로 제한되므로 앞쪽 25건이 계속 실패하면 뒤의 대기열 분배가 지연될 수 있다. 지속 실패 로그와 대기열 경과 시간을 관측해 원인을 해결해야 하며, DB에 남는 분배 단계별 재시도·격리 정책은 아직 없다.

발송 중 사용자·세션·기기·알림·초대 행의 잠금을 유지하며 HTTP 타임아웃은 10초다. 같은 사용자 요청과 초대 상태 변경이 그 시간 동안 대기할 수 있다. 앱의 토큰 발급 및 기기 API 요청은 각각 20초 제한을 둔다. 프로세스가 Expo 접수 후 DB 커밋 전에 종료되면 재시도에 따른 중복이 가능하다. TTL은 확정 정책이 아니며 실제 발송 전 운영 담당자 결정이 필요하다. Expo 자격증명·FCM/APNs, 운영 키·권한, Android/iPad 개발 빌드, 실제 수신·클릭 이동과 운영 모니터링은 아직 검증하지 않았다.

## 발송 잠금 운영 전 결정

현재 스케줄러는 인스턴스당 한 스레드지만 인스턴스 수가 늘면 동시 HTTP 호출과 DB 연결 점유도 늘어난다. 한 번의 조회 주기는 순차적으로 여러 전송과 receipt를 처리하므로 HTTP가 느리면 큐 지연이 쌓인다. 타임아웃은 개별 HTTP 요청의 상한이며 잠금 대기·DB 처리까지 포함한 전체 트랜잭션 시간의 상한은 아니다.

활성화 전 운영 담당자는 인스턴스 수와 DB 연결 풀 여유를 확인하고, Expo 호출 지연·실패율, 미처리 건수 및 가장 오래된 대기 시간, DB 풀 사용률·대기 시간, 로그인 갱신·로그아웃·초대 취소 응답 시간과 잠금 대기를 관측할 수 있어야 한다. 서비스 목표에 맞는 경보·중지 기준과 `DIO_PUSH_DELIVERY_ENABLED=false`를 통한 중지 및 큐 재처리 절차를 정하고 격리 환경에서 장애 주입으로 검증한 뒤 위험 수용 여부를 결정한다. 이 조건을 충족하기 전에는 발송을 활성화하지 않는다.

잠금을 HTTP 밖으로 옮기는 lease 방식은 지연을 줄일 수 있지만 마지막 유효성 검증과 실제 전송 사이에 로그아웃·계정 전환·초대 취소가 일어날 수 있다. 결과 저장 시 버전을 재검증해도 이미 접수된 푸시는 회수되지 않는다. 전환하려면 이 발송 경계의 허용 범위와 만료 lease 회수·중복·오래된 토큰·수신 클릭 재검증을 먼저 합의하고 PostgreSQL 경합과 장애 복구를 시험해야 한다.

## 푸시 대기열 30일 보관

초대 푸시 대기열과 전달 기록은 만료 및 모든 전달의 최종 처리 이후 30일 보관한다. 이는 사용자 알림과 같은 기간이지만 정리 대상은 별도이며, 알림과 초대 중복 방지 receipt는 이 정리 작업이 지우지 않는다. V26은 종료 시각을 저장하고 기존 종료 행은 마이그레이션 시점부터 보수적으로 30일을 계산한다. receipt 확인 중인 SENT, PENDING, LEASED와 범위가 없는 기존 행은 삭제하지 않는다.

대기열 정리는 `DIO_PUSH_QUEUE_RETENTION_ENABLED=true`를 명시하기 전까지 비활성이다. 환경·앱 범위가 올바른 초대 대기열만 대상으로 하며, 만료된 PENDING은 잠긴 전달을 건너뛰고 취소한 뒤 30일 후 삭제한다. 발송 중이거나 receipt 확인 중인 항목과 잠긴 행은 재실행에서 다시 확인한다. 한 번에 최대 100개 부모를 검사하고 삭제 시 자식 전달만 연쇄 삭제한다. 알림 및 `invitation_notification_receipts`는 남겨 재전달을 방지한다. 다른 유형 또는 이력이 없는 행은 자동 삭제하지 않고 운영자가 조사한다.

로그는 검사·취소·삭제·잠금 건너뜀 건수만 남긴다. 0건이나 잠금 건너뜀은 전체 정리 완료를 뜻하지 않는다. V26은 기존 종료 행을 갱신하고 인덱스를 생성하므로 배포 전 실제 행 수와 적용 시간을 확인해야 한다. 운영 활성화 전 인스턴스별 설정, 백업과 복구, NULL 범위 및 이력 누락 행의 별도 처리와 오래된 receipt 대기·LEASED에 대한 모니터링 절차가 필요하다. 스케줄러는 푸시 전용 단일 스레드를 사용하므로 발송 지연이 정리 실행도 지연시킬 수 있다.
