# MVP1 이미지 가져오기·로컬 원본 저장

관련 이슈: S15P31F106-67, S15P31F106-68. 페이지 전체 PNG 생성은 이후 내보내기 태스크에서 구현한다.

## 실행 환경

프론트는 Expo SDK 57 / React Native JavaScript다. 웹 미리보기는 react-native-web을 사용한다.
네이티브는 `Paths.document/dio-media`에 원본과 표시용 파일, AsyncStorage에 파일별 메타데이터를 보관한다.
웹은 기존 `dio-media` IndexedDB를 v3로 올려 `blobs`, `metadata`, `displays`에 하나의 트랜잭션으로 저장한다.
v1 GIF와 기존 문서의 data URI는 읽을 수 있으며, 기존 원본을 일괄 이동하거나 삭제하지 않는다.

## 초기 정책

- JPEG, PNG, 정지 WebP, HEIC, GIF. 확장자가 아닌 파일 시그니처와 실제 이미지 디코딩을 검사한다. HEIC는 HEVC 정지 이미지 브랜드(`heic/heix/heim/heis`)를 인식한다. AVIF 및 HEIC 시퀀스·Live Photo 영상은 대상이 아니다.
- 정지 사진: 파일당 50MiB(52,428,800바이트), 가로·세로 각각 12,000px, 전체 64,000,000화소 이하. 8,064×6,048 같은 48MP 사진을 허용한다.
- GIF: 변환 없이 애니메이션을 보존하므로 50MiB·가로·세로 각각 4,096px 제한을 둔다. 정책은 `mediaPolicy.js`에서 조정한다.
- 정책값은 초기 제안값이다. 제품 검토·실기기 측정 후 조정 가능하다.
- picker가 반환한 원본은 압축·축소·재인코딩하지 않는다. GIF도 그대로 보관한다. HEIC는 원본 `.heic`와 표시용 JPEG를 분리한다.
- 표시용 축소본은 긴 변 기준 사진 2,048px, 스티커 512px, 테이프 1,400px 이하로 만들며 작은 파일은 확대하지 않는다. PNG/WebP 소재는 PNG로 투명도를 보존하고 JPEG/HEIC는 JPEG로 만든다. 작은 JPEG/PNG/WebP는 별도 표시본을 만들지 않고 원본을 재사용한다.
- HEIC 변환: 네이티브는 Expo ImageManipulator/OS 디코더, 웹은 `heic-to/csp`를 사용해 로컬에서 처리한다. 서버 업로드는 없다. 변환을 지원하지 않는 기기·손상 HEIC는 `HEIC_CONVERSION_FAILED`로 안내한다. 구현 근거: [heic-to 공식 문서](https://github.com/hoppergee/heic-to).
- picker 자르기를 끄고 quality=1로 설정한다. 반환받은 파일 바이트를 보존하며 OS picker 이전 원본과 동일한지는 기기별 확인이 필요하다.
- 다중 선택은 한 장씩 검사·가공·저장해 디코딩 결과가 메모리에 누적되지 않게 한다. 어떤 단계에서든 실패하면 이번 호출에서 저장한 원본과 표시본을 함께 롤백한다. 전체 성공/실패 계약은 유지한다.
- 취소·검사 실패는 캔버스 변경을 만들지 않는다. 파일 형식·용량·해상도·읽기·디코딩·저장 오류를 구분한다.

## 호출 계약

`pickImages({ multiple: true, usage: 'photo' })`는 선택 취소 시 `[]`, 성공 시 아래 메타데이터에 `name`, `poster`를 더한 배열을 반환한다. `usage`는 `photo/sticker/tape`이며 표시본의 최대 크기를 결정한다.
웹에서 picker는 클릭 이벤트 안에서 즉시 실행한다. 전체 사진첩 접근 권한을 미리 요청하지 않는다.
웹은 `<input type="file">`로 파일을 받은 뒤 앱에서 디코딩한다. Expo 웹 picker의 사전 디코딩으로 HEIC가 변환 전에 거부되는 경로를 우회한다. 취소 이벤트 및 창 복귀 시 입력 요소·리스너를 정리한다.
중복 클릭은 기존 picker가 종료될 때까지 무시한다.

```js
{
  mediaFileId: 'UUID 문자열',
  originalName: 'motion.gif',
  mimeType: 'image/gif',
  extension: 'gif',
  fileSize: 131387,
  width: 128,
  height: 128,
  createdAt: 'ISO 8601',
  src: 'media:UUID 문자열'
}
```

- `mediaService.import(pickerAsset)`: 파일 검사와 저장 후 위 객체를 반환한다.
- 메타데이터 `width/height/fileSize/mimeType/extension`은 원본 기준이다. 표시본이 있으면 `display: { width, height, fileSize, mimeType, extension }`를 추가한다. 원본과 표시본은 같은 ID에 속한다.
- `mediaService.get(mediaFileId)`: `{ media, blob, displayBlob }`를 반환한다. `blob`은 항상 원본이고 `displayBlob`은 표시본 또는 `null`이다. 웹은 Blob, 네이티브는 Expo File이다.
- `mediaUri(src)`: 표시본이 있으면 표시본, 없으면 원본의 렌더링용 주소를 반환한다. 영구 데이터로 저장하지 않는다.
- `hydrateMedia()`: 저장된 원본을 기존 동기 렌더러에 연결한다.

캔버스 객체는 기존 `src: media:ID` 계약을 유지하고 `mediaFileId`도 갖는다.
새 미디어의 영구 식별 기준은 `mediaFileId`이며, 새 객체의 `src`는 동일 ID에서 생성하는 `media:{mediaFileId}` 호환 필드다. 서로 다른 파일을 가리키도록 별도로 수정하지 않는다. 기존 `src` 렌더러와 이전 data URI 문서는 유지하고, ID 중심 조회 통합은 S15P31F106-69에서 처리한다.
보관함용 poster는 파생 썸네일이다. PNG 내보내기 시 GIF 첫 표시 프레임은 원본에서 별도로 추출해야 하며, poster를 최종 출력 원본으로 쓰지 않는다.
최종 PNG 렌더러는 `mediaService.get`의 원본·표시본 메타데이터를 조회해 필요한 출력 픽셀 수에 충분한 소스를 선택한다. 표시본을 원본으로 취급하지 않으며, 픽셀 수가 충분할 때만 활용한다. HEIC와 메모리 제한 정책은 [출력 명세](../내보내기/페이지%20내보내기%20렌더러.md)를 따른다. 67·68 작업 자체는 페이지 내보내기를 구현하지 않는다.
썸네일 조회·생성은 선택적 후처리다. 실패하면 `poster: null`로 저장된 원본 참조를 반환해, 화면에는 실패만 보이고 원본만 남는 경로를 방지한다. 네이티브는 썸네일을 생성하지 않으므로 이 단계의 재조회를 생략한다.
이미지를 지운 페이지의 Undo/다른 페이지 참조가 있을 수 있어 원본 자동 삭제는 이 작업에 포함하지 않는다.

## 실패 및 일관성

원본·표시본·메타데이터 저장 완료 후에만 성공을 반환한다. 네이티브 파일 복사 성공 뒤 표시본 복사나 메타데이터 저장에 실패하면 두 파일을 정리한다. 가공 캐시는 성공·실패 모두 정리하며 picker 원본은 건드리지 않는다.
네이티브에서는 DB와 파일시스템을 하나의 트랜잭션으로 묶을 수 없으므로 프로세스 강제 종료 시 미참조 파일이 남을 수 있다. 재시도형 원본 정리는 후속 작업이다.
화면 표시 URL은 세션 캐시이며 hydration 시 중복 생성한 웹 URL은 해제한다.

## 검증

```sh
cd frontend
pnpm test:media
pnpm exec expo export --platform web
pnpm exec expo export --platform android --output-dir dist-android
pnpm web
```

자동 테스트는 HEIC 시그니처·48MP 경계·용도별 축소 크기·손상 파일·GIF 변환 우회·가공 캐시 정리·배치 롤백·IndexedDB v1 호환·원본/표시본 분리·메타데이터 원자성을 확인한다. 네이티브 테스트는 Expo IO 경계를 모의하므로 OS의 실제 HEIC 디코딩 성공을 보증하지 않는다.
실제 브라우저에서 PNG/GIF 선택, 원본 SHA-256 일치, 새로고침 후 이미지 복원을 확인했다.
리뷰 반영 후 브라우저 추가 확인: libheif 공식 `examples/example.heic`의 원본 SHA-256 일치 및 JPEG 표시, 8,000×6,000 JPEG의 원본 보관과 2,048×1,536 표시, 4,000×2,000 투명 PNG의 512×256 스티커 변환과 모서리 alpha=0 유지, 새로고침 후 HEIC·고해상도 사진 표시본 복원. 웹·Android 번들 생성 및 테스트 13개 통과.
네이티브는 Android 번들 생성까지 확인했으며 기기에서 사진첩 취소·권한·GIF 유지·강제 종료 후 복원 검증은 남아 있다.

## 남은 검증 및 후속 작업

- iPhone/iPad 실기기에서 HEIC 회전 방향, 사진 선택·취소, 실제 GIF 원본 유지, 강제 종료 후 표시본 복원을 확인한다. Android HEIC는 OS 디코더 지원에 영향을 받는다.
- 48MP 처리 시 한 장의 디코딩 피크 메모리는 여전히 기기에 의존한다. 50MiB·64MP 정책은 저사양 실기기 측정 후 낮출 수 있다.
- 기존 v1/v2 고해상도 데이터는 원본으로 복원한다. 새 표시본은 새로 가져오는 파일부터 적용하며 기존 자료 일괄 가공은 후속 작업이다.
- 다중 선택은 전체 성공/실패 계약이다. 부분 성공을 지원하려면 파일별 실패 결과와 안내 UI를 함께 설계한다.
