# 회원 다이어리 생성 트랜잭션 기반

현재 연결 상태(2026-10-27): 231 생성·232 회원 목록·233 상세/수정과 회원 기본 앱 연결을 구현했다. 아래 단계별 검증 수치는 당시 기록이며 최신 통합 검증은 [develop 통합 검토](./회원%20다이어리%20develop%20통합%20검토.md)를 따른다.

관련 이슈: [S15P31F106-231](https://ssafy.atlassian.net/browse/S15P31F106-231)

## 구현 범위

`MemberDiaryCreationService.create`는 다이어리, OWNER 멤버십, 요청한 초기 페이지 전체를 하나의 Spring 트랜잭션으로 생성한다. 기존 비회원 생성 서비스와 HTTP 경로는 변경하지 않았다. 신규 DDL도 없다. 이 문서는 내부 연결 계약이며 공개 API 명세 확정본이 아니다.

1. `DiaryCreationIdentity`에서 신뢰할 수 있는 인증 사용자 ID를 받는다. 요청 본문의 소유자 ID는 받지 않는다.
2. 활성·미삭제 사용자 행을 잠그고 서버에 저장된 `profile_color`를 읽는다. PostgreSQL은 `FOR SHARE`로 탈퇴·프로필 변경과 경합을 조정한다.
3. 메타데이터와 초기 페이지 목록을 검증한다. 현재 기반 구현은 PRIVATE 생성만 허용한다.
4. 페이지 모듈의 `DiaryInitialPages.validateSelections`를 호출해 카탈로그의 코드·버전·활성 여부와 설정을 검증한다.
5. 서버 UUID와 시각으로 다이어리, 해당 사용자의 OWNER 멤버십, 초기 페이지를 차례로 저장한다. 멤버 색상은 사용자 프로필 색상을 사용한다.
6. 실제 저장된 활성 페이지 ID와 반환된 목록의 개수·중복·순서, 소유자 및 OWNER 멤버십 일치를 확인한다. 불일치 시 전체 롤백한다.

페이지 생성이나 멤버십 생성 도중 예외가 발생해도 세 종류의 행이 남지 않는다. 트랜잭션 프록시를 우회한 직접 호출도 쓰기 전에 거부한다. 초기 페이지가 78개인 경우에도 첫 페이지만 생성하는 대신 요청 전체를 저장한다.

## JDBC 초기 페이지 연결

`JdbcDiaryInitialPages`를 기본 페이지 어댑터로 연결했다. 구현 시작 당시 develop `24b0300`에 별도 서버 페이지 생성 모듈이 없어 기존 V1 테이블을 사용해 추가했다. 기존 테스트 전용 페이지 생성기는 제품 어댑터를 상속한 실패 주입용 래퍼로 바꿨다. 인증 통합 테스트도 제품 페이지 어댑터를 사용한다.

- `page_templates`의 코드·버전이 일치하는 활성 항목이 정확히 하나일 때만 생성한다. 없는 속지나 중복된 활성 항목은 400으로 거절한다. 카탈로그·페이지를 임의로 보충하지 않는다.
- PostgreSQL은 카탈로그 행을 `FOR SHARE`로 생성 완료까지 잠근다. 코드·버전 순으로 잠가 서로 다른 페이지 순서 요청에서도 잠금 순서를 맞춘다. 실제 페이지는 요청 순서대로 `sort_key=1..N`으로 생성한다. 같은 속지를 여러 번 선택해도 페이지 UUID는 각각 새로 만든다.
- 가로·세로 규격은 각 카탈로그의 `canvas_width`·`canvas_height`를 사용한다. 클라이언트 규격이 제공되면 일치해야 한다. 서버 카탈로그 규격·방향·기본 설정이 잘못되면 500으로 실패하고 롤백한다.
- 설정은 현재 프런트 생성 입력에 맞춘 **내부 허용 범위**로 `width`, `height`, `paperAppearance`, `blank`만 받는다. 색상은 `backgroundColor`·`layoutColor`의 6자리 HEX만 허용하고 대문자로 정규화한다. `blank`는 불리언이다. 색상별로 카탈로그 기본값 위에 요청값을 덮어쓰며 카탈로그 원본을 변경하지 않는다.
- JSON 객체만 받으며 중복 키·후행 JSON·알 수 없는 키·잘못된 타입을 거절한다. 설정 문자열 상한은 16,384자, JSON 중첩 상한은 16이다. 이는 내부 구현 제한이며 최종 공개 API 정책 확정본은 아니다. 날짜·스코어보드 등 추가 속지 전용 설정은 담당 계약에 맞춰 허용 범위를 확장해야 한다.
- PostgreSQL JSONB에는 JSON 객체 자체를 저장한다. H2에서는 같은 동작을 검증하도록 `FORMAT JSON`을 사용한다. 문자열 안에 JSON이 다시 들어가는 이중 인코딩을 하지 않는다.
- 기존 OWNER 멤버십과 소유자가 일치하는 새 다이어리에서만 초기 생성한다. 기존 페이지가 있으면 추가·덮어쓰기 용도로 사용하지 못한다. 별도 트랜잭션이나 외부 호출을 만들지 않는다.

후속 V7에서 날짜형·만년형·방향별 빈 속지 288개 등록을 추가하고 프런트 에셋 ID→서버 코드/버전 매핑을 구현했다. 자세한 내용은 [속지 카탈로그 서버 매핑](./속지%20카탈로그%20서버%20매핑.md)을 참고한다. V7 적용 전 DB에 카탈로그 데이터가 없으면 요청은 400이다. 빈 속지는 프런트가 방향별 `dio-blank-landscape`·`dio-blank-portrait` 코드로 명시한다.

## 연결 지점과 남은 작업

- `DiaryCreationIdentity`: `DiaryRequestIdentity`를 통해 실제 로그인 JWT·서버 세션 검증기에 연결했다. 요청 부재·미인증·만료·로그아웃은 401이다. [인증 연결](./회원%20다이어리%20인증%20연결.md)을 참고한다.
- `DiaryInitialPages`: 제품 `JdbcDiaryInitialPages`를 기본 연결했다. 페이지 담당의 모듈로 대체할 때도 동일 DB·트랜잭션 참여와 카탈로그 잠금을 유지해야 한다.
- `DiaryOwnerMembershipWriter`: 기본 JDBC 구현은 기존 `diary_members`에 OWNER를 저장한다. 공유 모듈로 대체할 때도 동일한 트랜잭션에 참여해야 한다.
- 페이지 검증·생성은 같은 DB와 호출자의 트랜잭션을 사용해야 한다. 원격 API나 `REQUIRES_NEW`를 사용하면 원자성이 깨진다. 카탈로그 검증부터 생성까지 필요한 잠금은 페이지 어댑터가 담당한다.
- 내부 선택 항목은 `templateCode`, `templateVersion`, JSON 설정이며, 페이지 크기는 실제 카탈로그에서 결정한다. HTTP DTO·오류 응답은 후속 회원 HTTP 경로에 연결했다. 최종 팀 계약은 별도 확인한다.
- 초기 페이지 수 제한은 임시로 512개이며 `dio.diary.initial-pages.max-count`로 변경할 수 있다(설정 허용 범위 1~4096). 최종 제품 제한을 확정한 정책은 아니다.
- HTTP 생성에는 후속 IdempotentDiaryCreationService와 V8 영수증을 연결해 사용자별 키·같은 요청 재사용을 구현했다. 공유 멤버 초대·북마크·마지막 열람 페이지 갱신은 포함하지 않는다.

따라서 231 전체 완료나 실기기 API 연동 완료로 처리하지 않는다. 후속으로 회원 HTTP 경로를 연결했다. 회원 기본 앱 전환은 후속으로 완료했다. 최종 팀 계약·공유 DB 적용·실기기 통합 검증은 남아 있다.

## 검증

JDBC 연결 후(2026-10-27) 전체 백엔드 **170개 통과**, 조건부 DB 테스트 42개 제외, 실패·오류 0개. 별도 PostgreSQL 17.11에서 **21개 통과**, 잔여 테스트 스키마 0개 및 임시 DB 종료 확인. `git diff --check` 통과. 다른 활성 세션은 Safari 펜 QA와 알림 OpenAPI 보강 중임을 확인하고 별도 작업 폴더의 페이지 모듈만 수정했다.

초기 트랜잭션 기반 단계(2026-10-27)의 실행 결과는 전체 백엔드 149개 통과, 별도 PostgreSQL 13개 통과였다. 아래 JDBC 연결 검증은 제품 페이지 어댑터로 확장했다.

- H2 계약 테스트 20개: 기존 13개에 버전·방향·중복 선택 순서, JSONB 객체 저장과 기본 설정 병합, 잘못된 설정·규격·카탈로그, 실제 두 번째 INSERT 제약조건 실패와 재시도, 페이지 모듈 직접 호출·중복 초기화 거부, 빈 카탈로그 거부를 추가했다.
- Spring 연결 테스트: 서비스 프록시와 인증 요청이 없는 경우의 거부 동작.
- `postgresMemberDiaryCreationTest`: 실제 Flyway V1~V6를 독립 스키마에 적용해 공통 20개 계약과 카탈로그 비활성화의 실제 잠금 경합 1개를 PostgreSQL 17에서 검증한다. `DB_URL`은 로컬 주소만 허용한다. 각 테스트 종료 시 생성한 스키마를 제거한다.

```powershell
.\gradlew.bat test --console=plain
# 임시 로컬 PostgreSQL의 DB_URL, POSTGRES_USER, POSTGRES_PASSWORD 설정 후
.\gradlew.bat postgresMemberDiaryCreationTest --console=plain
```

HTTP 후속: [회원 다이어리 HTTP](./회원%20다이어리%20HTTP.md)에 생성·상세·수정 요청/응답/오류와 공개 경로 우회 차단 범위를 정리했다.
