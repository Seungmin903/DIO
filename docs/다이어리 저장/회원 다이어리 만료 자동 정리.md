## 삭제 범위와 30일 계약

- 복원과 자동 정리는 `DiaryRetention.PERIOD`의 고정 30일을 공유한다. 보관 기간 설정 주입은 없다. 삭제 시각 + 정확히 30일부터 정리 대상이며, 서버 UTC 시각을 마이크로초 단위로 계산한다.
- `owner_user_id IS NOT NULL`이고 `deleted_at <= now - 30일`인 자료만 후보로 읽는다. 활성 다이어리·30일 직전·소유자 없는 자료는 제외한다. 중단/재시작 시 다시 안전하게 스캔한다.
- 내부 배치는 로그인 사용자를 가장하지 않는다. 계정이 비활성화됐거나 OWNER 멤버십이 탈퇴했어도 만료된 서버 자료는 정리한다. 후보 조회 뒤에는 생성 영수증 → 다이어리 → 하위 자료 잠금 순서를 유지하고, 잠금 후 소유자 존재·현재 삭제 시각을 재검증한다. 복원됐거나 새 삭제 시각으로 바뀐 자료는 건너뛴다.
- `DiaryPurgeGraph`는 수동/자동 삭제의 동일한 하위 참조 정리를 한 트랜잭션에서 수행한다. 페이지·요소·획·이력·초대·멤버십·다이어리 미디어/폰트 사용 연결을 제거하고 대상 알림은 행을 보존하되 대상 FK·payload를 비운다. 생성 키/요청 지문/완료 표식은 남기고 대상 FK·응답만 비운다. 외부 미디어·폰트 원본·AI 작업·다른 다이어리 자료·공용 속지는 보존한다.
- 수동 삭제는 기존 `diary_purge_receipts`와 삭제를 원자적으로 커밋하고 원래 OWNER의 같은 ID 재요청 204·완료 시각 불변을 유지한다. 자동 만료는 HTTP 수동 삭제 완료 요청을 생성하지 않는다. 자동 삭제가 완료된 자료의 복원/상세는 404이며 되살리지 않는다.
- 알 수 없는 FK·잠금 타임아웃·후반 오류는 항목 트랜잭션 전체를 롤백한다. 이미 성공한 다른 항목은 유지하고 실패 항목은 다음 순환에서 다시 시도한다. 오류 로그에는 예외 종류와 집계 수만 남기고 SQL·개인 자료를 출력하지 않는다.

## 기본 비활성 및 운영 설정

`dio.diary.expiry-cleanup.enabled`가 없거나 false이면 엔진·스케줄러를 생성하지 않는다. 이 변경에서 운영 설정을 true로 바꾸지 않는다. 미사용 batch 설정이 잘못돼 있어도 비활성 앱 기동을 막지 않는다.

| 설정 | 기본값·범위 |
|---|---|
| `dio.diary.expiry-cleanup.enabled` | false, 명시적 true에서만 실행 |
| `dio.diary.expiry-cleanup.batch-size` | 20, 1~500 |
| `dio.diary.expiry-cleanup.lock-timeout-ms` | 1000, 1~5000 |
| `dio.diary.expiry-cleanup.delay-ms` | 60000 |
| `dio.diary.expiry-cleanup.initial-delay-ms` | 300000 |

삭제 시각/UUID 키셋으로 배치 크기만큼 선택한다. 실패를 포함한 마지막 키 다음으로 진행해 오래된 오류 항목 하나가 뒤 자료를 굶기지 않게 하며, 끝에 도달하면 처음부터 다시 조회한다. 프로세스 안에서는 run을 직렬화하고, 독립 작업자끼리는 DB 잠금 후 재검증으로 같은 그래프를 두 번 삭제하지 않는다. 항목별 새 트랜잭션은 15초 제한을 가진다.

운영 활성화는 별도 판단이다. 백업·복구 절차, 보관 계약, 실제 데이터 규모와 모니터링을 확인한 뒤 수행한다. 물리 DB 삭제 후 API 복원은 불가능하며 원본 파일 GC는 이 작업 범위가 아니다.

## migration·롤백

V14는 `(deleted_at, diary_id)`의 부분 인덱스 `diaries_expiry_cleanup_idx`만 추가한다. 기존 행·스키마 이력·기존 migration을 재작성하지 않는다. 기존 완료 기록을 포함한 V13→V14 행 스냅샷 보존, validate 및 재실행 추가 적용 0을 테스트한다. 기존 회원 migration 업그레이드 테스트도 V14 이력을 포함한다.

실행 중단은 `enabled=false`로 한 뒤 재시작한다. 애플리케이션 revert로 이미 삭제한 자료가 복구되지는 않는다. V14 파일을 지우거나 적용 이력을 수정하지 않으며, 필요 없는 인덱스 제거는 별도 후속 migration으로 다룬다.

## 검증

전용 폐기용 PostgreSQL의 루프백 `dio_trash_qa`와 임의 스키마만 사용한다. 개발/운영/공유 DB에는 실행하지 않는다.

```sh
cd backend
./gradlew test --tests 'com.f106.DIO.diary.expiry.*' --tests '*MemberDiaryPurgeHttpTests' --tests '*MemberDiaryTrashHttpTests' --tests '*MemberDiaryTrashTests'
# 명시적인 폐기용 DB_URL/POSTGRES_USER/POSTGRES_PASSWORD 및 DIO_LIST_QUERY_PG=true 필요
./gradlew postgresDiaryPurgeTest postgresDiaryTrashTest
./gradlew postgresMemberDiaryCreationTest --tests '*MemberMigrationUpgradePostgresTests'
```

Windows에서는 gradlew.bat을 사용한다. 기존 `postgresDiaryPurgeTest`의 `purge.*` 필터와 CI 실행·JUnit 수집 경로가 신규 만료·migration 테스트를 함께 실행하므로 CI 태스크를 중복 추가하지 않는다. 스케줄러 기본 비활성/명시적 활성·실패 격리, 정확한 만료 경계, 복원 우선/배치 우선, 재휴지통 삭제 시각 변경, 늦은 FK 오류 전체 롤백, 잠금 타임아웃 후 재시도, 다중 작업자를 검증한다. 최종 결과와 원본 보존 감사는 후속 MR 및 워크스페이스 `tmp/diary-expiry-followup/`에 기록한다.

실기기·운영 배치 활성화·운영 부하·백업 복구 훈련·외부 미디어 GC·배포는 검증 범위 밖이다. 이 문서는 배포나 운영 자동 정리 활성화 승인을 뜻하지 않는다.

로컬 최종 결과: H2 28개, PostgreSQL 회원 migration 업그레이드 1개·만료/영구 삭제 21개·휴지통 21개(합계 43개), 모두 통과·실패/오류/제외 0. V13→V14의 완료 기록을 포함한 전체 fixture 행 보존과 기존 수동 재시도·복원 계약이 유지되는지 검증했다. 사용한 임시 서버는 종료했다. 원격 CI/자동 리뷰 결과는 후속 MR에서 별도로 기록한다.
