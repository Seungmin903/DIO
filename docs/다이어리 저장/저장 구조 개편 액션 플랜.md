# 다이어리 저장 구조 개편 액션 플랜 (2026-11-04)

## 1. 왜 바꾸나 (실측)
| 한계 | 값 | 증상 |
|---|---|---|
| 한 행 읽기 | 약 4MB (3.85MB 정상 · 4.24MB 실패) | 다이어리가 목록에서 사라진 것처럼 보임 (`SQLiteBlobTooBigException`) |
| 전체 쓰기 | DB 합계 6MB (AsyncStorage 기본 `AsyncStorage_db_size`) | `SQLITE_FULL` → "⚠ 저장 안 됨" |
| 필기 점 | 연필 158B · 볼펜 계열 62~68B (점당) | 문서 용량의 91%가 점 |
| 사진·GIF 객체 | 약 10KB (그중 `poster` base64 9.5KB) | 객체 수에 비례해 증가 |

현재 구조: 다이어리 1권 = AsyncStorage 한 행(`dio:editor:doc:v4:<id>`)에 문서 전체 JSON. 한 장만 고쳐도 전체를 `JSON.stringify` 후 다시 쓴다.
→ 크기가 곧 한계이고, 크기에 비례해 저장 때 JS 멈춤도 커진다.

## 2. 외부 근거
| 근거 | 내용 | 출처 신뢰도 |
|---|---|---|
| Figma | 예전엔 파일 전체를 받아 메모리에 올림 → 선택한 페이지만 먼저 로드, 나머지는 필요할 때. 느린 5% 로드 33% 단축, 메모리 감소. 변경은 부분(subtree) 단위로 주고받음 | 공식 엔지니어링 블로그 (높음) |
| Android CursorWindow | 행 하나가 창(기본 2MB, 기기 따라 ~4MB)에 들어가야 읽힘. 해법: 큰 값은 파일, DB엔 경로 / 여러 행으로 분할 | 커뮤니티·라이브러리 PR (중간) |
| PencilKit | 점마다 time offset·굵기·필압을 저장하고 내부 압축은 비공개 | Apple 문서 (높음, 압축 방식은 알 수 없음) |
| MMKV 벤치 | 작은 값 반복 읽기에서 AsyncStorage보다 수십 배 빠름. **큰 JSON 한 키는 안티패턴** | 라이브러리 README·가이드 (중간, 오래된 수치) |
| SQLite 쓰기 | 트랜잭션으로 묶으면 수십 배 빠름, 인덱스는 삽입을 느리게 함, WAL은 동시성에 유리 | 일반 가이드 (중간) |
| expo-file-system (SDK 58) | `File.write/text` 제공, **원자적 쓰기 보장은 문서에 없음** → 임시 파일에 쓰고 `move`로 교체해야 함. `writeAsStringAsync`는 deprecated | Expo 공식 문서 (높음) |
| expo-sqlite | `withTransactionAsync`, 준비된 문장, WAL, Uint8Array(blob). 네이티브 모듈이라 **현재 프로젝트에 미설치 → 네이티브 재빌드 필요** | Expo 공식 문서 (높음) |
| GoodNotes · Notability | 내부 저장 구조는 공개 자료로 확인 못 함 | — (근거로 쓰지 않음) |

한계: Expo SDK 58에서 expo-sqlite · 파일 · AsyncStorage를 같은 조건으로 비교한 공개 벤치는 찾지 못했다. **저장소 선택은 우리 데이터로 직접 측정해서 결정한다 (단계 0).**

## 3. 설계 원칙
1. **한 번에 다루는 단위를 페이지로 줄인다** (읽기도 쓰기도).
2. **기존 사용자 데이터는 절대 잃지 않는다**: 옛 행은 새 구조에 저장·검증이 끝난 뒤에도 일정 기간 남긴다.
3. **저장소 접근을 한 계층(adapter)으로 모은다.** 지금 문서 키를 직접 읽는 곳은 아래 7곳이라 이 계층을 먼저 만들면 교체 범위가 작다.
   - `editorDocs.js` · `useDiaries.js`(고아 복구 `multiGet`) · `useGuestDiaryImport.js` · `useLibraryMetadata.js` · `OpenBookShelf.js` · `mediaLibraryRuntime.js` · `legacyMockCleanup.js`
4. 백엔드는 건드리지 않는다. 협업 쪽 변경이 필요하면 요청서로 넘긴다.

## 4. 액션 플랜
### 단계 0 — 즉시 완충 (반나절, 위험 낮음)
- `AsyncStorage_db_size_in_MB` 상향 (`frontend/android`는 gitignore → Expo config plugin으로 `gradle.properties`에 주입).
- 저장 실패 문구를 "용량 부족"과 "기타 오류"로 구분.
- 읽기 실패 시 "다이어리 없음"으로 착각하지 않도록 이미 막혀 있는지 재확인(`loadEditorDoc`는 reject 처리됨).
- **검증**: 태블릿에서 6MB 초과 문서 저장 성공 · 4MB 초과 행은 여전히 열기 실패(=단계 2가 필요한 이유) 재현.
- 이 단계 후에도 읽기 4MB 벽은 남는다. 임시 방편임을 명시.

### 단계 1 — 필기 점 압축 (1~2일, 호환 유지)
- 저장 계층에서만 변환: 좌표·압력 반올림(예: 좌표 0.1px, 압력 0.01), `time`은 델타, 렌더에 안 쓰는 필드 제거 후보 검토.
- **선행 조사**: 점 필드별 실제 사용처를 확인했다. `tiltX/tiltY/inkDistance/force/speed/pressure/time` 모두 연필·펜촉·지우개·내보내기·Skia 래스터가 읽는다. **"안 쓰는 필드"는 없고 반올림·델타 인코딩만 안전하다.** 필드 제거는 렌더 비교 테스트 후에만.
- 저장 형식 버전(v4→v5) 표기, 읽을 때 v4도 계속 인식.
- **검증**: 같은 문서의 전/후 렌더 이미지 픽셀 비교, 크기 감소율 측정(목표 3배 이상), 내보내기 PDF 비교.
- 실측(2026-11-04, 2.26MB 문서): 반올림만 1.29배(1.75MB), 반올림 + 열 분리 + 델타 3.48배(0.65MB). 처음 추정한 3~5배는 반올림만으로는 나오지 않으므로 열 분리 + 델타까지 해야 한다. 렌더 동일성은 7페이지 비교로 확인했다(다른 픽셀 0.015~0.60%, 16단계 이상 차이는 페이지당 최대 13픽셀, SM-X800). 읽기 벽은 구조 문제라 단계 2가 필요.

### 단계 2 — 페이지 단위 저장 (핵심, 3~5일)
선택지(단계 0.5에서 측정 후 확정):
| 안 | 장점 | 단점 |
|---|---|---|
| A. 기존 AsyncStorage에 키만 분리 (`doc:<id>:meta`, `doc:<id>:page:<pid>`) | 신규 네이티브 모듈 없음, 앱 재빌드 불필요, 마이그레이션 단순 | 합계 DB 6MB 벽(단계 0으로 상향), 행당 4MB 벽은 해소 |
| B. `expo-file-system`으로 페이지별 JSON 파일 | 용량 사실상 기기 저장공간, 이미 설치됨 | 원자적 쓰기 직접 구현(임시 파일→move), 파일 수 관리, 메타 인덱스 필요 |
| C. `expo-sqlite` (페이지 행) | 트랜잭션·인덱스, 부분 갱신, 쿼리 | 신규 네이티브 모듈(재빌드), 데이터 이중화 위험, 스키마 마이그레이션 |
- C는 비교에서 제외했다(사용자 결정, 2026-11-04).
- **A·B 실측 (SM-X510, 앱 안 측정, 각 3회 중앙값, 전체 쓰기·전체 읽기는 1회. 괄호는 JS 최대 멈춤, 단위 ms)**

| 문서 | 안 | 첫 화면(메타 + 1장) | 1장 저장 | 전체 읽기 | 전체 쓰기(이전 1회) |
|---|---|---|---|---|---|
| 4MB (45장) | A | 33 (29) | 24 (20) | 71 (36) | 147 (42) |
| 4MB (45장) | B | 70 (33) | 47 (28) | 229 (72) | 985 (31) |
| 30MB (347장) | A | 28 (24) | 22 (18) | 543 (176) | 492 (148) |
| 30MB (347장) | B | 43 (27) | 20 (17) | 1760 (32) | 4738 (33) |

- 같은 측정에서 현재 방식(한 행)은 4.24MB부터 읽기 실패, 30MB 저장은 stringify 329ms + 쓰기 1952ms였다.
- **결정: B (사용자 확정, 2026-11-04).** 평소 작업은 사실상 같고, 대량 읽기·쓰기는 A가 3~10배 빠르지만 B는 문서가 커져도 멈춤이 약 30ms로 일정했다. A는 행당 약 4MB(한 페이지 한계)와 DB 총량 설정이 남고, B는 기기 저장 공간만 남는다. 단 B는 전체 읽기가 느리므로 페이지 지연 로드가 전제이고, 원자성은 임시 파일 → move로 직접 보장해야 한다. iOS와 웹은 미측정이다.
- 구조: `meta`(페이지 순서·제목·표지·updatedAt) + 페이지 본문. 열 때 meta와 현재 페이지(+이웃 1~2장)만 읽고, 나머지는 필요할 때·유휴 시간에 읽음.
- 저장: 변경된 페이지만 쓰기(편집 reducer가 어느 페이지를 바꿨는지 알고 있으므로 dirty set 추적), meta는 순서·제목이 바뀔 때만.
- 쓰기 안전: 새 내용을 임시 키/파일에 쓴 뒤 교체, 실패 시 이전 버전 유지.
- **마이그레이션**: 첫 열기 때 옛 행을 읽어 페이지로 분할 → 새 구조 저장 → 읽어서 다시 비교 검증 → 성공 표시 후에만 옛 행 삭제(최소 한 버전 뒤). 실패하면 옛 행 계속 사용.
- **검증**: 25페이지·3.85MB 테스트 문서와 5MB 초과 문서로 열기 시간·저장 시간·JS 멈춤 측정(전/후), 강제 종료(저장 중 앱 kill) 시 데이터 보존, 마이그레이션 중 종료 재시도.

### 단계 3 — 부가 부하 줄이기 (각 0.5~1일)
- `poster` 분리는 하지 않는다(사용자 결정, 2026-11-04). 원본을 잃었을 때의 예비본 역할을 하고, 페이지별 저장에서는 해당 페이지를 읽을 때만 함께 읽어 부담이 작다.
- 협업: 페이지 전체 재요청 + 전체 JSON 비교 → 변경 객체 단위 비교(백엔드 요청서 필요 여부 확인).
- 썸네일/페이지 목록: 100~500장에서 측정 후 가상화·지연 생성.

## 5. 이 순서인 이유
- 단계 0은 코드 한 줄 수준으로 당장의 "저장 안 됨" 위험을 줄인다.
- 단계 1은 구조 변경 없이 용량을 줄여 단계 2 전까지 버틸 시간을 번다.
- 단계 2가 근본 해결이고 가장 위험하다. 그래서 0·1로 시간을 벌고 측정 후 진행한다.

## 6. 위험과 대응
| 위험 | 대응 |
|---|---|
| 마이그레이션 중 데이터 손실 | 검증 후 삭제, 옛 행 유지 기간, 실패 시 옛 구조로 동작 |
| 저장 중 종료로 반쯤 쓴 상태 | 임시→교체, 페이지 단위 원자성, meta를 마지막에 갱신 |
| 협업 중 페이지 충돌 | 서버 페이지 단위 동기화는 유지, 로컬 저장은 서버 응답과 독립 |
| 반올림으로 필기 모양 변화 | 픽셀 비교 테스트, 반올림 단위 보수적으로 시작 |
| iOS 동작 | 파일·AsyncStorage 모두 크로스플랫폼. iOS 실기기 확인은 별도(현재 대체 불가) |

## 7-1. 사용량 기준 (2026-11-04 조사)
다이어리 한 권당 페이지 · 글자 · 사진 수를 정리한 공개 업계 자료는 찾지 못했다. 아래 시나리오는 **통계가 아니라 가정**이며, 요소별 크기(실측)와 글자당 점 30개(추정)로 계산했다.

| 타이핑 위주, 매일 | 365장 · 500자 입력 · 사진 1 | 약 4.5MB | 약 4.5MB |

## 7-3. 저장 형식 분리 · 게스트 점진 로드 (2026-11-04 구현)
- 형식: 목차에 페이지 정보, 페이지 파일에 objects. 안 읽은 페이지(`unloaded`)는 정보만 저장하고, 파일을 찾지 못하면 저장 전체를 거부한다.
- 대상: 2MB(압축 후 파일 크기)를 넘는 게스트 문서. 회원 문서는 협업 때문에 전체를 읽는다.
- 읽는 동안 복제 · 삭제 · 초기화 · 내보내기를 막고, 안 읽은 페이지에서는 요소 편집을 막는다.
- 실측(SM-X800): 600MB 문서가 탭 후 약 1초에 현재 페이지 표시(이전 38초 이상), 나머지는 약 75초. 필기 프레임 90퍼센타일은 읽는 중 77~105ms에서 9ms로 줄었다(100MB 문서, adb 입력). 읽어 온 내용을 합쳐도 저장 예약을 미루지 않아, 필기 2~3초 뒤 강제 종료해도 저장된다.
- 남은 과제: 메모리 상한(전체를 다 읽으면 600MB 문서에서 약 1.1GB).
- 되돌리기 기록: 80회에서 20회로 줄이고 편집기를 나가면 비운다(사용자 결정, 2026-11-04). 기록이 페이지 내용을 붙들어 큰 문서의 메모리를 늘리기 때문이다. 절감량은 따로 재지 않았다.

## 7-4. MR 리뷰 반영 (2026-11-04)
- 참조 검사: 문서 전체를 문자열로 되살리지 않고 목차와 페이지 파일을 하나씩 훑는다(`scanText`, `storedScan.js`). 훑는 도중 그 문서가 저장되면 실패로 보고 아무것도 지우지 않는다. 고아 복구는 목차만 읽는다.
- 목차를 읽지 못한 문서: 참조 검사 목록에서 빼지 않는다. 그 문서를 읽을 때 실패해 사진과 PDF 원본을 지우지 않는다.
- 첫 저장 중 종료: 쓰다 만 `manifest.tmp`만 남으면 문서가 없는 것으로 보고 옛 행과 다시 옮기기로 돌아간다.
- 옮기기 확인: 옛 행과 사본을 값까지 비교한다. 좌표와 필압만 저장 눈금의 오차를 허용한다. 눈금에 맞지 않는 센서 값이 있는 획은 압축하지 않아 손실이 없다.
- 점진 로드: 돌려받지 못한 페이지가 있으면 "다 읽음"으로 넘기지 않고 실패로 알린다. 읽기 실패는 한 번 다시 시도한다.
- 남겨 둔 것: 홈 펼침면을 읽을 때 목차 요약과 페이지 읽기 사이에 저장이 끼면 다른 페이지가 잠시 보일 수 있다. 표시 전용이고 데이터 손실은 없다.

## 8. 바로 할 일 (제안 순서)
1. 단계 0 적용 + 태블릿 재현 검증
2. 저장 계층(adapter) 분리 리팩터 (동작 변화 없이, 테스트 통과)
3. A·B 두 안을 같은 문서로 측정해 확정
4. 단계 1 → 단계 2 순서로 각각 별도 Jira·MR
