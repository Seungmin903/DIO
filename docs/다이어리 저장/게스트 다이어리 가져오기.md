# 게스트 다이어리 가져오기 (S15P31F106-423)

로그인 전(게스트)에 이 기기에서 만든 다이어리를 로그인한 회원의 서버 보관함으로 복사한다. 이번 범위는 **프런트만**, 지금 있는 서버 API로 옮길 수 있는 만큼이다. 서버 변경이 필요한 항목은 아래 "빠지는 항목"과 "백엔드 후속"에 정리했다.

## 흐름

1. 로그인해 회원 보관함이 열리고 앱 잠금이 풀리면, 이 계정으로 아직 가져오지 않은 게스트 다이어리(휴지통 제외)가 있는지 본다(`GuestImportHost`).
2. 있으면 묻는다: **가져오기 / 나중에 / 가져오지 않기**. "가져오지 않기"는 계정별로 기록해 다시 묻지 않는다. 끝나지 않은 가져오기가 있으면 그 다이어리만 다시 묻는다.
3. 다이어리마다 순서대로 보낸다(`createGuestDiaryImporter`).
   1. 계획 만들기: 페이지 → 서버 속지(카탈로그 code·version), 요소 → 새 UUID와 서버 요소 형식. 계획은 기기에 저장해 다시 보낼 때 그대로 쓴다.
   2. `POST /member/diaries`(Idempotency-Key): 제목·표지 색·무늬(`coverStyle`)·초기 페이지(최대 512쪽).
   3. `PATCH /pages/{id}`: 페이지 크기, 이름, 격자, 속지 글꼴(서버의 templateConfig에 `paperAppearance.font`만 더해 통째로 넣는다).
   4. 요소마다 사진·스티커·테이프·PDF 원본을 `POST /media`로 올리고 서버 id로 바꾼다(`canvasMedia.prepare`, 편집기와 같은 기록 자리). 서버가 바쁘면(503) 잠시 뒤 다시 보낸다.
   5. `POST /pages/{id}/canvas-operations`: 100개·3MiB 묶음. 묶음이 거절되면(400/413/422) 하나씩 다시 보내 거절된 요소만 빠진다.
   6. 게스트 즐겨찾기는 `PATCH /diaries/{id}/membership`.
   7. 이 기기의 회원 문서 캐시를 `GET /pages/{id}`로 채운다(직접 만든 회원 다이어리처럼 바로 열린다. 실패해도 가져오기는 끝난 것으로 본다).
4. 진행률을 보여 주고, 끝나면 가져온 수·실패와 빠진 항목을 보여 준다. 실패한 다이어리는 **다시 시도**로 이어서 보낸다.
5. 성공한 다이어리만 `dio:diary:guest-imports:v1`에 "어느 계정의 어느 다이어리로 가져왔는지"를 기록한다. **게스트 원본은 지우지 않는다.**

## 중복 방지

- 다이어리 생성: 처음 정한 Idempotency-Key를 기기 기록(`dio:member:v1:<계정>:guest-import:v1`)에 두고 다시 보낼 때 그대로 쓴다. 서버는 24시간 동안 처음 결과를 돌려준다.
- 생성 응답을 받지 못한 채 키 보관 기간이 지나 `409 IDEMPOTENCY_KEY_EXPIRED`가 오면 연결 재시도 대신 회원 보관함에서 생성 여부를 확인하라는 전용 안내를 표시한다. 자동으로 새 키를 만들지 않는다. 서버에 이미 다이어리가 생성됐을 수 있어 중복 생성을 막기 위해 계획과 키를 보존한다.
- **만료 복구 한계:** 키 만료 후에는 같은 요청의 재시도만으로 가져오기를 완료할 수 없으며 미완료 안내가 다시 나타날 수 있다. 먼저 회원 보관함에서 생성 여부와 내용을 확인해야 한다. 앱에는 확인 후 만료 계획을 재설정하는 기능이 없으므로, 새 키로 재생성하는 복구 경로는 후속 범위다. 게스트 원본은 유지된다.
- 요소: 요소 id·clientOperationId를 계획에 저장하고, 업로드로 바꾼 요청도 저장한 뒤 보낸다. 다시 보내면 서버가 처음 결과를 돌려준다.
- 사진: 올린 결과(로컬 id → 서버 id)를 기기에 기록해 다시 올리지 않는다. `/media`에는 멱등 키가 없어 업로드 응답이 사라진 경우에만 같은 사진이 한 번 더 올라갈 수 있다.
- 로그인이 끝나거나 계정이 바뀌면(401) 남은 다이어리를 보내지 않는다. 다음 로그인 때 이어서 묻는다.

## 진행 기록 저장

- 계정별 기존 `guest-import:v1` 키는 작은 `format: 2` 헤드로 사용한다. 다이어리 메타데이터와 전송 묶음 본문을 분리하고, 인덱스·큰 본문도 64K UTF-16 코드 단위 이하 조각으로 나눈다. 서로게이트 쌍을 보존하며 조각의 UTF-8 크기는 최대 192KiB다.
- 준비된 묶음은 `request`만 남겨 원본 `creates`와 같은 본문을 중복 저장하지 않는다. 완료된 묶음은 식별자·완료 기록만 유지하고 큰 본문은 해제한다. 변경되지 않은 묶음·다른 다이어리 본문은 다시 쓰지 않는다.
- 새 조각과 인덱스 저장을 마친 뒤 마지막에 헤드를 교체한다. 그 전에는 이전 체크포인트를 유지하며, 저장 실패 시 요청을 먼저 전송하지 않는다. 같은 계정의 실행기 사이에서도 읽기·쓰기·정리를 직렬화한다.
- 기존 `format: 1` 단일 키 기록은 읽을 수 있으면 요청 ID·준비된 본문을 유지해 다음 저장 때 이전한다. 누락·손상된 조각이나 이미 플랫폼 읽기 한도를 넘은 기존 행을 자동 초기화하지 않는다.
- 현재 인덱스가 참조하지 않는 이전 조각은 저장 후 정리한다. 정리 실패는 확정된 체크포인트를 취소하지 않으며, 이후 실행의 첫 저장에서 고아 조각을 다시 회수한다.
- 조각 저장은 행 크기 문제를 줄이지만 기기 전체 저장 용량·AsyncStorage 총량 제한을 없애지는 않는다. 공간이 부족하면 실패로 남기고 게스트 원본을 유지한다. 큰 기록 테스트는 행 읽기·쓰기 상한을 256KiB로 제한한 저장소 모형에서 검증하며 실제 기기 저장 용량과는 구분한다.

## 옮기기 흐름

- 로그인 뒤 한 번 묻는다: `나중에` · `N권 옮기기`. 항목을 고르지 않고 후보 전부를 옮긴다.
- `나중에`를 고른 계정에는 자동으로 다시 묻지 않는다(새로 만든 게스트 다이어리도). 보관함의 `이 기기의 다이어리 N권 옮기기`로 언제든 시작한다. 끝나지 않은 옮기기만 다시 묻는다.
- 다 옮긴 다이어리의 원본은 기기에서 지운다(휴지통 영구 삭제와 같은 경로, 다른 곳에서 쓰는 사진 파일은 남는다). 지우기 전에 앱이 꺼지면 다음 로그인 때 마저 지운다.
- 아래 표의 내용 항목이 빠진 다이어리는 원본을 남기고 결과 창에 알린다. 내 손글씨 글꼴만 빠진 경우는 지운다(글자는 옮겨졌고 글꼴 파일은 기기에 남는다).
- 끊긴 옮기기를 이어서 끝낼 때 계획을 만든 뒤 게스트 내용이 바뀌었으면 원본을 남긴다(계획 뒤에 쓴 내용은 서버에 없다).
- 예전 앱에서 복사만 한 다이어리는 지우지 않는다.

## 기기에만 잇는 값

서버가 받지 않는 값은 `dio:member:v1:<계정>:local-meta`에 서버 다이어리 id별로 남겨 회원 목록에 합친다. 이후 사용자가 고친 값이 우선이다.

| 값 | 쓰는 곳 | 다른 기기 |
|---|---|---|
| 표지 꾸밈(`cover`) | 표지 그리기 | 안 보임. 백엔드: 표지 설정 JSON 칸 |
| 방향(`pageSize`) | 표지 · 책장 방향 | 서버 페이지 크기(`GET /diaries/{id}/pages`)로 한 번 읽어 채운다 |
| 처음 만든 날짜(`originalCreatedAt`) | 최근 생성순 정렬(화면에서 다시 정렬) | 옮긴 시각 기준. 백엔드: createdAt 보존 옵션 |

## 빠지는 항목 (결과 창에 "옮기지 못한 항목"으로 보여 준다)

| 항목 | 이유 | 해결 |
|---|---|---|
| 날짜 속지의 날짜 글자 | 날짜 속지(`dated-…`)는 서버 카탈로그에 없어 같은 양식의 만년형 속지로 옮김 | 백엔드: 날짜 속지 카탈로그 또는 templateConfig 확장 + 프런트 해석 |
| 서버에 없는 속지 그림 | 카탈로그에 없는 속지·버전은 같은 방향의 빈 속지로 옮김 | 백엔드: 옛 버전 수용 또는 대응표 |
| 15MiB 넘는 GIF, 기기에서 지운 사진 | GIF 업로드 상한 15MiB(정지 이미지는 5MiB, JPEG로 낮춰 올림) | 상한 상향은 반영됨, 그 이상은 서버 한도 |
| 서버에 저장할 수 없는 요소 | 서버 요소 종류는 글·사진·스티커·테이프·펜·도형뿐 | — |
| 내 손글씨 글꼴 | 글 요소의 `font: 'personal-…'`는 그대로 옮기지만 서버 폰트와 잇는 규칙이 없어 다른 기기에서는 기본 글꼴로 보임 | 프런트·백엔드: 손글씨 폰트 업로드·`POST /diaries/{id}/fonts`와 id 대응 |
| 512쪽을 넘는 페이지 | 초기 페이지 상한 | 프런트 후속: 만든 뒤 `POST /diaries/{id}/pages`로 이어 붙이기 |
| 꾸미기 공방 자료(스티커 폴더·나의 표지·나의 속지·색 프리셋) | 저장 API 없음. 기기에 그대로 남음 | 백엔드: 공방 자료 API |

긴 펜 획은 서버 요소 한도(128KiB)를 넘으면 같은 좌표계를 둔 여러 획으로 나눠 보낸다(이음매 점을 겹친다). 획의 재질 무늬(renderVersion 3)는 이음매에서 조금 달라질 수 있다.

또 서버 쪽 한계로 가져오기 요소도 실행 취소 기록에 남고, 올린 사진은 `/media` 목록에 보인다.

## 플랫폼별 확인 사항

가져온 회원 다이어리는 사진 표시가 끝난 뒤 펜·텍스트·이미지가 유지되는지와 앱 재접속 후 복원을 확인한다. 웹 배포는 페이지 목록·미디어 파일 조회의 CORS와 인증도 별도로 확인한다.

## 실행·세션 보호

가져오기는 기존 서버 API를 사용하는 프런트 기능이며, 게스트 원본과 계정별 진행 기록을 분리한다.

- 가져오기 연속 클릭과 실행기 중복 호출을 한 번의 실행으로 묶는다.
- 완료 기록 저장 후 진행 기록 정리에 실패했어도, 재시도는 완료 기록을 먼저 확인해 다이어리를 다시 만들지 않는다.
- 세션별 GuestImportHost를 분리하고, 로그아웃·계정 전환·화면 종료 후 늦은 진행/완료 응답을 화면에 반영하지 않는다. 생성 응답을 받은 뒤 세션이 바뀌면 생성 키/서버 ID 진행 기록을 보존하고 추가 전송을 중단한다.
- 앱 잠금 중에는 가져오기 창을 숨긴다. 이미 동의해 실행 중인 같은 세션의 가져오기는 유지하며 잠금을 풀면 결과를 표시한다. 나중에/닫기를 고른 뒤 같은 로그인에서 잠금 해제만으로 다시 묻지 않는다.
- 손상된 JSON이나 페이지 없는 저장 문서를 빈 다이어리로 바꾸어 전송하지 않는다. 저장 문서 자체가 없는, 아직 열지 않은 다이어리는 기존 기본 문서 규칙을 유지한다. 게스트 원본은 삭제하거나 덮어쓰지 않는다.
- 즐겨찾기 및 회원 문서 캐시 조회의 인증 실패를 완료로 처리하지 않는다. 재로그인 후 같은 생성 키와 요청으로 이어서 보낸다.
- 긴 펜 획을 분할할 때 마지막 점이 한 개 남는 길이도 끝점과 이음매를 보존한다.

## 검증 방법

`pnpm test:guest-import`로 서비스·훅·네이티브 multipart 회귀 테스트를 실행한다. 회원 보관함 회귀와 대상 플랫폼 번들 생성도 확인하며, 자동 테스트·번들 생성과 실제 기기 검증 결과는 MR에 구분해 기록한다.

### Android Expo Go 이미지 업로드 실패 보완

- 네이티브 사진·PDF multipart는 공용 `filePart`를 사용한다. React Native용 uri·type·name과 Expo용 bytes()를 함께 제공하며, bytes()는 `expo-file-system.File`로 파일을 읽는다. uri만 있는 객체는 Expo multipart 인코더와 호환되지 않는다.
- 미전송 묶음의 이미지와 일반 요소를 분리한다. 사진 네트워크 오류가 나도 다른 페이지의 펜·텍스트 전송은 계속한다.
- 이미지 실패는 가져오기 완료로 기록하지 않는다. 기존 재시도에서 같은 서버 다이어리·요소 ID로 남은 전송을 이어가며 게스트 원본은 유지한다.
- 이미 전송 준비가 끝나 저장된 요청의 clientOperationId·본문은 변경하지 않는다.
- 회귀 테스트는 Expo multipart 실제 직렬화, 이미지 오류 후 펜·텍스트 보존, 재시도 시 중복 방지를 검증한다. 실기기 최종 확인은 별도로 필요하다.


### 재시도 누락 집계·생성 입력 거절 보완

- 영구 오류 사진의 누락 목록은 묶음 준비가 모두 끝난 뒤 전송 요청과 함께 저장한다. 뒤 사진에서 네트워크 오류가 발생하면 임시 누락 집계는 버려 재시도마다 개수가 늘어나지 않는다.
- 빈 제목은 서버 전송 계획에서 `제목 없음`으로 대체하며 게스트 원본 제목은 수정하지 않는다.
- 생성 단계의 400/413/415/422 입력 거절은 해당 실행을 실패로 반환하고 미완료 계획을 정리한다. 다음 수동 시도는 원본으로 새 계획을 만든다. 가져오기 완료 기록으로 취급하지 않는다.
- 멱등 키 관련 오류는 위 정리 대상에서 제외한다. 네트워크/응답 유실, 인증·권한, 408/409/429/5xx도 계획과 요청 ID를 보존한다. 결과가 불명확한 요청을 새 키로 자동 재생성하지 않는다.
- 생성 이후 페이지·요소 단계의 오류는 기존 이어받기 기록을 유지한다. UI·API·DB 변경은 없다.


### 사진 업로드 오류 구분

파일 형식·크기 등 입력 거절(400/413/415/422)과 상태 코드 없는 명시적 기기 파일 오류만 누락 항목으로 처리한다. 서버의 403/404/409, 인증·요청 제한·네트워크·5xx 오류는 누락 완료로 확정하지 않고 미완료 기록을 유지해 다시 시도한다. 서버 404와 기기 원본이 없는 `MEDIA_NOT_FOUND` 오류를 구분한다.


### 가져오기 대상 조회 실패

게스트 목록 JSON 손상·배열 형식 오류, 후보 장부 또는 미완료 인덱스 읽기 실패는 기존 결과창에 조회 오류를 안내한다. 게스트 목록 키 없음과 정상 빈 배열만 후보 없음으로 처리하고, 손상된 목록을 빈 목록으로 숨기거나 덮어쓰지 않는다. 다이어리 가져오기 실패 건수로 오인하지 않도록 조회 실패 문구를 사용하며 기존 버튼·스타일·배치는 유지한다. 실패도 해당 세션에서 확인한 것으로 표시해 잠금 해제·재렌더마다 같은 조회를 반복하지 않는다.

기존 `다시 시도`는 후보·진행 인덱스를 다시 읽는다. 조회가 복구되면 후보 안내로 돌아가며, 실제 가져오기는 사용자가 선택한 뒤 실행한다. 기록·게스트 원본을 자동 초기화하지 않고, 화면 종료·세션 변경 뒤 도착한 조회 결과는 반영하지 않는다.


### 가져오지 않기 선택 저장

선택 저장에 실패하면 기존 공용 notify로 저장 실패와 다음 로그인 시 안내가 다시 표시될 수 있음을 알린다. 게스트 원본·기존 진행 기록을 초기화하지 않는다. 저장 중 중복 선택은 한 번만 처리하며, 화면 종료·세션 변경 후의 실패 알림은 다른 계정에 표시하지 않는다. 다이얼로그 디자인·버튼·배치는 유지한다.
