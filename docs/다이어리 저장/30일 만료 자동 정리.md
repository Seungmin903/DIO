## 실행 정책

서버 UTC Clock의 실행 시작 시각에서 보관 기간(기본 30일)을 뺀 cutoff를 한 번 계산한다. `deleted_at <= cutoff`인 회원 소유(owner_user_id NOT NULL) 휴지통만 후보로 고른다. 정각 이전은 보존, 정각부터 대상이다. 활성 자료와 owner=NULL 비회원 자료는 제외한다. 사용자가 입력한 시각이나 요청 헤더로 대상을 정하지 않는다.

이 작업은 서버 내부 수명 관리이므로 사용자 JWT·OWNER 역할을 가장하지 않는다. 만료된 회원 소유 자료는 소유자의 비활성/탈퇴 상태나 left_at 때문에 영구 보존되지 않는다. 계정/멤버십 자체는 변경하지 않는다. HTTP 엔드포인트와 수동 영구 삭제의 인증·권한 정책은 변경하지 않는다. 이 자동 정리 범위는 Draft 정책으로 운영 활성화 전에 확인한다.

## 중복 없는 삭제와 경합

173의 SQL 정리를 DiaryPurgeGraph로 추출하고 수동 영구 삭제와 배치가 함께 사용한다. 페이지·요소·획·이력·초대·공유 연결·멤버·알림 참조/payload·생성 영수증을 동일한 규칙으로 정리한다. media_files/폰트 원본·AI 작업·공용 속지·회원·인증·외부 저장소 파일은 그대로 보존한다. 물리 미디어 GC를 추가하지 않는다.

후보 선택은 잠금을 잡지 않는다. 각 후보를 별도 REQUIRES_NEW 트랜잭션으로 처리하고 영수증→다이어리→페이지/요소 순서로 잠근다. 잠금 후 현재 owner_user_id, deleted_at, cutoff를 다시 확인한다. 이미 삭제/복원됐거나 새 삭제 시각으로 재이동한 자료는 건너뛴다. 복원이 정각 직전에 시작해 먼저 커밋하면 보존하고, 배치 삭제가 먼저 완료되면 뒤의 복원은 기존 404가 된다. 같은 후보를 여러 인스턴스가 선택해도 잠금 후 재확인으로 중복 삭제하지 않는다.

건당 트랜잭션 제한은 15초, PostgreSQL lock_timeout 기본 1000ms(트랜잭션 로컬)다. 실패한 항목은 알림·영수증·자식 정리까지 모두 롤백하고 다음 항목을 계속 처리한다. 실패 행은 DB에 남아 다음 순회에서 재시도된다. 작업 완료 기록을 DB 삭제와 별도로 남겨 중복 정리하는 구조는 아니다.

## 제한된 배치와 재시도

기본 한 번에 20개, 최대 500개를 deleted_at/UUID 오름차순 키셋으로 선택한다. 프로세스 내 커서는 선택한 마지막 키 다음을 이어 읽고 끝에 도달하면 처음부터 순회한다. 오래된 오류 행이 뒤 후보를 계속 가리지 않게 하며, 실패 행은 순회가 돌아오면 다시 처리한다. 프로세스가 재시작되면 처음부터 재조회하지만 삭제된 자료를 다시 만들거나 복원하지 않는다. 커서는 재시도 완료 표식이 아니므로 영속 큐가 유실되는 경우가 없다.

같은 서비스 인스턴스의 실행은 synchronized로 겹치지 않는다. 여러 서버는 각자 커서를 가지며 DB 잠금/재확인으로 정합성을 유지한다. 잠금 실패는 다음 순회로 미루고 이번 실행의 failed 집계에 포함한다. 결과는 examined/deleted/skipped/failed 숫자만 남기며 사용자 ID·자료 ID·SQL·본문·토큰을 로그에 출력하지 않는다. DB 선택 자체가 실패하면 스케줄러가 오류 종류만 기록하고 다음 주기에 다시 시도한다.

## 설정과 활성화

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| dio.diary.expiry-cleanup.enabled | false | true일 때만 정리 엔진과 스케줄러 생성. 이 작업에서 운영 설정은 변경하지 않음 |
| dio.diary.expiry-cleanup.delay-ms | 60000 | 한 번 실행이 끝난 뒤 다음 실행까지 지연 |
| dio.diary.expiry-cleanup.initial-delay-ms | 300000 | 앱 시작 후 첫 실행 지연 |
| dio.diary.expiry-cleanup.batch-size | 20 | 실행당 최대 후보, 1~500 |
| dio.diary.expiry-cleanup.lock-timeout-ms | 1000 | PostgreSQL 잠금 대기, 1~5000ms |
| dio.diary.trash.retention-days | 30 | 172 복원 정책과 같은 설정, 1~36500일 |

정리 기능이 꺼져 있으면 전용 batch-size/lock-timeout 설정은 바인딩·검증하지 않는다. 켜면 기존 범위 검증을 적용한다. 공통 trash.retention-days는 172 복원 서비스에서도 검증하므로 유효해야 한다.

선행 MR 병합·정책/백업 검토 후 `dio.diary.expiry-cleanup.enabled=true`로 활성화한다. Spring 환경변수는 `DIO_DIARY_EXPIRYCLEANUP_ENABLED=true` 또는 배포 설정의 정확한 프로퍼티 이름을 사용한다. 보관 기간을 바꾸면 기존 삭제 시각에도 새 기간이 적용된다. batch-size와 주기는 실제 행 수·잠금 시간을 보며 조정한다. 단일 실행의 전체 시간은 후보 수와 건별 제한에 영향을 받는다.

## 마이그레이션·복구

V11__index_expired_member_diaries.sql은 `(deleted_at,diary_id)`의 회원 휴지통 부분 인덱스만 추가하며 기존 행·V1~V10은 변경하지 않는다. 일반 CREATE INDEX이므로 적용 중 다이어리 쓰기가 대기할 수 있으며 운영 적용 시점은 별도로 정한다. 스케줄러를 끄면 새 자동 실행을 막을 수 있지만 이미 커밋한 영구 삭제는 복원되지 않는다. 앱 revert와 인덱스 제거만으로 데이터가 돌아오지 않는다. 실제 운영 활성화 전 DB 백업/복구 정책을 확인한다. 미디어 파일 보존은 173의 경계를 유지한다.
