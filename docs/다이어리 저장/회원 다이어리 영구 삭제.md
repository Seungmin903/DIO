# 회원 다이어리 영구 삭제·참조 정리 (235)

관련 Jira: [S15P31F106-235](https://ssafy.atlassian.net/browse/S15P31F106-235). 기반: [!172](https://lab.ssafy.com/s15-final/S15P31F106/-/merge_requests/172), SHA 2e348258. 이 후속 MR은 !172 브랜치를 대상으로 235 변경만 제출한다. !166→!172 선행 병합 뒤 develop 대상으로 전환하고 최신 코드·마이그레이션·CI를 다시 검증한다. 선행 MR 자체를 수정하거나 먼저 후속 내용을 합치지 않는다.

## 제공하는 동작

`DELETE /api/v1/member/diaries/{UUID}/purge`는 활성 계정의 검증된 로그인 세션과 `owner_user_id`에 일치하는 활성 OWNER 멤버십을 요구한다. !172의 회원 SecurityFilterChain·DiaryRequestIdentity와 기존 계정/멤버십 검증을 사용한다. 임의 사용자 헤더·요청 본문·클라이언트 역할은 권한 근거가 아니다.

- 휴지통 자료만 수동 영구 삭제한다. 보관 기간이 남아 있어도 소유자는 실행할 수 있다.
- 성공 204 + Cache-Control: no-store는 DB의 다이어리·자식 자료와 아래 참조 정리가 커밋됐다는 뜻이다. 외부 저장소 파일 삭제 완료를 뜻하지 않는다.
- 활성 자료는 409/DIARY_NOT_TRASHED. 상태 판단 전에 권한을 검사한다.
- 없는 ID·타인·EDITOR/VIEWER·탈퇴/불일치 OWNER는 동일 404/DIARY_NOT_FOUND. 성공 후 재요청도 404이며 추가 정리는 발생하지 않는다. 204 응답 유실 후에는 이 404를 확인하고 목록을 재조회한다.
- 무인증·위조·만료·취소 세션·비활성 계정은 401. 잘못된 UUID는 400.
- 삭제 후 복원과 활성 목록/상세 접근은 불가능하다. 같은 생성 키 재전송은 기존 결과 사용 불가 409이며 새 다이어리를 만들지 않는다.

## 트랜잭션과 삭제 순서

모든 DB 변경은 하나의 트랜잭션이다. 후반의 FK 위반·연결 실패를 포함해 예외가 나면 알림·영수증·자식 삭제도 모두 롤백한다. 새 모듈의 미처리 FK를 발견하면 CASCADE로 무시하지 않고 실패한다.

잠금 순서는 활성 사용자→해당 생성 영수증(키 순서)→다이어리 FOR UPDATE→활성 OWNER 멤버십→페이지/요소(UUID 순서)다. 영수증을 다이어리보다 먼저 잠가 기존 생성 재전송의 영수증→다이어리 순서와 역전되지 않게 한다. 영수증 잠금 전 소유자 조회는 조기 거부용이며 잠금 후 권한·휴지통 상태를 다시 검사한다. !172 복원과 경합하면 먼저 커밋한 상태를 잠금 이후 재확인한다. 페이지·요소 잠금은 FK를 통한 새 자식 삽입을 삭제 종료까지 직렬화한다.

1. 대상 페이지를 가리키는 모든 diary_members.last_opened_page_id를 NULL로 해제한다. 다른 다이어리 멤버의 잘못된 포인터도 해당 포인터만 해제한다.
2. 대상 diary_id 또는 대상 페이지를 가리키는 notifications의 diary_id/page_id/payload_json을 NULL로 해제한다. 수신자·종류·읽음·생성 시각과 알림 행은 보존한다. 대상과 무관한 알림은 변경하지 않는다. 이 정책은 대상 정보 노출과 기존 FK를 함께 해소하는 Draft 제안이다.
3. diary_creation_receipts의 대상 diary_id/response_body를 NULL로 비운다. user_id/key_hash/request_hash/completed_at 표식은 보존한다. 최신 회원 기반의 V10의 삭제 표식 제약·트리거와 호환되며 V10을 수정하지 않는다.
4. 대상 페이지의 canvas_history_operations, element_strokes, canvas_elements를 정리한다. 활성/개별 삭제된 페이지·요소를 모두 포함한다.
5. 대상 diary_invites, diary_media_library, diary_handwriting_fonts, diary_members 연결을 삭제한다.
6. 대상 pages 전체와 diaries 행을 삭제한다.

수정·공유·페이지/캔버스 담당은 부모 상태 확인과 같은 부모 우선 잠금 규칙을 사용해야 한다. 이 MR에서 제공하지 않는 각 모듈의 실제 쓰기 API 종단 경합은 해당 통합 시 검증한다. PostgreSQL이 검출한 교착/잠금 실패는 전체 롤백 후 기존 저장소 오류로 반환하며 부분 성공으로 처리하지 않는다.

## 미디어 보존 경계

media_files, 원본/파생 관계, ai_jobs, page_templates, users·인증 자료는 삭제하지 않는다. 다른 활성 다이어리·복원 가능한 휴지통·요소/이력/템플릿 JSON·개인 보관함·폰트·진행 중 AI 작업은 파일을 공유할 수 있다. 특정 다이어리의 연결 해제만으로 미사용 파일이라고 판정하지 않는다.

이번 구현은 storage_key 삭제, S3 호출, 파일 상태 변경, 추정 UUID JSON 탐색을 수행하지 않는다. 대상에서만 사용한 것처럼 보이는 파일도 원본 메타데이터와 객체를 보존한다. 따라서 물리 미디어 GC나 그 outbox/작업자를 구현했다고 표현하지 않는다. 미디어 담당과 참조 필드·개인 보관함 소유권·새 참조 생성 차단·보존/삭제 작업 계약을 합의한 뒤 별도 구현해야 한다. 현재 JSON 형식이 불명확한 참조는 보존한다.

## 데이터·복구 영향

신규 migration 및 기존 migration 변경은 없다. DB 행의 영구 삭제는 API로 복원할 수 없고 애플리케이션 revert로도 되돌아오지 않는다. 운영 사용 전 DB 백업·복구 절차와 위 알림/미디어 보존 정책을 확인한다. 이 작업은 전용 테스트 DB에서만 실행했으며 개발/운영 자료와 외부 저장소 파일은 변경하지 않는다.

## 검증 재현

backend에서 `gradlew.bat test --tests 'com.f106.DIO.diary.http.MemberDiaryPurgeHttpTests'` 및 전체 `gradlew.bat test`를 실행한다. HTTP 테스트는 실제 서명 JWT·활성 세션·필터·생성 키 재전송을 사용하며 이메일 로그인 화면·실기기 검증은 아니다.

실제 PostgreSQL은 폐기 가능한 루프백 `dio_trash_qa` DB만 사용한다. `DIO_LIST_QUERY_PG=true`, `DB_URL=jdbc:postgresql://127.0.0.1:<port>/dio_trash_qa`, `POSTGRES_USER`, `POSTGRES_PASSWORD`를 지정하고 `gradlew.bat test --tests 'com.f106.DIO.diary.purge.*'`를 실행한다. 각 테스트가 임의 purge_qa_ 스키마에 전체 Flyway를 적용하고 finally/AfterEach에서 자기 스키마만 제거한다. CI의 기존 격리 authPostgresTest에도 동일 테스트를 포함한다. !172 기반의 `infra/scripts/test-auth-postgres.sh`가 전용 DB를 만들고 테스트 컨테이너에 `DIO_LIST_QUERY_PG=true`, `DB_URL=jdbc:postgresql://127.0.0.1:5432/dio_trash_qa`, PostgreSQL 계정 환경변수를 전달한다. Gradle 필터 추가만으로 실행됐다고 판단하지 않고 CI 아티팩트에서 실제 실행 수·skipped=0을 확인한다.
