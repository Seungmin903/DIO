# 다이어리 카드 페이지 수 (S15P31F106-252)

보관함 스와이프·한눈에 보기와 검색 결과의 카드 제목 아래에 `N페이지`를 표시한다. 표지 그림·생성 전 미리보기와 저장 형식은 그대로 사용한다.

## 데이터 기준

- 로컬 보관함은 기존 `useLibraryMetadata`가 읽는 편집 문서의 `pages.length`를 사용한다. 저장 문서가 없으면 실제 생성할 초기 구성의 페이지 수를 센다.
- 편집 후 보관함 복귀 시 기존 요약 훅이 다시 조회하므로 페이지 추가·삭제가 반영된다.
- 목 API 보관함은 다이어리 응답의 `pageCount`를 사용한다. 별도 문서 로드나 실제 API 연결을 추가하지 않는다.
- 응답에서 페이지 수가 빠지면 어댑터가 `null`로 남겨 확인 불가로 표시한다. 기존의 `0` 기본값으로 잘못된 빈 다이어리를 표시하지 않는다.
- 확인 전은 `페이지 수 확인 중`, 조회 실패·잘못된 값은 `페이지 수 확인 불가`로 표시한다. 정상 응답 0은 `0페이지`로 표시한다.
- 새 저장 키나 페이지 수 사본을 만들지 않는다. 기존 선택·즐겨찾기·검색·정렬·다중 삭제 동작을 유지한다.

## iPad QA 순서

1. 로컬 보관함에서 서로 다른 페이지 수의 다이어리를 열어 확인한 뒤 홈으로 돌아온다. 카드의 `N페이지`가 페이지 목록 개수와 같은지 확인한다.
2. 스와이프·한눈에 보기·즐겨찾기·제목 검색을 바꿔 같은 다이어리의 개수가 같은지 확인한다.
3. 편집기에서 페이지를 추가하고 홈으로 돌아와 1 증가하는지 확인한다. 페이지를 삭제하고 홈으로 돌아와 감소하는지 확인한다.
4. 앱을 다시 열어 최신 페이지 수가 유지되는지 확인한다.
5. 긴 이름의 다이어리와 관리 모드에서 제목·페이지 수·선택 표시·휴지통 버튼이 겹치지 않는지 확인한다.
6. 개발용 목 보관함에서는 여행 기록 9페이지, 함께 쓰는 일기 5페이지가 표시되는지 확인한다.

## 검증 기록

- 자동 테스트 112개 통과: 다이어리 API·생성·수정·휴지통·페이지네이션 회귀, 카드·검색 전달, 조회 실패 및 페이지 추가·삭제 후 요약 갱신을 확인했다.
- `node qa/diary-page-count-browser.cjs`: 별도 Edge 컨텍스트의 합성 자료로 1280×800·412×892 로컬 보관함을 확인했다. 스와이프·격자·검색·선택, 조회 실패 표시, 실제 편집기의 페이지 복제 후 3→4·삭제 후 4→3·새로고침 후 3페이지를 확인했다.
- `node qa/diary-page-count-browser.cjs --mock`: 같은 두 화면 크기의 목 보관함에서 여행 기록 9페이지가 스와이프·격자·검색·선택 중에도 유지되는지 확인했다. 네 컨텍스트 모두 브라우저 pageerror 0건이다.
- 웹·iOS 개발 번들 생성 확인. 번들 생성은 실기기 실행 검증과 별개다.
- 브라우저 QA는 로컬 웹 개발 번들을 `.expo/diary-page-count-web`, `EXPO_PUBLIC_DIARY_SOURCE=mock-library` 웹 개발 번들을 `.expo/diary-page-count-mock-web`에 생성한 뒤 실행한다. `expo export`에는 `--dev`가 필요하다. 결과·화면 자료는 Git 제외 경로 `frontend/qa/.out/diary-page-count/`에 생성한다.
- iPad 실기기: 2026-10-25 사용자가 로컬 보관함 QA 전 항목 정상 동작을 확인했다. 카드 페이지 수, 보기 방식 전환, 페이지 복제·삭제 후 갱신, Reload 후 유지, 긴 제목·관리 모드 표시를 확인했다. 기기 모델·iPadOS 버전은 제공되지 않았다.
- Android 실기기 및 iPad 목 보관함 별도 검증은 미확인이다. Jira는 병합 전 진행 중으로 유지한다.
- 커밋 전 코드 리뷰에서 필수 수정 사항은 발견되지 않았다. 관련 자동 테스트 112개를 재실행해 모두 통과했다.
