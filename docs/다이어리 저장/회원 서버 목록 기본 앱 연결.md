# 232 회원 서버 목록과 기본 앱 연결

2026-10-27. 다른 세션은 `DIO-ToolGuide`의 펜 성능과 `diary-api-preparation`·`notification-backend`의 알림 watermark 분리를 작업 중임을 확인했다. 해당 폴더는 수정하지 않았다. 기존 `diary-list-query`의 232 검색·정렬·복합 커서 방식을 참고해 현재 231·233 작업 폴더의 회원 HTTP 경계에 연결했다. 그 브랜치의 휴지통 작업이나 공개 목록 범위를 가져오지는 않았다.

## 서버

`GET /api/v1/member/diaries?q=&sort=created&limit=100&cursor=...`

- 기존 로그인 JWT·활성 세션에서 회원을 식별한다. 요청의 userId를 조회 권한으로 사용하지 않는다.
- 활성 멤버십과 실제 소유권이 일치하는 OWNER, 다른 소유자의 EDITOR/VIEWER만 포함한다. 탈퇴 멤버·삭제 다이어리·비참여 자료는 제외한다.
- 제목 부분 검색(%, _, !는 리터럴), created/updated/title/pages 정렬, 1~100개 커서 페이지를 지원한다. 정렬 값 동률은 UUID로 구분한다.
- 커서는 계정·검색어·정렬에 연결된다. 커서 값 자체를 권한으로 신뢰하지 않으며 모든 페이지에 회원 범위를 다시 적용한다. 입력 오류는 400 Problem 응답이다.
- 응답 items는 `{diary, pageCount, shared}`이고 nextCursor/hasNext를 제공한다. pageCount는 삭제되지 않은 서버 페이지 수다. canEdit는 233과 같은 메타데이터 수정 권한(OWNER)이다.
- 추가 DB 마이그레이션은 없다. 전용 로컬 PostgreSQL의 V1~V8 DB로 검증했다.

## 기본 앱

로그인 후 캐시를 읽고 서버 목록을 페이지당 100개씩 끝까지 조회한다. 전체 수집이 성공했을 때만 회원 인덱스를 교체한다. 따라서 기존 앱의 검색·필터·정렬은 첫 페이지에 한정되지 않고 수집한 전체 목록에 적용된다. 현재 앱의 검색·정렬 UI는 전체 수집 후 로컬 처리하며 서버 q/sort는 어댑터/API에서 지원한다. 목록은 메타데이터만 받아오고 편집 본문·이미지를 내려받지 않는다. 매우 많은 다이어리에서 첫 조회 비용을 줄이는 가상 목록·서버 검색 UI는 후속 최적화다.

`회원 목록 새로고침`으로 다시 조회할 수 있다. 페이지 실패·반복 커서는 기존 목록을 지우지 않으며 오류와 재시도를 제공한다. 조회 중 생성·수정이 발생하면 오래된 목록으로 덮어쓰지 않고 재조회를 안내한다. 계정 종료 후 늦게 도착한 결과는 반영하지 않는다. 기존 로컬 즐겨찾기·템플릿 설정·편집 문서는 같은 ID에 유지한다. 서버에서 사라진 ID는 표시 목록에서 빼지만 기기 문서를 삭제하지 않는다.

다른 기기에서 만든 다이어리도 카드와 서버 페이지 수가 표시된다. 기기에 편집 문서가 없으면 열 때 안내하고 빈 문서를 저장하지 않는다. 서버 본문·미디어·페이지 편집 동기화는 별도다. 공유 표시는 서버 멤버십으로 결정하며 기존 목 공유 기능과 합치지 않는다. 회원 휴지통 연결도 별도다.

## PostgreSQL 비ASCII 검색과 커서 호환성 (2026-10-27)

MR !166 INFO 검토에서 `initdb --locale=C`인 실제 QA DB의 `LOWER('ÉÄ')`가 대문자를 유지하여 Java Locale.ROOT로 소문자화한 검색어와 일치하지 않는 문제를 재현했다. PostgreSQL에서는 제목과 검색어 모두 ICU root `und-x-icu`로 소문자화하고, 제목 키 정렬·비교에는 `C`를 명시한다. DB 기본 locale이나 데이터·스키마·Flyway 이력은 바꾸지 않는다. 실행 환경에 `und-x-icu`가 있어야 하며 없으면 서버 시작 시 명확히 실패한다. 운영/공유 PostgreSQL에서도 이 전제를 확인해야 한다. H2 테스트의 LOWER 동작만으로 PostgreSQL 동작을 보증하지 않는다.

검색은 앞뒤 공백 제거 후 부분 일치이고, 원본 및 소문자화한 검색어는 각각 100자 이하여야 한다. 악센트 제거 또는 모든 Unicode 문자의 동등화는 제공하지 않는다. `%`, `_`, `!`의 리터럴 검색은 유지한다. 정규화·제목 순서 변경 때문에 불투명 커서는 v2를 발급하며 이전 v1은 400으로 거부한다. 배포 중 이전 커서를 보유한 호출자는 첫 페이지부터 다시 조회해야 한다. 저장된 다이어리나 기기 문서는 변환하지 않는다.

전용 PostgreSQL 회귀 3개는 ÉÄ/éä, Σ/σ, İ/i+결합점 검색, 제목 순회 중 중복·누락, 동등 검색어로 후속 페이지 조회, v1 커서 거부를 검증한다. 재현 시 3개 실패를 확인한 뒤 수정본에서 모두 통과했다. 최신 종합 결과는 [develop 통합 검토](./회원%20다이어리%20develop%20통합%20검토.md)를 따른다.


## 목록 집계 실행 계획과 V11 (2026-10-27)

최신 INFO의 모든 정렬에서 LIMIT 전에 전체 후보를 집계한다는 주장은 현재 PostgreSQL 계획과 다르다. created/updated/title은 조회분(limit+1)에 대해서만 두 집계를 수행했다. pages 정렬은 후보별 정확한 pageCount가 정렬·커서 비교에 필요하며 후속 페이지 조건에서 같은 집계가 여러 번 평가될 수 있다. 비정규화 카운터는 페이지 추가·삭제·복구·동시 수정의 일관성 계약까지 바꾸므로 이번에는 도입하지 않았다.

실제 병목은 pages.diary_id의 활성 페이지 인덱스가 없어 후보마다 pages 전체를 순차 스캔하는 점이었다. V11__index_active_diary_pages.sql은 `pages(diary_id) WHERE deleted_at IS NULL` 인덱스만 추가한다. SQL·정확한 COUNT·회원 권한/탈퇴 필터·v2 커서 형식은 그대로다. 인덱스가 적용된 격리 스키마에서 삭제된 페이지·탈퇴 멤버·0페이지·동률·네 정렬의 여러 커서 순회를 검증한다.

일반 CREATE INDEX이므로 Flyway 트랜잭션에서 실행되며 구축 중 pages 쓰기가 대기할 수 있다. 큰 공유/운영 DB는 적용 시점과 쓰기 중단 허용 범위를 확인해야 한다. 기존 QA 레거시 V7/V8 이력은 먼저 별도 백업·복제 검증과 V9/V10 대응이 필요하며 V11을 구 이력 위에 무조건 실행하면 안 된다. 이번에는 원본 QA DB·기존 API에 적용하지 않았다. 수치·범위·검증은 [develop 통합 검토](./회원%20다이어리%20develop%20통합%20검토.md)를 참조한다.
