## 병합 순서

1. !166을 develop에 Squash merge한다. 먼저 229·230 계약 확인, 실기기 QA, 작성자 외 승인과 해당 SHA의 필수 CI를 확인한다.

후속 MR을 먼저 기반 기능 브랜치에 병합하거나 네 MR을 동시에 병합하지 않는다. 공유 브랜치 force-push/rebase로 선행 이력을 덮어쓰지 않는다. 최신 166은 인증 V7/V8을 보존하고 회원 카탈로그 V9/생성 영수증 V10을 사용한다. 174의 만료 인덱스는 기존 활성 페이지 V11과 충돌하지 않도록 V12로 연결한다. 선행 MR의 Draft/Ready 상태를 자동 변경하거나 작성자를 대신해 승인하지 않는다.

## 실기기 QA 실행표 (!166 중심)

테스트 계정 A/B, 실행 SHA·앱 빌드 ID·기종/OS·서버 주소(인증 정보 제외)·시각과 결과를 기록한다. iPad와 Android 태블릿에서 각각 실행한다.

- A 로그인→목록/검색/정렬→다중 내지 생성→서버 ID/첫 페이지로 편집기 진입. 생성 응답 유실 후 같은 키 재시도에서 중복 다이어리가 생기지 않는지 확인한다.
- 제목/표지 수정, 오래된 수정 기준 요청의 409와 최신 정보 재조회(로그인 정책으로 세션이 무효화되면 우선 401), 편집 중 늦은 GET이 필기·최신 메타데이터를 덮지 않는지 확인한다.
- 앱 종료/재실행, 세로/가로, 큰 글자·VoiceOver/TalkBack 탐색, 키보드·오류 재시도·오프라인 복귀를 확인한다.
- 로그아웃→B 로그인/같은 계정 재로그인에서 A의 목록·미확정 생성·편집 캐시가 노출되지 않는지 확인한다.
- 새 기기에 서버 다이어리만 있을 때 빈 로컬 문서를 자동 생성하지 않는지 확인한다. 현재 캔버스/미디어/페이지 편집의 기기 저장 경계를 설명한다.

현재 연결된 Android 기기가 없었으므로 위 항목은 실기기 미검증이다. Windows 번들/브라우저/서버 테스트를 iOS 네이티브 설치·실기기 성공으로 바꾸어 기록하지 않는다.

## 서버 QA 실행표 (!172→!174)

실제 환경 재현은 테스트 전용 계정·DB에서만 수행한다. 운영 자료를 대상으로 파괴 테스트하지 않는다.

- A 소유 자료 DELETE→삭제 시각 확인→반복 DELETE에서 시각 유지→본인 휴지통 조회→B/EDITOR 접근 404→기간 내 복원→정각부터 410을 확인한다.
- 휴지통의 A 자료 purge→DB 자식 제거·알림 참조/payload 해제·영수증 표식 보존→다른 다이어리/휴지통의 공유 사진·폰트 보존→동일 생성 키 409/복원 404를 확인한다.
- 자동 배치는 테스트 환경에서만 활성화하고 정각 이전/정각/이후 자료, 실패 FK 항목과 정상 항목, 복원·재삭제 동시 요청 및 두 실행자를 확인한다. disabled로 되돌린 뒤 새 주기 실행이 없는지 확인한다.
- 실제 처리량·잠금 대기·failed 누적을 관측하고 batch-size/delay/lock-timeout을 결정한다. 백업 복원 리허설·운영 활성화는 별도 담당 확인 결과를 남긴다.

## 자동 검증과 기록

최신 후속 체인에서 backend 전체 test와 authPostgresTest(인증/알림/비밀번호 재설정·234·235·236)를 실행한다. 실제 PostgreSQL의 새 체인과 V11→V12 기존 행 보존을 확인한다. 개발·원본 QA DB의 구 마이그레이션 이력은 수정/repair하지 않는다. 구 V9 만료 인덱스를 적용한 일회성 테스트 DB는 최신 체인 검증용 새 DB와 구분한다.

각 MR에 자신의 최신 통합 SHA·검증 결과·CI와 이 문서 링크를 기록한다. 사람이 수행할 항목은 미완료로 남긴다. 코드 통합/검증을 실제 MR 병합·Draft 해제·승인·운영 배치 활성화로 해석하지 않는다.
