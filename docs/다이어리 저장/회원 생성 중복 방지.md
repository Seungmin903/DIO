## HTTP 계약

`POST /api/v1/member/diaries`는 `Idempotency-Key`가 필수다. 8~128자이며 첫 글자는 영숫자, 이후에는 영숫자·점·밑줄·콜론·하이픈을 허용한다. 키는 대소문자를 구분하고 공백을 제거해 보정하지 않는다. 새 생성 작업에는 충분히 임의적인 새 키를 만들고, 응답 유실·네트워크 실패 후 재시도에는 **처음의 키와 본문을 유지**한다.

| 상황 | 결과 |
|---|---|
| 최초 성공 | 201, Idempotency-Replayed: false |
| 같은 사용자·키·정규화 요청 | 최초 201 본문과 Location, Idempotency-Replayed: true |
| 같은 사용자·키·다른 내용 | 409 IDEMPOTENCY_KEY_REUSED |
| 키 누락·형식 오류 | 400 MISSING_IDEMPOTENCY_KEY / INVALID_IDEMPOTENCY_KEY |
| 동일 키의 DB 잠금 대기 초과 | 409 IDEMPOTENCY_IN_PROGRESS, Retry-After: 1 |
| 원래 결과 삭제·소유권/OWNER 멤버십 상실 | 409 IDEMPOTENCY_RESULT_UNAVAILABLE, 새 다이어리를 만들지 않음 |

인증·활성 계정·현재 OWNER 권한을 재확인하므로 키만 알아서는 결과를 읽을 수 없다. 같은 문자열 키를 다른 사용자가 사용하면 독립된 생성 작업이다. 응답 재사용은 **처음 생성 당시 스냅샷**이며, 현재 제목이나 페이지 상태는 상세 조회로 다시 확인한다. 속지 비활성화 이후에도 이미 성공한 동일 요청은 최초 응답을 반환한다.

## 원자성과 동시 요청

V10의 `diary_creation_receipts`는 사용자 ID+키 SHA-256 해시를 PK로 사용한다. 원문 키·토큰·전체 요청 본문은 보관하지 않는다. 요청 해시에는 기본값·앞뒤 공백 제거를 적용한 메타데이터와 속지 코드·버전·설정이 포함된다. 객체 키 순서와 숫자 표기는 정규화하고 페이지 배열 순서·색상 문자열 등 실제 값의 차이는 구분한다. 카탈로그 기본값을 해석한 결과가 아닌 요청 자체의 정규화이므로 `{}`와 명시적 width/height는 다른 요청이다.

키 예약, 다이어리·OWNER·전체 페이지 생성, 성공 응답 저장은 **같은 DB 트랜잭션**이다. 성공 전 어떤 단계에서 실패해도 키 기록까지 롤백한다. 실패 응답을 캐시하거나 별도 트랜잭션에서 키를 먼저 확정하지 않는다.

PostgreSQL의 `INSERT ... ON CONFLICT DO NOTHING`과 행 잠금으로 동일 키를 직렬화한다. 첫 생성이 커밋되면 기다리던 요청은 결과를 재사용하고, 첫 생성이 롤백되면 다음 요청이 생성한다. 키 삽입·영수증 행 잠금의 기본 대기 상한은 5초이며 `dio.diary.idempotency.lock-timeout-ms`로 100~10000ms 사이에서 설정한다. 트랜잭션의 기존 lock_timeout은 성공 시 복원한다. SQLSTATE 55P03/57014와 대응 Spring 예외를 대기 초과로 변환하고, 실패한 PostgreSQL 트랜잭션에서 추가 SQL을 실행하지 않는다.

## 보관·삭제

키를 조용히 만료시키면 오래된 재시도가 두 번째 다이어리를 만들 수 있어 현재 자동 만료는 없다. 영구 삭제 시 FK가 다이어리 참조를 비우고 V10 트리거가 응답 스냅샷을 제거한다. 키·요청 해시와 완료 시각만 중복 방지 표식으로 남긴다. 사용자 영구 삭제 시에는 FK CASCADE로 제거된다.

235 영구 삭제 통합에서는 이 새 참조를 함께 고려해야 한다. receipt→diary→membership 순서의 재요청 잠금과, 삭제 시 FK 갱신을 고려해 잠금 순서를 정한다. DB 경합으로 롤백된 요청은 같은 키로 재시도하며 키를 바꿔 우회하지 않는다. 최종 보관 정책이 바뀌면 중복 생성 방지 보장을 유지하는 별도 정책이 필요하다.

### 보관 비용과 정책 변경 시 주의

현재 계정이 유지되는 동안 키 표식의 개수는 자동으로 줄어들지 않고, 영구 삭제되지 않은 다이어리의 최초 응답 스냅샷도 유지된다. 따라서 저장 용량이 무제한으로 관리된다는 보장은 없다. 운영 데이터 규모에서 영수증 수·테이블/인덱스 크기를 관찰하고 최종 보관 기간·용량 정책을 합의해야 한다. 응답 본문만 지우더라도 현재 같은 키 재응답 계약이 바뀌므로 단순 정리 배치를 임의 추가하지 않는다. 기간 제한을 도입하려면 오래된 기기 재시도와 키 재사용을 구분하는 서버/클라이언트 계약부터 정해야 한다.

회귀는 오래된 완료 시각의 키도 같은 최초 결과를 재응답하는지, 다이어리 영구 삭제 후 응답 제거·표식 유지·재생성 거부, 사용자 영구 삭제 후 표식 정리를 실제 PostgreSQL에서 검증한다. 사용자 삭제 회귀는 이 FK의 동작 확인이며 235 전체 영구 삭제 기능이 완성됐다는 뜻은 아니다.

## 프런트

`createMemberDiaryApi.create(input, { requestId })`의 requestId가 필수이며 기존 HTTP transport가 이를 Idempotency-Key로 전달한다. 어댑터가 호출할 때마다 새 키를 만들지 않는다. 호출자/진행 중 생성 작업이 키·입력을 유지해야 한다. 회원 기본 앱은 생성 키·입력을 요청 전에 계정별 기기 저장소에 보관하며 재실행·재로그인 뒤 같은 키와 본문으로 재시도한다. 게스트·체험 계정의 목 생성 mutation은 별도다.

서버의 키 충돌·처리 중·기존 결과 사용 불가 코드를 보존하고 해당 상황에 맞는 안내를 제공한다. 새 키로 자동 재전송하지 않는다. CORS에서 Location·Idempotency-Replayed·Retry-After를 노출한다.

## 검증 범위

- H2/PostgreSQL 공통: 최초 결과 재사용, 메타데이터 변경 후 최초 스냅샷, JSON 순서·숫자 정규화, 내용·순서 충돌, 사용자별 키 분리, 페이지 저장·응답 저장 실패 롤백과 같은 키 재시도, 잘못된 키·과도한 숫자 거부, 삭제·멤버십 상실·카탈로그 비활성화 후 동작.
- PostgreSQL 별도: 서로 다른 서비스 인스턴스·DB 트랜잭션의 동시 요청 1회 생성, 첫 실패 후 대기 요청의 생성, 100ms 잠금 시간 초과와 같은 키 재시도, 영구 삭제 후 응답 제거·키 표식 유지.
- HTTP: 키 필수, 재요청 본문·Location 일치, Idempotency-Replayed 헤더, 다른 내용 409, 계정별 독립 생성·로그아웃 거부.
- 프런트: 응답 유실 뒤 헤더·본문 유지, 충돌 시 새 키 자동 전환 금지, 실제 Spring 응답·OpenAPI 계약.

이 단계에서는 실제 개발/운영 DB에 직접 적용하지 않았다. 이후 전용 로컬 DB의 V8 적용과 기본 앱 전환은 [회원 기본 앱 연결](./회원%20기본%20앱%20연결.md)에서 진행했다. 공유/운영 DB 배포와 실기기 QA, 최종 팀 계약은 별도다.
