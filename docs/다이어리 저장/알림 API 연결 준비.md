- 250: 공통 카운트 구독, 앱 활성/복귀·30초 갱신, 초대 최신 상태 조회, 공유 화면 전달 콜백 준비. 실제 공동 편집·초대 수락/거절·닉네임 저장은 구현하지 않았다.

## 구조와 연결 지점

| 파일 | 역할 |
|---|---|
| `frontend/src/notifications/notificationApi.js` | 244 제안 DTO·경로를 화면 모델로 변환. 문자열 ID, pagination/count 검증 |
| `mockNotificationTransport.js` | 계정별 메모리 목. 조회/쓰기/카운트/초대 오류를 독립 주입 |
| `notificationStore.js` | UI와 분리된 상태·경합 처리·동일 요청 재시도·페이지 조회·갱신 수명 |
| `useNotifications.js` | 한 로그인 세션의 store 및 AppState/웹 visibility 구독 |
| `NotificationPanel.js` | 목록 및 상세 상태 표시, `NotificationEntry`와 공유할 count, `onInvitationReady` |
| `MockNotifications.js` | 계정 A/B, 응답 설정, 공유 화면 콜백 검증용 화면 |

실제 연결 시 인증 세션을 경계로 API/게이트웨이/store를 새로 만들고 이전 store를 dispose한다. 보관함과 편집기는 동일한 store를 상위 Provider에서 공유한다. 화면별로 각각 store를 만들어 카운트를 분리하지 않는다. `NotificationEntry`의 `count`와 `onPress`를 224 진입 버튼에 적용하거나 기존 버튼에 같은 상태를 전달한다.

`onInvitationReady(detail)`에는 공유 게이트웨이에서 확인한 inviteId와 현재 상태를 전달한다. 이 콜백은 수락 성공을 뜻하지 않는다. 공유 담당 화면은 수락 직전 다시 권한·상태를 검증하고, 성공/거절 후 `store.refresh()`를 호출한다. 문서 저장/탭 전환은 기존 편집기의 이동 절차를 따른다.

## 잠정 정책과 합의 필요

- 244 초안 기반 제안이며 HTTP transport는 연결하지 않았다. `/notifications`와 `/me/invitations/{id}` 경로·DTO는 실제 서버 합의 후 이 어댑터에서 수정한다.
- 빨간 점 = `actionableUnreadCount > 0`. 만료·취소된 미읽음 초대는 점 개수에서 제외.
- 목록 진입만으로 읽지 않는다. 항목 확인은 읽음 요청과 초대 상세 조회를 독립 실행한다. 읽음 실패도 상세 확인을 막지 않는다.
- 현재 목 서버의 전체 읽음은 숫자 ID 순서를 사용하며 최초 요청의 최상단 ID 경계를 재시도에도 유지한다. 이 비교는 UUID에는 적용할 수 없다. 실제 서버 연결 전 244에서 서버 발급 `readWatermark` 사용을 우선 합의한다. 프론트는 경계값을 해석하지 않고 재시도에도 같은 값을 보낸다. 새 도착 알림을 읽지 않는 보장·경계값 검증·만료·오류 정책까지 확정한 뒤 어댑터를 변경한다. `createdAt`을 대안으로 쓰면 동일 시각의 정렬 기준도 합의해야 한다. 아직 확정된 서버 계약은 아니다.
- 알림 삭제는 내 알림만 숨기는 동작이다. 초대 원본·멤버십·다이어리는 삭제하지 않는다. 반복 읽음/삭제는 멱등이라는 계약이 필요하다.
- 카운트 갱신 실패 시 이전 값을 유지하고 오류를 표시한다. 목록 조회 실패도 기존 결과와 재시도를 표시한다.
- 쓰기 성공 후 재조회 실패는 쓰기 실패로 표시하지 않는다. 쓰기 중 연타 차단, 불명확한 실패는 같은 명령만 재시도, 400/401/403/404/409/410/422는 단순 쓰기 재시도 제외.
- 화면이 활성일 때 카운트를 30초마다 조회한다. 초기·포그라운드 복귀·재진입·조작 후 목록과 카운트 조회. 백그라운드에서는 주기 타이머 중단. 실시간 수신을 보장하지 않는다.
- 인증 217·218, 공유 담당의 수신자 상세/수락/거절/닉네임, 244 계약, 245~248 BE가 확정되어야 실제 서버 연결 가능.

### 개발용 알림 표시 검증

- 249·250 개발용 알림 연결 검증에서는 `danger`의 8pt 점을 유효한 미읽음 초대 표시로 사용한다. 접근성 이름에 개수도 표시한다. 최종 UI 규칙이 아니며 224 최종 배치·빨간 점 조건은 244 합의 후 확정한다.
- ‘알림’과 ‘공유 버튼 연결 검증’의 같은 개수·점은 동일 저장소 구독을 검증하기 위한 배치다. 224 연결 시 보관함 알림과 편집기 공유 등 각 화면의 진입점에 적용한다.
- !136 리뷰 반영으로 개발용 표시 규칙을 공통 디자인 가이드에서 이 문서로 이동했다. 실행 코드·표시 동작은 변경하지 않았다. 전체 읽음 경계는 244의 합의 항목으로 추적한다.

## 실행과 iPad QA

폴더: `C:\Users\SSAFY\Documents\ChatGPT\자율프로젝트 2\.worktrees\diary-api-preparation\frontend`

```powershell

```

이미 이 폴더의 mock-library 서버가 실행 중이면 Expo Go에서 Reload한다. **목 보관함 → 알림 연결 검증**으로 진입한다. `__DEV__`와 mock-library 환경 분기 안에서만 노출된다. 일반 앱·기존 로컬 다이어리를 변경하지 않는다. 목 알림 화면을 완전히 닫았다 다시 열면 메모리 샘플은 초기화된다.

1. **기본**: 샘플 계정 A, 새 초대 2개 표시. 알림 더 보기로 총 4개 확인. 알림/공유 버튼 연결 검증의 개수가 같다.
2. **조회**: 알림 목 응답 설정 → 목록 한 번 실패 → 알림 새로고침 → 이전 목록과 오류 → 알림 목록 다시 시도. 빈 목록도 별도로 확인.
3. **읽음**: 읽음·삭제 한 번 실패 → 초대 확인 4. 상세는 열리고 읽음 오류가 남아야 한다. 알림 처리 다시 시도 후 새 초대 1개.
4. **이동**: 초대 화면으로 이동 → inviteId 전달 확인. 이는 실제 가입/수락이 아니다. 알림으로 돌아가기.
5. **초대 오류**: 초대 만료/취소/권한 없음 선택 후 초대 확인. 이동 버튼 없이 상태 안내. 초대 정상 → 상세 다시 시도로 회복.
6. **삭제**: 읽음·삭제 응답 유실 → 알림 삭제 → 같은 처리 다시 시도. 해당 알림만 사라지고 성공. 초대는 목 서버에 유지(자동 테스트에서 검증).
7. **전체 읽음 경합**: 읽음·삭제 응답 유실 → 모두 읽음 → 오류 후 새 초대 도착 → 알림 처리 다시 시도. 새 초대는 안 읽음·빨간 점으로 남는다.
8. **카운트 오류**: 알림 수 한 번 실패 → 포그라운드 복귀 재조회. 기존 점 유지·오류 표시 → 알림 수 다시 시도.
9. **수명**: 목록을 닫고 새 초대 도착 후 30초 내 점 증가. 앱을 다른 앱으로 보냈다가 복귀하면 재조회. 사용자 iPad 정상 확인 보고.
10. **계정**: 알림 샘플 계정 변경 → B 샘플만 표시. 보관함으로 돌아갔을 때 기존 다이어리/수정 상태 유지.

응답 설정은 다음 요청부터 적용되며 ‘한 번 실패’는 선택할 때마다 한 번만 실패한다. 권한 없음 상태는 설정을 정상으로 돌린 뒤 새로운 요청으로 확인한다.

## 리뷰 수정 및 iPad 확인 이력 (2026-10-25)

- 사용자가 기존 249·250 목 응답 QA를 iPad에서 모두 정상 확인했다고 보고했다. 기기 모델/iPadOS는 별도 수집하지 않았다.
- 이후 코드 리뷰에서 발견한 세 경계 상황을 수정했다.
  1. 앱 복귀·새로고침 때 열린 초대 상세도 갱신한다. ‘초대 화면으로 이동’은 공유 게이트웨이에서 다시 확인한 PENDING만 전달한다. 조회 중·실패·만료·취소·권한 오류에서는 이동하지 않는다. 조회 도중 상세 닫기/다른 초대 선택/계정 종료도 이전 콜백을 무효화한다.
  2. 첫 페이지 재조회가 성공하기 전에는 기존 전체 목록과 커서를 유지한다. 실패해도 더 보기로 받은 항목을 유지하며, 성공하면 새 첫 페이지로 교체한다.
  3. 추가 페이지의 항목 개수와 다음 커서를 독립 관리한다. 빈 마지막 응답의 null 커서를 반영하여 더 보기 반복을 막는다.

- 웹 QA 스크립트에 더 보기 결과 보존과 이동 직전 만료 차단을 추가했고, Edge 1280×800·412×892 모두 통과했다(pageerror 없음).
