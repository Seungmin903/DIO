# DIO 실기기 QA 14개 항목 웹 조사 (기준일 2026-11-04)

표기: **[확인]** 은 페이지 본문을 직접 열어 읽은 것이다. **[검색요약]** 은 검색 결과 요약만 본 것이다. **[미확인]** 은 근거를 못 찾은 것이다. 일반 지식은 "일반 지식"이라고 따로 적었다.

한계는 세 가지다.

- 가입 이관, 초대 수락, 협업 권한 박탈에 대한 "공식 모범 문서"는 못 찾았다. 해당 항목에는 사례 근거 수준이라고 적었다.

## 1. 게스트에서 가입하는 lazy registration

**권장 해법**
- 가치를 먼저 주고 로그인은 "저장·공유·동기화"처럼 계정이 꼭 필요한 순간에만 요구한다. 게이트 시점은 한 가지 규칙으로 통일한다. 예: 서버 저장이 필요한 기능을 누를 때만 요구한다.
- 게이트 직전에 "하려던 동작(intent)"을 저장해 두고, 로그인이 끝나면 같은 화면·같은 동작으로 복귀시킨다(post-login return). 이건 설계 권고이며, 이 항목에 직접 맞는 공식 문서는 못 찾았다.
- 게스트 데이터는 새 계정을 만들어 복사하는 방식보다, 같은 익명 ID에 자격증명을 연결(link)해서 데이터가 그대로 이어지게 하는 방식이 업계 표준이다. 이미 가입된 계정으로 로그인하면 "충돌" 상황이 되니, 이때만 병합 또는 선택 UI를 보여 준다.
- 가입 후 기능이 줄어드는 건 설계 결함이다. 게스트 기능의 상위집합이 회원이어야 한다. 가져오기 다이얼로그는 "이 기기 다이어리를 내 계정으로 옮기기"를 기본으로 하고 보조 선택지 1개만 둔다. 버튼 3개는 과하다.
- 가입 전에 "왜 계정이 필요한지"를 먼저 설명한다. 가입 직후에는 불필요한 추가 질문 없이 바로 환영하고 원래 작업으로 돌려보낸다.

**참고 사례**
- Duolingo는 첫 레슨 뒤에 "진행 저장"을 이유로 가입을 요구한다고 한다. 출처가 블로그라 [검색요약] 수준이다.
- Firebase 익명 인증은 `linkWithCredential`로 데이터를 보존한다. 다른 계정에 이미 쓰인 자격증명이면 `credential-already-in-use` 오류가 나며, 병합은 직접 구현해야 한다.
- Firebase 익명 계정은 Identity Platform에서 30일 지난 계정 자동 삭제를 켤 수 있다.

**출처**
- Apple Sign in with Apple HIG [검색요약]: https://developer.apple.com/design/human-interface-guidelines/sign-in-with-apple (계정이 꼭 필요하면 이유를 먼저 설명하고, 완료되면 바로 환영하며, 계정에 불필요한 정보를 요구해 늦추지 말라는 취지)
- Apple Managing accounts [검색요약]: https://developer.apple.com/design/human-interface-guidelines/managing-accounts
- Firebase 익명 인증(미러 페이지): https://firebase.google.cn/docs/auth/web/anonymous-auth?hl=vi
- Android Credential Manager 패스키 블로그 [검색요약]: https://android-developers.googleblog.com/2025/09/best-practices-migrating-users-passkeys-credential-manager.html (가입 직후·로그인 직후 패스키 제안, 복구 경로 유지, 단계적 롤아웃)

**미확인**
- 게스트 이관 UX를 직접 다룬 Apple/Google 공식 문서는 못 찾았다. "게스트에서 가입 후 기능이 줄어든다"는 안티패턴 서술도 근거 문서가 없다.

## 2. 앱 재실행 시 세션 풀림 (RN 세션 유지)

**권장 해법**
- 액세스 토큰은 짧게 쓰고, 리프레시 토큰은 `expo-secure-store`(iOS Keychain, Android Keystore 암호화)에 둔다. 앱 시작 때 저장된 리프레시 토큰으로 조용히 갱신(silent refresh)한 뒤 화면을 그린다. 갱신이 실패하면 안내 없이 게스트로 떨어뜨리지 말고 "다시 로그인해 주세요"를 한 번 알린다. 데이터가 이어지는 로그인 화면으로 보내야 한다.
- 공개 클라이언트(앱)의 리프레시 토큰은 sender-constrained이거나 rotation(1회용 교체)을 써야 한다. 갱신 요청은 동시에 하나만 보내도록 직렬화한다(레이스로 토큰이 무효화되는 것을 막는다).
- Android는 Auto Backup에서 SecureStore 항목을 제외해야 한다. 복원 후에는 복호화가 안 된다. expo-secure-store 설정 플러그인이 백업 설정이 없으면 자동 제외한다. 이미 커스텀 백업 규칙이 있으면 직접 제외 규칙을 넣어야 한다.
- SecureStore 값이 사라질 수 있으니(Android는 앱 삭제 시 삭제, iOS는 재설치해도 유지) 토큰 유실은 정상 경로로 취급해 재로그인으로 복구한다.

**참고 사례**
- 앞의 리서치 `안드로이드 정책.md` 11번에서도 토큰을 백업 제외하라고 이미 권고했다.

**출처**
- Expo SecureStore **[확인 아님, 검색요약]**: https://docs.expo.dev/versions/latest/sdk/securestore/ (현재 문서 경로는 secure-store일 수 있음: https://docs.expo.dev/versions/latest/sdk/secure-store/)
- RFC 9700 **[확인]**: https://www.rfc-editor.org/rfc/rfc9700 ("Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation")
- RFC 8252 (네이티브 앱 OAuth, 외부 사용자 에이전트 사용) [검색요약]: https://www.rfc-editor.org/rfc/rfc8252

## 3. 공유 초대 수락 후 바로 콘텐츠로 안 들어감

**권장 해법**
- 초대 링크는 "수락 + 해당 콘텐츠 열기"를 한 번에 한다. 수락 후 목적지는 항상 초대받은 다이어리다. 보관함으로 돌아가면 안 된다.
- 앱 미설치, 비로그인, 로그인 후 복귀 세 경우 모두 초대 토큰을 보존했다가 마지막에 해당 다이어리로 보낸다.
- 링크가 만료·취소된 경우는 막다른 화면 대신 "초대가 만료됐어요 + 초대한 사람에게 요청하기" 같은 다음 행동을 준다.
- Firebase Dynamic Links는 2025-08-25 종료됐고 공식 대체재가 없다. 미설치 상태의 deferred deep link는 Android App Links/iOS Universal Links만으로는 안 되고, 설치 후 복원에는 별도 수단(Play Install Referrer, 서버에 보관한 초대 토큰, 서드파티)이 필요하다. 이 부분은 [검색요약]이다.

**참고 사례**
- Figma: 초대 메일의 "Open in Figma" 버튼이 초대를 수락하고 파일을 연다. 링크 공유가 "anyone with the link"면 링크를 여는 것만으로 참여한다. 계정이 필요하다. 팀 초대는 특정 계정에 묶이지 않아 올바른 계정으로 로그인해야 한다. [검색요약]
- Google Docs: 권한이 없으면 "You need access → Request access"를 보여 준다. [검색요약]
- Notion·Goodnotes 초대 수락 플로우의 공식 문서는 못 찾았다. [미확인]

**출처**
- Figma 초대 수락: https://help.figma.com/hc/en-us/articles/1500008023902-Accept-invitations
- Google Docs 접근 권한: https://support.google.com/docs/answer/14743550
- FDL 종료 정리(서드파티): https://blog.pragmaticengineer.com/google-shutting-down-firebase-dynamic-links/
- Expo Android App Links(앞 리서치에서 확인됨): https://docs.expo.dev/linking/android-app-links/

## 4. 공동 편집 중 권한 박탈·저장 거절 UX, 개발자 코드 없는 오류 문구

**권장 해법**
- 저장이 거절돼도 로컬 편집은 보존한다. "저장하지 못했어요"를 한 번만 상단에 보여 주고, 원인(권한이 바뀜 / 네트워크 / 로그인 만료)별로 다음 행동을 준다. 예: "편집 권한이 없어졌어요. 내 사본으로 저장할래요?"
- 권한이 읽기 전용으로 바뀌면 편집 도구를 즉시 비활성화하고 이유를 한 줄로 설명한다. 조용히 도구만 사라지면 안 된다.
- 오류 문구는 NN/g 원칙을 따른다. 명확하고 간결하고 정중하게 쓰고, 해결 방법을 제안하며, 사용자를 탓하지 않는다. 기술 용어를 쓰지 않고, 사용자의 작업은 최대한 보존한다. 개발자 코드(HTTP 403, 스택 문자열)는 UI에 노출하지 않고 로그로만 남긴다.
- Adobe Spectrum의 3요소 구조도 참고할 만하다. 무슨 일이 일어났는지, 원인(알면), 해결 방법을 쓴다.

**참고 사례**
- Google Docs의 "You need access"와 "Request access" 패턴. [검색요약]

**출처**
- NN/g 오류 메시지 가이드라인 [검색요약, 본문 미확인]: https://www.nngroup.com/articles/error-message-guidelines/
- NN/g 영상 요약: https://www.nngroup.com/videos/error-message-communication-guidelines/
- Adobe Spectrum Writing for errors [검색요약]: https://spectrum.adobe.com/page/writing-for-errors

**미확인**
- Material 3 / Apple HIG의 오류 문구 작성 원칙 페이지는 본문을 못 읽었다. HIG Writing(https://developer.apple.com/design/human-interface-guidelines/writing)은 링크만 확인했다.
- "실시간 공동 편집에서 권한 박탈 시 UX"를 직접 다룬 공식 문서는 못 찾았다. 위 권고는 일반 오류 문구 원칙에서 이끌어 낸 것이다.

## 5. 뒤로가기로 작업 소실, 뒤로가기 계층

**권장 해법**
- 계층은 "열린 메뉴/시트 닫기 → 선택 해제 → 도구 해제 → (변경 있으면) 확인 → 나가기" 순서로 한 번에 한 단계씩 한다. 가장 안쪽 UI부터 닫는다.
- 변경이 있으면 곧바로 나가지 말고 확인을 둔다. 문구는 "변경 사항을 저장할까요?" 같은 형태로 하고 버튼은 저장 / 저장 안 함 / 계속 편집 정도로 한다. 가능하면 자동 저장(편집기 특성상)을 우선해 확인 자체를 줄인다. 이건 일반 설계 권고다.
- 뒤로가기 가로채기는 변경 사항이 있을 때만 켠다(enabled 플래그를 상태에 연동). 공식 문서가 이 방식을 권한다. 단, 제스처가 플래그 갱신 전에 들어올 수 있다는 주의가 있다.
- targetSdk 36 + Android 16에서는 predictive back이 기본 켜지고 `onBackPressed`가 호출되지 않는다. RN `BackHandler` 동작은 실기기에서 확인한다(앞 리서치 5번).
- iOS는 스와이프 닫기를 막고(`isModalInPresentation`) 시도 시 액션시트로 확인하는 것이 UIKit 관례다. 이건 일반 지식이다. HIG Modality 본문은 못 읽었다. [미확인]

**참고 사례**
- 공식 predictive back 디자인 문서는 제스처가 취소되면 "undoing any state changes"로 복귀하라고 한다(미리보기 중 상태를 바꾸지 말라는 뜻). **[확인]**

**출처**
- Predictive back 가이드: https://developer.android.com/guide/navigation/predictive-back-gesture [검색요약]
- Predictive back 디자인 **[확인]**: https://developer.android.com/design/ui/mobile/guides/patterns/predictive-back
- PredictiveBackHandler 레퍼런스(타이밍 주의): https://developer.android.com/reference/kotlin/androidx/activity/compose/PredictiveBackHandler.composable
- Android 16 behavior changes(앞 리서치): https://developer.android.com/about/versions/16/behavior-changes-16

## 6. 폰 세로 편집 도구 줄, 하단 시트 높이, 플로팅 되돌리기

**권장 해법**
- 가로 스크롤로 도구가 잘리는 방식보다, 주 도구 4~5개를 고정하고 나머지는 "더보기" 시트로 보내는 방식이 낫다. 도구 사용 빈도 상위를 고정하는 것이 원칙이다.
- Procreate Pocket은 상단 바에 현재 도구와 툴바 확장 버튼을 두고, 색·레이어는 하단에서 올라오는 팝아웃으로 연다. 4손가락 탭으로 UI를 숨길 수 있고, 되돌리기는 제스처가 있다. **[검색요약]**
- Goodnotes는 툴바를 숨김/표시·순서 변경으로 커스터마이즈할 수 있다고 한다. 컴팩트 툴바는 사용자 요청 수준이고 iPhone 툴바 문서는 못 찾았다. [검색요약, 일부 미확인]
- 바텀시트는 모달/스탠다드를 구분하고 드래그 핸들을 둔다. Compose는 `ModalBottomSheet`와 `SheetState`를 제공한다. **[확인]** 높이 규격(최대 폭, 핸들 크기, 피크 높이) 수치는 m3.material.io가 안 읽혀 [미확인]이다. 이 프로젝트 결정(바깥 눌러 닫기 없음)은 그대로 두면 된다.
- 플로팅 되돌리기는 캔버스 가장자리 제스처 영역과 겹치지 않게 시스템 제스처 insets 안쪽에 둔다. predictive back 문서가 "제스처 영역 아래에 터치 대상을 두지 말라"고 한다. **[확인]**
- Canva 모바일 하단 툴바 문서는 못 찾았다. [미확인]

**출처**
- Procreate Pocket 인터페이스: https://help.procreate.com/pocket/handbook/interface-gestures/interface
- Procreate Pocket 제스처: https://help.procreate.com/pocket/handbook/interface-gestures/gestures
- Compose 바텀시트 **[확인]**: https://developer.android.com/develop/ui/compose/components/bottom-sheets

- Goodnotes 툴바 사용자 요청 글: https://feedback.goodnotes.com/forums/191274-customer-suggestions-for-goodnotes/suggestions/45980212-toolbar-editor

## 7. 빈 상태 설계, 온보딩, aha moment

**권장 해법**
- NN/g의 세 가지를 따른다. 상태 알림(로딩 중 / 실패 / 진짜 비어 있음을 구분), 학습 단서(이 공간이 뭔지·어떻게 채우는지 한 줄), 핵심 작업으로 가는 직접 경로(버튼). 로딩 중에 "비어 있음"을 먼저 보여 주면 안 된다. **[확인]**
- 첫 실행은 강제 튜토리얼보다 맥락 안 도움말을 우선한다. 사진 한 장 고르고 첫 스티커를 붙이는 순간까지 단계를 최소화한다.
- 마스코트는 CTA를 가리지 않는 보조 장식으로만 쓴다. 이 프로젝트의 "안내 멘트 금지" 규칙과 충돌하지 않도록 사용법 설명 대신 "상태 + 버튼"만 쓴다.
- Duolingo는 가입 전에 첫 레슨을 먼저 하게 하고 일일 목표를 정하게 한다. 출처는 블로그다. [검색요약]
- Toss 사례는 이번 조사에서 근거를 못 찾았다. [미확인]

## 8. 키보드 회피, 캔버스 위치 복원

**권장 해법**
- 앱 루트를 `KeyboardProvider`로 감싸고 `react-native-keyboard-controller`의 `KeyboardAvoidingView`/`KeyboardAwareScrollView`를 쓴다. 기본 RN `KeyboardAvoidingView`는 Android에서 edge-to-edge일 때 adjustResize 계약이 깨져 어긋난다. 이 부분은 [검색요약]이고 라이브러리 공식 문서는 직접 못 열었다. [미확인]
- 캔버스는 키보드가 열릴 때 편집 중인 텍스트가 보이도록 일시적으로 이동하고, 키보드가 닫히면 이전 팬/줌 값으로 복원한다. 키보드 열기 전 변환값을 저장해 두는 방식이다. 이건 설계 권고다.
- 네이티브 기준은 `WindowInsetsCompat.Type.ime()`과 `WindowInsetsAnimationCompat`(API 30+)이다. edge-to-edge가 전제다. **[검색요약]**
- 라이브러리 문서 중 한 곳은 Android 15에서 겹침이 보이면 `adjustResize`를 설정하라고 하지만, 다른 곳은 `KeyboardProvider`가 자동 처리한다고 한다. 서로 충돌하므로 설치 버전의 README로 확인해야 한다.

## 9. 시스템 글자 크기, 터치 타깃, TalkBack

**권장 해법**
- UI 크롬(도구 줄·버튼·시트)과 사용자 콘텐츠(캔버스 텍스트)를 분리한다. UI는 `maxFontSizeMultiplier`로 상한을 두고(예: 1.3 안팎), 본문·설정 텍스트는 확대를 허용한다. 캔버스에 놓인 글은 사용자가 정한 크기가 기준이므로 시스템 배율을 적용하지 않는다. 상한 값은 일반 지식이며 공식 수치는 없다.
- Android 14는 글자를 최대 200%까지 확대하고 비선형 곡선을 쓴다. 텍스트는 sp, 줄 높이도 sp로 정의하고 여백에는 sp를 쓰지 않는다. 200%로 UI를 테스트하라는 것이 공식 권고다. **[검색요약]**
- WCAG 1.4.4는 텍스트 200% 확대를, 1.4.10은 가로 스크롤 없는 리플로우를 요구한다. 두 기준 모두 W3C Understanding 본문은 못 읽었다. [검색요약]
- 터치 타깃은 Android 48dp 이상이 권고다. 아이콘이 작아도 padding으로 맞춘다. WCAG 2.5.8(AA)은 24×24 CSS px 최소이고 그보다 작으면 간격 예외가 있다. 모바일은 44~48을 목표로 한다. **[검색요약]**
- `configChanges`에 `fontScale`을 넣으면 글자 크기 변경 때 액티비티 재시작을 막을 수 있다. 대신 앱이 변경을 직접 처리해야 한다(RN은 `Dimensions` 이벤트로 재조정). WordPress Gutenberg-mobile 사례가 있다. Expo에서는 설정 플러그인이 필요할 수 있다. Expo 문서는 [미확인]이다.
- TalkBack 라벨은 동작을 말하게 한다. "제출"이지 "제출 버튼"이 아니다. 장식 요소는 접근성에서 숨긴다. RN에서는 `accessibilityLabel`을 쓴다. **[검색요약]**
