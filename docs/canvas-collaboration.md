# 캔버스 공동 편집

Jira: S15P31F106-350~355. 커서는 이번 범위에서 제외한다.

## 구조와 적용 범위

2026-11-02 캔버스 요소 프론트 연결에서는 개인 다이어리 저장은 요소 API, 공유 다이어리 저장은 기존 `/canvas-operations`로 분리한다. 서버 활성 멤버가 2명 이상인지 확인하며 준비된 재시도 작업의 경로는 유지한다. 현재 호출 경로와 재시도 한계는 [캔버스 요소 프론트 연결](./canvas-element-frontend-integration.md)을 따른다. 같은 변경을 두 경로로 이중 호출하지 않는다. 작업 이력·Undo/Redo·실시간 수신은 유지한다.

백엔드는 `collaboration/controller`, `service`, `domain`, `repository`, `dto`, `exception`, `config`, `infrastructure`로 나눈다. 기존 `canvas_elements`, `canvas_history_operations`, `pages`, `diaries`, `diary_members`를 사용한다. 새 테이블·컬럼·마이그레이션은 추가하지 않는다.

기존 요소 생성·수정·삭제·복구·일괄 변경 API도 같은 이력 기록 경로를 거친다. 기존 요청·응답 경로를 유지한다. 요소 생성 DTO에는 선택적 숫자 `sortKey`가 추가됐다(정수부 10자리·소수부 10자리). 명시적 null은 400이며, 생략하면 서버가 최대 순서 + 1에 배치한다. batch creates에도 같은 규칙을 적용한다. 새로운 공동 편집 API는 명시적 요소 UUID와 재시도 식별자를 추가로 요구한다.

프론트는 회원 서버 다이어리의 **텍스트·그림·기본 스티커·도형·기본 테이프**를 연결한다. 그림의 좌표·필압·펜 종류는 기존 요소 JSON과 이력에 저장한다. 사진·사용자 이미지 스티커·이미지 테이프와 사진 틀의 칸은 기존 에셋 API를 통해 파일 참조까지 공유한다. 기기 원본은 유지한다. 커서는 제외한다.

## REST API

모두 기존 Access Token 인증과 현재 OWNER/EDITOR 권한이 필요하다. 탈퇴·강퇴·비활성 계정은 사용할 수 없다. ID는 실제 서버 UUID를 사용한다.

| 기능 | Method | 경로 | 성공 |
|---|---|---|---|
| 작업 반영 | POST | `/api/v1/pages/{pageId}/canvas-operations` | 200 |
| 내 작업 취소 | POST | `/api/v1/pages/{pageId}/undo` | 200 |
| 내 작업 다시 실행 | POST | `/api/v1/pages/{pageId}/redo` | 200 |
| 내 작업 이력 | GET | `/api/v1/pages/{pageId}/history/me?page=0&size=20` | 200 |

작업 반영 예시:

```json
{
  "clientOperationId": "11111111-1111-4111-8111-111111111111",
  "changes": {
    "creates": [{
      "elementId": "22222222-2222-4222-8222-222222222222",
      "elementType": "TEXT",
      "x": 10, "y": 20, "width": 200, "height": 60,
      "propertiesJson": {"text": "함께 쓰는 기록"}
    }]
  },
  "expectedVersions": {}
}
```

`changes`는 기존 batch의 creates/updates/deleteElementIds/restoreElementIds를 사용한다. update에는 현재 `version`, delete/restore에는 `expectedVersions: {"요소 UUID": 현재 버전}`이 필요하다. 생성 요소 UUID는 클라이언트가 먼저 만든다. 기존 batch의 항목 수·본문 크기·미디어 검증 제한을 그대로 적용한다.

응답은 `operationId`, 원래 작업의 `clientOperationId`, `status`, `revision`, `replayed`, 현재 페이지의 살아 있는 요소 목록 `items`다. Long 작업 ID는 문자열로 반환한다. 동일 페이지·사용자·clientOperationId와 동일 본문을 재전송하면 중복 저장하지 않는다. 본문이 다르면 409다. 재전송 응답의 `items`는 최초 응답 복사본이 아니라 **현재 서버 상태**다.

취소·다시 실행은 이력 응답의 `nextUndo` 또는 `nextRedo`에서 operationId/revision을 읽고 다음처럼 요청한다.

```json
{
  "operationId": "123",
  "clientOperationId": "33333333-3333-4333-8333-333333333333",
  "expectedRevision": 0
}
```

새 명령에는 새 UUID를 만들고, 응답 유실 재시도에는 **같은 본문과 UUID**를 사용한다. 직전 명령의 재전송은 중복 실행하지 않는다. 이후 단계가 진행된 오래된 revision은 409로 거절한다. 다음 작업까지 연속 취소하는 빈 본문 API가 아니다.

## 이력과 충돌 정책

- 한 번 완료된 행동을 한 작업으로 저장한다. 드래그·슬라이더는 손을 뗐을 때 기록하며 취소한 제스처는 보내지 않는다.
- 현재 페이지에서 본인의 마지막 적용 작업부터 취소한다. 다시 실행은 취소의 역순이다. 다른 사람의 이력을 취소할 수 없다.
- 본인의 새 작업은 본인의 **같은 페이지** 다시 실행 후보만 무효화한다.
- 다른 사람이 같은 요소의 내용을 바꿨다면 전체 작업을 409로 거절한다. 일부 요소만 복원하지 않는다. 서로 다른 요소의 편집은 보존한다.
- 비교에서 버전·수정 시각만 증가한 차이는 제외하므로 본인 작업을 연속 취소할 수 있다. 위치·내용·스타일·삭제 상태 등 실제 저장 내용은 비교한다.
- 다이어리 → 페이지 순서로 잠근 뒤 최신 참여 권한과 버전을 확인한다. 요소와 이력은 한 트랜잭션에서 저장한다.
- 생성 취소는 요소를 soft delete하고 다시 실행 시 복원한다. 기존 레거시 형식 이력은 조회할 수 있지만 새 형식처럼 취소하지 않는다.

이력 스냅샷 형식은 `COLLAB_ELEMENTS_V1`이다. 기존 JSON 컬럼에 before/after 요소, 현재 충돌 검사 기준, revision, 마지막 명령 식별자를 보관한다.

## 실시간 연결

`ws(s)://서버/ws/diaries/{diaryId}`에 연결한다. JWT는 URL에 넣지 않는다. 연결 후 첫 프레임은 다음과 같다.

```json
{"type":"AUTH","accessToken":"발급받은 Access Token"}
```

인증·참여 검증 후 `READY`가 온다. 변경 트랜잭션이 커밋되면 `PAGE_CHANGED`(pageId, operationId, clientOperationId, actorUserId, revision, action)를 보낸다. 페이지 목록이 바뀌면 `PAGES_CHANGED`, 참여·탈퇴·강퇴·소유권 이전·멤버 닉네임/프로필 사진 변경·계정 탈퇴에 따른 멤버 이탈이 커밋되면 `MEMBERS_CHANGED`를 각각 `{"type":"PAGES_CHANGED","diaryId":"UUID"}`, `{"type":"MEMBERS_CHANGED","diaryId":"UUID"}` 형식으로 보낸다. 프론트는 페이지·참여자 이벤트를 받은 뒤 해당 HTTP 목록을 다시 조회하며, 소유자·역할 표시는 그 결과로 갱신한다. WS로 요소 변경이나 커서는 전송하지 않는다.

클라이언트는 15초 간격으로 PING을 보내고 PONG을 받는다. Access Token이 갱신되면 AUTH로 교체한다. 서버는 주기적으로 세션·참여 권한도 검사하고 로그아웃·강퇴·만료 시 1008로 닫는다. 미인증 연결은 약 5~6초 후 닫는다. 프레임 크기·빈도와 서버/IP/사용자별 연결 수를 제한한다.

Origin은 기존 `AUTH_ALLOWED_ORIGINS`를 재사용한다. dev/prod Nginx에 `/ws/` Upgrade 전달을 추가한다. dev의 기존 Basic 인증은 유지한다. Expo native는 개발 인증 헤더를 같은 서버에만 전달하며, 브라우저 dev 테스트는 해당 서버의 Basic 인증을 먼저 통과한 상태여야 한다. 프록시·Origin 설정은 실제 배포에서도 확인해야 한다.

이벤트는 커밋 후 별도 executor에서 전달하므로 소켓 I/O가 쓰기 트랜잭션을 붙잡지 않는다. 편집기 소켓이 `READY`인 동안 참여자 목록은 `MEMBERS_CHANGED`로만 다시 조회하고, 5초 HTTP 폴링은 연결 유실·WS 미지원 또는 공유 시트만 열려 있는 경우의 보조 수단이다. 이벤트를 영속 보관하는 outbox나 새 테이블은 없다. 현재 전달은 **단일 백엔드 인스턴스 내부** 기준이며, 다중 인스턴스 운영에는 공용 메시지 전달 수단이 추가로 필요하다.

## 오프라인·기존 화면 연결

계정·다이어리·페이지별 AsyncStorage 큐에 작업을 먼저 저장하고 서버로 보낸다. 저장한 요청 본문과 UUID를 재사용하여 네트워크 응답 유실·앱 재시작에도 중복 적용을 막는다. 기존 텍스트 로컬 저장 키와 더 최신의 문서 저장 내용도 복구한다. 늦게 온 응답은 새로 입력한 내용이나 다른 계정의 화면을 덮어쓰지 않는다.

동일 요소 충돌 시 로컬 편집과 대기 작업을 보존하고 기존 저장 상태 영역에 충돌을 표시한다. 자동 덮어쓰기·자동 충돌 병합은 하지 않는다. 충돌 내용을 선택적으로 합치거나 버리는 전용 화면은 이번에 추가하지 않았다. 기존 undo/redo 버튼은 회원 다이어리의 공유 가능한 캔버스 요소 작업에 대해 서버 승인을 기다린다. 페이지 설정 등 별도 로컬 작업을 취소할 때도 현재 원격 요소를 보존한다.

## 확인 방법

### 공동편집 프론트 실기기 재검증 (2026-11-03)

- 최신 develop의 WebSocket Origin·프록시 외부 포트 전달 수정 반영 후 Android Expo Go에서 `open → ws-ready`와 `ws-change` 수신을 확인했다. 이전 HTTP handshake 403 실패와 구분한다.
- 제공된 실기기 로그에서 공유 작업 POST `/pages/{id}/canvas-operations` 성공 184ms, 변경 알림 후 동기화 468ms가 관찰됐다. 이 값은 해당 요청·동기화 구간이며 양 기기 사이 전체 표시 지연이나 성능 보장 수치가 아니다.
- 사용자가 두 계정에서 상대 변경 반영 속도 개선, 자기 작업 실행 취소·다시 실행, 연결 복구 후 내용 동기화를 확인했다. 내 작업 이력 조회도 성공 로그로 확인했다.
- 프론트 소켓·진단·편집기 연결 테스트 `node --test tests/collaboration-socket.test.js tests/collaboration-diagnostics.test.js tests/collaboration-hook.test.js`: 27개 통과.
- 확인 후 로컬 진단 설정을 0으로 되돌렸다. 적용하려면 Expo 서버 재시작·기기 리로드가 필요하다. 진단 기능은 개발 환경에서 명시적으로 켤 때만 출력하며 기본은 꺼짐이다. 백엔드·인프라 코드는 이번 프론트 작업에서 수정하거나 테스트하지 않았다.

### 두 기기 지연 진단 (2026-11-02)

실기기에서 로컬 조작·상대 반영 지연이 보고되어 원인 측정용 진단을 추가했다. `frontend/.env`의 `EXPO_PUBLIC_COLLABORATION_DIAGNOSTICS=1`과 개발 실행에서만 활성화한다. 변경 후 Expo 서버를 재시작하고 두 기기를 리로드한다. `[collaboration-perf]`의 HTTP durationMs, sync waitMs/durationMs, ws-ready/ws-unavailable/ws-change/poll을 확인한다. ID·토큰·요청 본문·오류 내용은 기록하지 않는다. 기본은 꺼짐이고 서버 저장·재시도 정책은 변경하지 않는다.

두 기기에서 같은 페이지를 열고 텍스트 하나를 추가한 뒤 저장 완료와 상대 반영까지의 시간을 관찰한다. ws-change 없이 poll 뒤에만 반영되면 WebSocket 연결·이벤트 전달을 확인하고, HTTP 시간이 길면 해당 요청의 서버/네트워크 시간을 조사한다. waitMs가 길면 앞선 페이지 동기화 대기를 확인한다. 이 진단은 렌더링 FPS를 측정하지 않으므로 펜 움직임 자체의 끊김은 별도로 확인해야 한다. 실기기 로그를 받기 전에는 원인을 확정하지 않는다. 확인 후 환경변수를 제거한다.

### API 확인 절차

1. Swagger에서 두 계정을 준비하고 각각 로그인한다. 계정 A로 서버 다이어리와 페이지를 생성해 실제 diaryId/pageId를 받는다.
2. B를 초대해 EDITOR로 참여시킨다. A 토큰으로 작업을 생성하고 `history/me`에서 nextUndo를 확인한다.
3. nextUndo의 operationId/revision과 새 명령 UUID로 undo한다. 같은 요청을 다시 보내 중복 취소하지 않는지 확인한다. nextRedo로 복원한다.
4. B가 같은 요소를 수정한 뒤 A가 취소하면 409인지 확인한다. 다른 요소를 바꾼 경우에는 양쪽 내용을 유지해야 한다.
5. 두 WS 연결에 AUTH를 보내 READY를 확인한다. 커밋된 변경만 PAGE_CHANGED를 받는지, B 강퇴 후 B 연결과 API 권한이 종료되는지 확인한다.
6. Expo에서 같은 회원 다이어리를 열어 텍스트·그림·기본 스티커 변경과 재접속을 확인한다. 실제 기기에서는 기존 API 주소에 개발 PC의 LAN 주소가 필요하다.

자동 검증은 `CanvasCollaborationTests`(실제 임의 포트 WS 포함), 전용 PostgreSQL의 `CanvasCollaborationPostgresTests`, 프론트의 `collaboration-*.test.js`를 사용한다. PostgreSQL 태스크는 `collaborationPostgresTest`이며 `DIO_COLLABORATION_POSTGRES_URL=jdbc:postgresql://127.0.0.1:포트/dio_collaboration_qa`, `DIO_COLLABORATION_POSTGRES_PASSWORD`를 명시해야 한다. 개발 DB로 폴백하지 않는다. CI 전용 DB 스크립트에도 같은 태스크를 연결한다.

## 이미지 전용 API 제거 (2026-10-29)

사용자 요청에 따라 임의로 추가했던 이미지 업로드·조회 컨트롤러와 해당 전용 서비스·저장소·미디어 엔티티, 프론트 파일 전송·다운로드 연결을 제거했다. 기존 프로필 사진·기기 미디어 저장 기능과 다른 팀의 에셋 코드는 수정하지 않는다. 기존 파일·DB 데이터도 삭제하지 않는다.

당시 확인한 브랜치에는 재사용할 에셋 업로드·조회 API가 없었다(현재 연결은 아래 2026-10-30 항목 참고). 별도 에셋 작업 브랜치의 구현은 소유자 전용 조회이므로 이 작업에 가져오거나 권한을 임의로 바꾸지 않았다. 에셋 API와 참여자 접근 계약이 준비된 다음 연결한다. 대체 API는 추가하지 않는다.

사진·이미지 스티커·이미지 테이프의 기기 객체는 원격 스냅샷 가져오기와 로컬 실행 취소에서도 보존한다. 파일이나 기기 URI를 캔버스 API로 우회 전송하지 않는다. 과거에 이미지가 포함된 요청 본문이 기기 큐에 저장된 경우 요청 ID/본문을 수정해 재전송하지 않고 `deferredMedia`에 보관한다. 텍스트·그림·기본 스티커의 일반 전송은 유지한다.


제거 후 검증: 기존 페이지 API·공동 편집 및 배포 계약 회귀가 통과했다. 프론트 공동 편집 17개와 회원 계약 CI 73개가 통과했다. 삭제한 이미지 경로의 미등록, 그림·기본 스티커의 undo/redo, 로컬 사진 보존과 기존 이미지 전송 대기 보관을 확인했다.


## 초대받은 기기의 첫 문서 열기 보완 (2026-10-29)

초대 수락은 서버 멤버십을 만들지만 기존 앱은 계정별 기기 문서가 없으면 편집기를 열지 못했다. 이제 기기 문서가 처음 없는 경우에만 기존 `GET /api/v1/diaries/{diaryId}/pages`, `GET /api/v1/pages/{pageId}`로 실제 서버 페이지 ID·속지·공유 가능한 요소를 읽어 계정별 문서를 준비한다. 기존 기기 문서는 덮어쓰지 않고 읽기 실패·권한 거절·다른 문서 ID·빈 서버 페이지는 대체 문서를 만들지 않는다. 조회 도중 계정이 바뀌거나 기기 문서가 생기는 경우도 검사한다.

페이지 응답에 `templateCode`, `templateVersion`을 추가해 서버 PK를 추정하지 않고 기존 속지 에셋을 연결한다. 기존 DB 컬럼을 읽는 매핑만 추가했고 새 API·테이블·컬럼은 없다. 공유 창을 닫을 때 기존 보관함 조회를 갱신해 방금 참여한 다이어리를 찾을 수 있도록 한다.


### 동시 편집 충돌 복구

- 좌표가 겹치는 별도 필기는 서로 다른 요소로 저장되어 함께 표시됩니다.
- 같은 요소를 수정할 때는 최신 서버 요소에 기기에서 변경한 속성만 합칩니다. 서로 다른 속성 변경은 보존하고, 같은 속성 변경은 서버에 나중에 반영된 값이 적용됩니다. 텍스트 문자열과 필기 points 배열은 각각 하나의 속성으로 취급하며 문자·점 단위 CRDT 병합은 아닙니다.
- 서버에서 삭제된 요소를 오래된 수정으로 되살리지 않습니다.
- 409로 확정 거절된 편집 요청은 보관한 후 새 명령 ID로 다음 동기화에서 최신 버전에 재적용합니다. 네트워크 오류나 응답 유실은 기존 명령 ID와 본문을 유지해 중복 저장을 막습니다.
- 실행 취소 충돌은 해당 명령만 중단·보관하고, 다음 일반 편집과 서버 조회는 계속합니다.
- 편집 대기 기록이 없는 오래된 기기 스냅샷은 복구 사본을 남기고 서버의 기존 요소를 불러옵니다. 서버에 없는 기기 요소는 추가 작업으로 유지합니다.
- 기존 API와 저장 구조를 사용하며 API·테이블 추가는 없습니다.


### 조작 없이 원격 변경 표시

- 스티커·텍스트·도형 추가는 이동이나 추가 조작 없이 완료 작업으로 전송합니다.
- 텍스트 자동 높이 측정처럼 실행 취소 기록을 만들지 않는 캔버스 변경도 전송 대기열에 포함합니다.
- 조회 도중 기기 편집이 생겨도 페이지 전체 응답을 폐기하지 않습니다. 서버 변경과 요청 이후의 기기 변경을 요소·속성별로 합쳐 표시하고, 로컬 전용 사진은 보존합니다.
- 드래그 중에는 내 이동을 유지하며 상대의 새 요소를 표시합니다. 상대 요소를 내 편집으로 다시 전송하지 않도록 드래그 시작 스냅샷도 보정합니다.
- WebSocket 변경 이벤트는 즉시 조회를 요청합니다. 같은 페이지 이벤트가 몰리면 진행 중인 조회와 후속 조회 한 번으로 합쳐 밀림을 줄입니다. 5초 주기 조회는 알림 누락 복구용으로 유지합니다.
- 조회 결과 서버 요소(id·version·순서)도 그대로고 보낼 편집도 없으면 미리보기를 만들거나 편집 화면과 대조하지 않고, 저장 상태 표시도 바꾸지 않습니다. '저장 중'은 보낼 편집이나 실행 취소 요청이 남아 있을 때만 표시합니다(2026-11-08, S15P31F106-624).
- 요소 목록 비교와 편집 전후 차이 계산은 같은 객체를 가리키는 요소를 인코딩하지 않고, 길이가 다르면 바로 다르다고 봅니다. 획 하나를 확정하는 비용이 페이지 요소 수에 비례해 직렬화하지 않게 하기 위해서입니다.


### 편집기 새 페이지 추가

- 회원 편집기는 기존 `POST /api/v1/diaries/{diaryId}/pages` 성공 후 서버의 `pageId`로 페이지를 열고 캔버스 연결을 시작합니다. 비회원 기기 문서의 페이지 추가 방식은 유지합니다.
- 속지 코드·버전·용지 설정은 기존 `templateConfig` JSON에 저장하고 크기는 기존 필드로 전달합니다. DB의 속지 PK를 임의로 추정하지 않습니다.
- 페이지 생성 응답이 유실되면 기기에 남긴 요청 식별자로 기존 페이지 목록에서 결과를 찾아 복구합니다. 결과 불명 상태에서 생성 POST를 무조건 반복하지 않습니다.
- 기존 페이지 목록을 연결·주기 조회할 때 새 서버 페이지를 발견해 추가합니다. 이미 열린 페이지의 필기·사진과 현재 선택은 유지합니다. 페이지 목록 갱신은 현재 5초 주기 조회로도 복구됩니다.
- 기존에 서버 없이 만든 기기 전용 페이지는 자동 삭제하거나 서버에서 삭제된 페이지로 단정하지 않습니다.
- 새 API·테이블·컬럼은 추가하지 않습니다.


### 페이지 생성·삭제·복제와 목록 동기화 보완

- 기존 생성 `POST /api/v1/diaries/{diaryId}/pages`, 복제 `POST /api/v1/pages/{pageId}/copies`, 삭제 `DELETE /api/v1/pages/{pageId}`를 사용합니다. 새 HTTP/WS 경로와 테이블은 없습니다.
- 복제 전에 해당 페이지의 전송 대기 작업을 확인하고 서버에 저장된 캔버스를 복제합니다. 새 페이지 및 요소 ID는 서버 응답을 사용합니다. 삭제는 기존 소프트 삭제 계약을 유지합니다.
- 회원 페이지 삭제는 서버 성공 결과를 목록에 반영하며, 서버 페이지를 기기 undo만으로 복구했다고 표시하지 않습니다. 비회원 페이지 조작은 기존 기기 방식입니다.
- 페이지 API의 트랜잭션 커밋 후 기존 `/ws/diaries/{diaryId}` 연결에 `PAGES_CHANGED`와 diaryId를 보냅니다. 인증을 마친 해당 다이어리 멤버만 수신하고, 클라이언트는 기존 목록 API를 다시 조회합니다. 롤백 시 알림은 보내지 않습니다.
- 목록은 추가뿐 아니라 서버에서 사라진 페이지도 반영합니다. 현재 페이지가 서버에 없으면 남은 실제 페이지로 이동하고, 제거된 기기 페이지 본문은 문서의 `pageRecovery`에 보관합니다. 해당 페이지의 전송 대기 기록을 서버 요소 삭제 명령으로 바꾸지 않습니다.
- 유효한 페이지 목록을 확인하기 전에는 임의의 기기 UUID로 캔버스 요청을 보내지 않습니다. 404 PAGE_NOT_FOUND를 받으면 목록을 재확인하여 이미 삭제되었거나 기기 전용인 페이지를 계속 요청하지 않습니다.
- 진행 중인 로컬 페이지 변경보다 오래된 목록 응답은 버리고 다시 확인합니다. 기존 페이지 내용과 기기 사진은 목록 갱신으로 덮어쓰지 않습니다.
- 현재 UI의 마지막 페이지 삭제 방지는 유지합니다. 서버가 이미 빈 목록인 경우 기기 내용을 보관한 채 새 페이지 추가를 안내합니다.


- 생성 요청의 `templateConfig.clientPageRequestId`는 UUID입니다. 기존 생성 API가 다이어리 잠금 아래 같은 ID·본문의 재요청에는 같은 페이지를 반환합니다. 다른 본문이나 삭제된 페이지의 ID 재사용은 `409 PAGE_CREATION_CONFLICT`로 거부합니다. 별도 테이블·컬럼은 추가하지 않습니다.
- 클라이언트는 요청 본문을 기기에 보관하고, 응답 유실 시 목록에서 먼저 결과를 찾습니다. 결과가 없으면 같은 ID·본문으로 기존 생성 API를 재시도할 수 있습니다. 페이지 복제 시에는 원본의 생성 요청 ID를 복제본 설정에서 제외합니다.


### 페이지 순서 변경 연결

- 기존 `PATCH /api/v1/diaries/{diaryId}/pages/order`에 활성 페이지 ID 전체를 전달합니다. 새 API·테이블·컬럼은 추가하지 않습니다.
- 회원 편집기의 단일 페이지 이동과 여러 페이지 묶음 이동을 모두 연결합니다. 비회원 문서는 기존 기기 이동 방식을 유지합니다.
- 이동 직전에 기존 목록 API로 최신 ID를 읽고, 사용자가 선택한 페이지를 기준 페이지의 앞·뒤로 옮깁니다. 다른 사람이 추가한 페이지를 빠뜨린 예전 목록을 그대로 보내지 않습니다.
- 조회 이후 동시 추가·삭제·정렬로 요청이 거절되면 최신 목록으로 한 번 재계산합니다. 이동 대상·기준 페이지가 사라졌으면 임의의 위치를 추측하지 않고 목록을 갱신합니다.
- 서버가 저장한 순서는 기존 PAGES_CHANGED 알림 및 목록 조회로 양쪽에 적용합니다. 현재 선택한 페이지 UUID와 페이지의 필기·사진 객체는 유지하며, 페이지 순서를 기기 undo만으로 바꾸지 않습니다.


### 필수 안정화 범위

- 회전·도형 테두리·색상 팔레트 및 HEX 입력이 끝나면 편집 종료를 전달해 다음 조작 없이 전송합니다. 팔레트가 중단되거나 닫혀도 화면에 적용된 값을 전송 대기열에 남깁니다.
- 회원 문서의 서버 미연결 초기화 버튼은 보류하며, reducer에서도 임의 페이지 UUID 생성으로 처리하지 않습니다. 비회원 기기 초기화는 유지합니다.
- 서버 페이지 삭제 확인에는 기기 undo로 복구 가능하다는 안내를 표시하지 않습니다.
- 보고 있지 않은 기존 페이지의 변경 알림도 기존 캔버스 API로 읽어 썸네일·전체 문서 내용을 갱신합니다. 현재 선택 페이지는 유지합니다.
- 속지 색·스터디 플래너·인덱스 공유, 사진 파일 공유 및 커서 표시는 이번 필수 안정화에 추가하지 않습니다.


### 연결 및 작업 큐 안정화

- dev/prod의 `forward-headers-strategy: native`와 필수 `AUTH_TRUSTED_PROXY_REGEX`를 WebSocket 핸드셰이크에도 적용합니다. Nginx가 전달 헤더를 실제 연결 주소로 덮어쓰고, 신뢰 프록시를 통과한 요청만 Tomcat이 변환합니다. 앱은 임의의 X-Forwarded-For를 직접 신뢰하지 않습니다. 실제 배포 대역 설정과 클라이언트 IP 분리는 배포 환경에서도 확인해야 합니다.
- JWT 서명 검증은 AUTH/재인증 때 수행하고 연결에는 만료 시각만 보관합니다. 이벤트 전파와 5초 점검은 같은 다이어리·사용자의 권한 조회를 한 번씩 공유합니다. 권한 결과는 해당 순회 안에서만 사용하므로 다음 전파 때 강퇴·탈퇴를 다시 확인합니다.
- 1008 종료는 기존 인증 갱신 API를 이용해 재접속합니다. READY 없이 연속 거절되면 두 번까지만 재시도합니다. 정상 READY 이후에는 다음 만료에 대한 복구를 다시 허용합니다.
- 확정적인 400/403/404/405/410/413/415/422 거절은 작업 본문·전후 상태와 오류 코드를 기기의 rejectedEdits에 보관하고 전송 큐에서 제외합니다. 입력 거절은 다음 작업을 진행하고 화면에 보관 안내를 표시합니다. 권한 상실·페이지 삭제는 현재 전송을 중단하며 남은 작업은 유지합니다. 네트워크·408·429·5xx는 같은 작업 ID로 재시도합니다.
- 스냅샷은 페이지와 요소 ID 목록으로 일괄 조회합니다(문장당 최대 500개). 누락된 ID는 기존과 같이 null로 보존합니다. 서버 실행 취소 스냅샷은 사용자·페이지별 최신 80개를 보관합니다. 오래된 행은 새 작업 저장 시 최대 80개씩 스냅샷을 비우며 명령 식별자는 유지합니다.
- 기존 페이지 설정 수정 API도 커밋 후 PAGES_CHANGED를 발행합니다. 상대 기기는 기존 페이지 조회 API로 갱신합니다.
- API 경로·테이블·컬럼 추가 없음. H2/PostgreSQL 복원 SQL 분기는 이번 변경에서 유지합니다.


### 요소 삭제 경합·세션 폐기·전송 및 이력 보완

- `404 CANVAS_ELEMENT_NOT_FOUND`는 확정 폐기하지 않고 409와 같이 작업 ID를 바꿔 재구성합니다. 다음 조회의 최신 base에서 사라진 요소만 제외하고 같은 묶음의 다른 요소 변경은 전송합니다. `PAGE_NOT_FOUND`와 권한 상실은 기존 보관·중단 정책을 유지합니다.
- AUTH 때 검증한 세션 UUID를 연결에 보관합니다. 이벤트 전파 및 5초 점검에서 기존 refresh_tokens의 세션 만료·폐기 및 사용자 활성 상태를 확인합니다. 같은 세션의 여러 연결은 순회 안에서 조회를 공유하며, 다른 기기의 활성 세션은 유지합니다. JWT 원문은 저장하지 않습니다.
- 이벤트 처리와 소켓 쓰기는 별도 executor를 사용합니다. 연결마다 최대 32개 대기 프레임, 전송 스레드 8개·전체 대기 작업 512개로 제한하고 연결별 FIFO 순서를 유지합니다. 느린 쓰기는 주기 점검에서도 확인하며 과부하 연결은 종료합니다. 이벤트/전송 드롭 누적 횟수를 경고 로그에 기록합니다. 전 연결이 느린 상황에서는 기존 HTTP 재조회가 복구 수단입니다.
- 최초 after에는 elements만 저장하고 expected가 없으면 elements를 충돌 기준으로 읽습니다. undo/redo 후에는 변경된 expected를 기록하며 이전 expected 포함 이력도 계속 읽습니다.
- 사용자·페이지별 최신 80개 작업에 상세 스냅샷을 유지합니다(기존 편집기 80단계 이력과 일치). 오래된 작업은 `COLLAB_PRUNED_V1`/`EXPIRED`로 표시하고 before/after/expected 요소 본문만 제거합니다. 원본 캔버스·다른 사용자 이력은 수정하지 않습니다. clientOperationId 및 요청 해시 등 작은 메타데이터는 중복 실행 방지를 위해 남기며, 정리된 명령의 재요청은 409로 거부합니다. 별도 메타데이터 행 삭제 정책은 도입하지 않습니다.
- 페이지 생성 재시도는 기존 templateConfig의 요청 UUID를 DB에서 후보 필터링한 뒤 정확한 필드를 확인합니다. 삭제된 요청도 확인해 같은 ID로 새 페이지를 만들지 않습니다. 전체 JSON을 앱에 적재·파싱하지 않지만, 새 인덱스가 없으므로 DB의 JSON 텍스트 검색 비용까지 없애는 것은 아닙니다. JSON 숫자는 값으로 비교하여 1024와 1024.0을 동일하게 처리합니다.
- 다이어리→페이지 쓰기 잠금, 기존 API 경로, 테이블·컬럼은 유지합니다.


### 오류 코드·연결 정원·요소 순서 보완

- 공동 편집 컨트롤러의 요소 부재는 `CANVAS_ELEMENT_NOT_FOUND`, 페이지 부재는 `PAGE_NOT_FOUND`, 다이어리 부재는 `DIARY_NOT_FOUND`로 구분합니다. 요소 삭제 경합만 재구성 대상이며 페이지·다이어리 삭제를 요소 삭제로 재시도하지 않습니다.
- 전역 연결 정원 512개가 찬 경우 WebSocket 1013(Try Again Later)으로 종료합니다. 클라이언트는 기존 지수 백오프(최대 30초 간격)로 재연결하며 강제 토큰 갱신이나 1008의 두 번 제한을 적용하지 않습니다. 미인증 IP당 4개와 인증 사용자당 8개 제한은 기존 정책을 유지합니다.
- 기존 update DTO·서비스의 sortKey 저장 경로는 유지합니다. 클라이언트 순서 변경은 서버의 기존 공유 요소 sortKey 슬롯을 재배치하며 사진 등 비공유 요소는 업데이트하지 않습니다. 구형 데이터에 중복 키가 있으면 전체 응답의 비공유 요소 키까지 고려한 최상위 여유 슬롯으로 공유 요소만 재배치합니다. 생성 요소도 비공유 요소를 포함한 최댓값 뒤에 배치합니다.
- 비공유 요소는 파일 공유 대상으로 바꾸지 않습니다. 서버 응답에서는 순서값만 별도로 기억하고 기기 저널에 저장하며, 원격 미디어 본문이나 파일을 새 API로 전송하지 않습니다.
- 순서 변경 후 기존 페이지 조회 및 세션 재시작에서도 순서가 유지되는지, 다른 멤버도 같은 순서를 읽는지 검증합니다. 새 API·테이블·컬럼은 없습니다.


### 미인증 연결 방어 및 누적 정리 검증

- JWT 서명·세션 검증 이후에도 sid가 없거나 정규 UUID 형식이 아니면 명시적으로 1008로 종료합니다. 토큰 원문이나 클레임 값을 로그에 남기지 않습니다.
- 전체 512개 정원과 별개로 미인증 연결은 최대 64개까지만 대기시킵니다. 미인증 대기 한도도 1013으로 안내해 백오프 재접속을 유지합니다. 인증 성공 시 대기 슬롯을 반환하며, 5초 이상 미인증 상태인 연결은 1초 간격 검사와 신규 연결 수락 시 정리합니다. 기존 인증 연결은 이 정리로 종료하지 않습니다.
- 이 제한은 미인증 연결의 점유 시간과 수를 줄이는 조치이며, 신규 연결을 항상 보장하거나 분산 공격을 완전히 방어하는 것은 아닙니다. 기존 신뢰 프록시·IP별 제한은 유지합니다.
- 이력 정리는 여전히 미정리 V1 형식만 조회합니다. 300개 누적 이력이 있어도 후속 저장에서 배치 정리를 따라잡고 최신 80개만 남기는지 테스트합니다. 정리 조건·테이블·컬럼·API는 변경하지 않습니다.


### 검증 장애·프레임 제한·권한 확인 순서

- 캔버스 이벤트, 페이지 목록 이벤트, 정기 점검에서 JWT 만료·세션 폐기·멤버 권한 상실은 1008로 종료합니다. DB 등 인프라 예외는 1011로 종료하고 예외 종류만 경고 로그에 기록합니다. 클라이언트는 1011에서 강제 토큰 갱신이나 인증 실패 재시도 횟수를 소진하지 않고 기존 백오프로 재연결합니다. 검증에 실패한 상태로 알림을 보내지는 않습니다.
- AUTH와 PING의 요청 예산을 분리합니다. AUTH는 연결당 10초에 최대 4회, PING은 초당 최대 1회입니다. AUTH 직후 첫 PING 및 PING 직후 재인증 AUTH는 허용합니다. 과도한 동일 종류 프레임과 미인증 PING은 1008로 거절합니다. 기간 계산은 단조 시계를 사용합니다. 현재 클라이언트의 15초 heartbeat는 변경하지 않습니다.
- 레거시 batch와 공동 편집 batchTracked는 서비스 진입 시 쓰기 권한을 먼저 확인한 뒤 생성 ID 보정·중복 ID 검증을 수행합니다. 다이어리·페이지 잠금 후의 권한 재확인은 유지합니다. MVC의 JSON·Bean Validation 등 서비스 진입 이전의 400 처리는 그대로입니다.
- 새 API·테이블·컬럼·클라이언트 화면 추가 없음.

잘못된 JSON 또는 객체가 아닌 WebSocket 프레임은 1008로 종료한다. 파싱 이외의 서버·저장소 장애는 기존 1011 처리를 유지한다.

## 기존 에셋 API를 통한 이미지 연결 (2026-10-30)

새 API·테이블·컬럼·화면은 추가하지 않는다. 기존 POST /api/v1/media(multipart file, libraryCategory)와 GET /api/v1/media/{mediaFileId}/file을 사용한다. 기존 canvas-operations·요소 API의 mediaFileId와 propertiesJson.cells의 미디어 ID를 검증하고 저장한다. 개인 보관함 목록·메타 조회·원본 삭제의 소유자 제한은 유지하고 파일 조회만 활성 캔버스를 읽을 수 있는 해당 다이어리 소유자·편집자에게 허용한다. 비참여자·강퇴·나간 계정은 공유 파일을 조회할 수 없으며, 미디어 ID를 알더라도 남의 비공개 이미지를 첨부할 수 없다.

프론트는 기기 사진을 업로드한 뒤 서버 ID로 요청 본문을 확정하여 기기 큐에 저장하고 캔버스 작업을 전송한다. 업로드 매핑과 명령 ID를 유지해 응답 유실 후 재시도한다. 상대 기기는 파일을 백그라운드에서 검증·기기 보관소에 저장한 후 기존 이미지 캐시 구독을 갱신해 표시한다. 느리거나 실패한 파일 하나가 텍스트·다른 요소의 동기화를 막지 않으며 기존 미디어 오류 안내와 재조회 경로를 사용한다. 기기 파일 경로·Blob URL·poster 데이터는 캔버스 요청에 포함하지 않는다. 사진·사용자 스티커·이미지 테이프·여러 칸 사진 틀의 추가·변형·삭제·순서·Undo/Redo에 같은 동기화 경로를 사용한다. 파일 제거는 캔버스 요소 삭제와 분리한다.

서버 에셋 한도는 정지 이미지 5MiB, GIF 15MiB이며 JPEG·PNG·WebP·GIF를 지원한다. HEIC 또는 큰 정지 이미지는 이미 만들어 둔 JPEG/PNG 표시본이 있으면 사용한다. 표시본도 한도를 넘거나 GIF 원본이 15MiB를 넘으면 기기 원본을 유지하고 해당 작업을 보관하며 나머지 동기화를 진행한다. 과거 삭제된 전용 API의 준비 요청은 기존 deferredMedia에 계속 보관하며 임의 재전송하지 않는다.

캔버스의 활성·복원 가능한 요소, 사진 칸 JSON, Undo/Redo 이력에서 참조하는 파일은 원본 삭제 및 정리에서 보호한다. 운영 PostgreSQL은 V22의 GIN 인덱스로 JSON 안의 mediaFileId 값을 검색한다. 본문에 적힌 UUID 문구는 이미지 참조로 취급하지 않으며, 저장 시에는 임의 중첩 객체·배열까지 모든 mediaFileId를 첨부 권한 검증한다. 파일 읽기 권한은 앱이 표시하는 기존 필드와 다이어리 멤버십으로만 판단해 숨은 메타데이터의 읽기 권한을 넓히지 않는다. 로컬 파일 캐시는 계정/다이어리 문서에 서버 ID로 연결되며, 업로드 성공 후 매핑 저장 전 앱이 강제 종료되는 경우 기존 비멱등 업로드 API 특성상 미참조 업로드가 남을 수 있다. 이 경우 캔버스 요청은 아직 전송되지 않는다.

실제 Expo Go 두 기기의 화면·GIF·배포 S3 확인은 수동 검증 대상이다.

### 이미지 참조 조회와 실패 재시도 보완

V22은 기존 canvas_elements와 canvas_history_operations에 표현식 GIN 인덱스 3개만 추가한다. 테이블·컬럼·API는 추가하지 않는다. 사진 칸, 대문자 UUID, Undo/Redo 스냅샷의 mediaFileId를 소문자 배열로 추출한 인덱스와 같은 @> 조건을 사용한다. 파일 조회·첨부·삭제, 탈퇴, 물리 정리에서 PostgreSQL의 전체 JSON LIKE 검색을 제거한다. H2 테스트 호환 경로만 문자열 검색을 유지하며 DB 종류는 컴포넌트 초기화 시 한 번 확인한다. 정리 배치 크기는 설정값이 크더라도 1~100으로 제한하고 기존 최대 5페이지 커서를 유지한다.

기본 PostgreSQL 회귀는 요소 10,000개와 이력 10,000개를 추가해 정리 결과 집합을 검증한다. 특정 실행 계획·인덱스 선택이나 실행 시간은 기본 CI의 성공 조건으로 삼지 않는다. DIO_MEDIA_EXPLAIN_QA=true를 지정한 선택 진단만 트랜잭션 안에서 SET LOCAL enable_seqscan=off로 인덱스 사용 가능성을 확인하고 backend/build/media-reference-explain.txt를 기록한다. 설정은 진단 트랜잭션 종료 시 복구하며, 진단 결과가 운영 비용 기반 플래너 선택이나 실서비스 부하 시험을 대신하지 않는다.

다운로드의 일시 오류(네트워크·5xx·408·429)는 실패 후 5초, 15초, 60초 간격으로 다음 조회에서 재시도하며 자동 시도는 최초 포함 최대 4회다. 4xx(408·429 제외), 손상/지원 불가 이미지, 저장 공간 부족은 자동 재시도를 멈춘다. 다른 이미지와 캔버스 편집은 계속 진행한다. 기존 ‘이미지 다시 조회’ 버튼만 실패 상태를 초기화해 즉시 한 번 더 시도한다. 일반 렌더링의 resolveDisplay는 이 제한을 초기화하지 않는다. 재시도 상태는 해당 편집 세션의 메모리에만 보관하고 화면 종료 시 등록한 재조회 연결도 해제한다. 버튼·문구·스타일이나 프로필 UI는 변경하지 않는다.

### V22 호환성·배포 인덱스 생성

이미 적용됐을 수 있는 V22 SQL과 체크섬은 변경하지 않는다. Spring Boot의 MediaIndexMigrationConfiguration이 Flyway migrate 호출 전에 MediaIndexPreparation을 실행한다. 기존 테이블이 있는 PostgreSQL은 별도 auto-commit 연결에서 누락된 V22 인덱스를 CREATE INDEX CONCURRENTLY로 먼저 생성한다. 완료 후 기존 V22의 IF NOT EXISTS는 생성 작업을 건너뛴다. 이미 적용된 유효한 인덱스도 다시 만들지 않는다. 여러 서버의 준비 작업은 이 기능 전용 세션 advisory lock으로 직렬화하며 캔버스 DML을 잠그지 않는다. 중단된 동시 생성으로 남은 무효 인덱스는 해당 테이블의 예약된 이름에 한해서 DROP INDEX CONCURRENTLY 후 재시도한다.

테이블 자체가 아직 없는 새 DB는 준비 작업을 건너뛰며, 기존 Flyway가 빈 테이블에 V22을 적용한다. CONCURRENTLY는 Flyway 트랜잭션 내부가 아닌 전용 연결에서 실행하므로 V22의 executeInTransaction 설정이나 과거 SQL 수정·repair가 필요 없다. 기존 쓰기 트랜잭션을 기다릴 수는 있지만 새 캔버스 쓰기는 막지 않는지 PostgreSQL 동시성 테스트로 확인한다. 운영에서 Spring Boot를 거치지 않고 Flyway를 직접 실행한다면 같은 준비 단계를 먼저 실행해야 한다.

중첩 참조 검증은 생성과 수정의 propertiesJson 전체에서 mediaFileId를 수집해 권한을 확인한다. 다른 사용자 파일을 x.mediaFileId나 배열 안에 숨겨 삭제 보호를 유발하는 요청은 404로 거절하며 요소·이력에 남기지 않는다. UUID를 언급한 일반 텍스트는 참조로 취급하지 않는다. 기존 저장 JSON을 임의로 삭제하거나 파일 읽기 범위를 확장하지 않는다.

### 미디어 검증·기동 보완

- 요소 하나의 이미지 참조는 기본 `mediaFileId`를 포함해 서로 다른 UUID 최대 64개다. 중첩 JSON 전체를 검증하며 초과 시 미디어 조회·행 잠금 전에 400으로 거절한다. 같은 ID의 반복은 한 개로 센다.
- 물리 삭제 쿼리는 PostgreSQL 전용이다. H2에서는 미디어 만료 정리 스케줄을 켜도 실행을 건너뛴다. 물리 삭제 검증은 전용 PostgreSQL 테스트로 수행한다.
- 인덱스 사전 생성은 조건부 `FlywayMigrationStrategy`가 아니라 `BEFORE_MIGRATE` 콜백으로 등록한다. 다른 전략에서도 설정된 Flyway의 `migrate()`를 호출하면 먼저 실행되며 기존 V22 SQL·체크섬은 유지한다.

- 최신 develop의 V21 초대 알림 마이그레이션과 번호가 겹쳐 인덱스 SQL은 내용 변경 없이 V22로 이동했다. 이 기능 브랜치의 이전 V21을 직접 적용한 개인 테스트 DB는 버전 이력이 최신 develop과 달라 자동 업그레이드 대상으로 보지 않는다. 백업 후 전용 테스트 DB를 새로 만들거나 담당자와 이력을 확인해야 하며 자동 repair/이력 삭제는 하지 않는다. develop의 V21은 수정하지 않는다.


### WebSocket handshake 403 운영 점검

Android native의 REST 성공과 WebSocket Origin 허용은 별도다. 개발 서버 외부 Origin은 `https://k15f106.p.ssafy.io:8443`이며, 배포 `AUTH_ALLOWED_ORIGINS`에 정확한 외부 포트를 포함한다. Nginx `/ws/`는 `Host $http_host`와 고정 `X-Forwarded-Port`(dev 8443/prod 443)로 외부 포트를 보존하며, Tomcat은 신뢰 프록시에서만 포트 헤더를 읽는다. HTTP 101 이전의 401/403과 연결 후 회원 인증 실패 1008을 구분한다. 비공개 env 갱신·컨테이너 재생성과 101→AUTH→READY 확인 절차는 [인증 배포 문서](../infra/auth-deployment.md)의 Android Expo Go WebSocket Origin 점검을 따른다.
