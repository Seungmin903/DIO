# PDF 내보내기 계약 (S15P31F106-108)

> 기준일: 2026-10-20 · 확인한 develop: `1706b2e` (88번 기본 펜 병합 포함)
> 상태: 구현용 계약 초안. 이 문서는 PDF 기능의 구현·실기기 검증 완료를 뜻하지 않는다.

## 1. 범위와 기존 계약

MVP1의 로컬 문서를 이미지 기반 PDF 한 파일로 내보낸다. 기존 PNG의 전용 렌더러와 미디어 준비를 공통화하며 서버 API·로그인·업로드·저장 스키마 변경은 추가하지 않는다.

- 기존 계약 작업: [56](https://ssafy.atlassian.net/browse/S15P31F106-56). 해당 초안은 별도 로컬 작업으로, develop에 병합된 계약으로 간주하지 않는다.
- 구현 기준: [페이지 렌더러](./page-export-renderer.md), [GIF 첫 프레임](./gif-first-frame-export.md), [PNG 저장](./png-file-export.md).
- 기준 문서의 책임: 56번은 이미지 저장·조회와 공통 연동 계약, 기존 PNG 구현 문서는 공통 렌더링·PNG 저장, 이 문서는 PDF 고유 정책의 기준이다. 56번의 PDF 관련 제안과 충돌하면 이 문서를 따른다. 56번의 나머지 계약은 흡수하거나 완료로 처리하지 않는다.
- PDF는 보관·일반 인쇄를 고려해 기본 2배로 정한다. 기존 PNG의 기본 1배 동작은 변경하지 않는다.
- 검색·선택 가능한 텍스트, 벡터 필기, PDF 가져오기, 암호화, 움직이는 PDF, 사용자용 JPEG 파일 출력, 서버 보관은 범위 밖이다.
- 라이브러리 및 플랫폼 API 선택은 109·110·112에서 설치된 Expo 환경과 호환성을 확인하고 결정한다. 아래 함수명·오류는 신규 제안이며 현재 존재하는 API라는 뜻이 아니다.

## 2. 사용자 정책과 기본값

| 항목 | 계약 |
| --- | --- |
| 형식 | PNG 또는 PDF. 기존 PNG는 현재 페이지 한 장을 유지 |
| PDF 범위 | 현재 페이지 / 페이지 개별 선택 / 연속 페이지 범위. 전체 페이지는 개별 선택 화면의 전체 선택으로 제공 |
| 순서 | 시작 시점 문서의 페이지 배열 순서. ID·생성 시각으로 재정렬하지 않음 |
| 포함 | 빈 페이지 포함, 문서 페이지 한 장당 PDF 한 면. 표지는 문서의 실제 페이지일 때만 포함 |
| PDF 크기 | A4 가로 297×210mm (약 841.89×595.28pt). 논리 좌표와 물리 크기를 분리하고 비율 유지 contain 배치·중앙 정렬. 임의 자르기·늘이기·두 쪽 합치기 없음 |
| 배율 | PDF 기본 2배. 초기 UI에는 배율 선택 없음. 현재 논리 규격 1188×840 → 2376×1680px. 기존 PNG 파일 출력 기본값은 1배 유지 |
| 페이지별 상한 | 긴 변 4096px 및 총 8,000,000px; 기존 PNG와 동일한 비율 유지 축소 산식 적용 |
| 배경 | 현재 구현대로 불투명 흰색. 실제 내지/종이색 구현 시 PNG와 공유하는 배경 렌더러로 함께 확장 |
| 편집 요소 | 사진·스티커·테이프의 위치·크기·회전·자르기·반전 등 공통 렌더러가 지원하는 변형·투명도 및 배열의 뒤→앞 순서 |
| 제외 | 숨김/투명도 0 요소, 선택 표시, 보조 격자, 참여자 커서, 도구·패널 |
| GIF | 원본 0번 프레임을 PNG로 변환한 결과. 재생 시점 무관, 원본 보존 |
| 제한 | 최대 20페이지, 모든 페이지의 출력 픽셀 합계 80,000,000px, PDF 삽입용 인코딩 이미지의 누적 바이트 및 최종 PDF 각각 50MiB 이하 |
| 시간 | 페이지별 준비·로드·캡처 30초, 전체 생성 180초. OS 저장/공유 대기 시간은 제외 |

1MiB는 1,048,576바이트다. 위 제한은 실기기 측정 전의 초기 보호값이며 성능 보장값이 아니다. 113번에서 생성 시간·실패율·측정 가능한 메모리를 기록해 조정한다. 순차 처리라도 PDF 조립기 내부 이미지와 직렬화 버퍼가 누적되므로, 파일 크기 제한을 메모리 사용 상한으로 설명하지 않는다.

이전1188×840의2배 출력은 한 장3,991,680px,20장79,833,600px다. 현재1280×800의2배는 한 장4,096,000px이며19장77,824,000px는 예산 안,20장81,920,000px는80MP를 초과한다. 최대20장은 개수 상한이며 실제 선택 가능 수는 픽셀 예산에 따라 더 적을 수 있다. 큰 규격은 20장 미만이어도 합계 예산을 초과할 수 있다. 사전 검사에서 페이지 수·규격·픽셀 합계를 확인하고, 각 페이지의 삽입용 이미지 인코딩 뒤 누적 바이트, 직렬화 뒤 최종 PDF 바이트를 확인한다. 중간 캡처 PNG의 누적 생성량은 이 한도에 합산하지 않고 현재 처리 중인 한 장만 유지한다. 상한 초과는 배율 자동 저하·일부 페이지 저장 대신 중단하고 현재 페이지 출력이나 문서 분할을 안내한다.

### 물리 크기와 이미지 밀도

PDF의 A4 크기는 1배/2배와 무관하게 고정하며 배율은 삽입 이미지의 픽셀 밀도만 바꾼다. 배치 배율은 `min(pdfWidthPt / logicalWidth, pdfHeightPt / logicalHeight)`이고 남는 공간은 종이 배경색으로 채운다. 현재 1188:840은 A4와 거의 같아 작은 여백만 생긴다. PDF 좌표계 차이에 따른 상하 반전 없이 페이지 전체를 넣는다.

2배의 2376×1680px는 A4에서 약 203dpi다. 화면 보관·일반 인쇄의 기본값이며 고품질 300dpi 인쇄를 보장하지 않는다. 입력 사진·기본 스티커 해상도가 낮으면 2배 출력도 디테일을 복원하지 못한다. 고해상도 캡처가 필요한 픽셀을 실제로 만드는지도 네이티브 실기기에서 확인한다.

## 3. 입력과 스냅샷

제안하는 입력 경계:

```js
// 화면 상태/저장소를 다시 읽지 않고 전달받은 최신 메모리 문서만 사용한다.
createPdfExportSnapshot(doc, {
  scope: 'pages', // 'current' | 'pages' | 'range'
  selectedPageIds, // pages: 전체 선택 또는 사용자가 고른 ID 배열
  range: { start: 2, end: 6 }, // range: 현재 문서 기준 1부터, 양끝 포함
  currentPageId,
  width, height, // 실제 캔버스 논리 규격: 필수
  title,
  now, // 파일명 재현/테스트를 위한 Date 주입
})
// -> { jobId, scope, fileName, pages: [
//   { documentPageNumber: 1, ...createExportSnapshot(page, { width, height, scale: 2 }) }
// ] }
```

- 사용자가 만들기를 누르면 편집기 담당의 입력 확정 경계를 거쳐 진행 중인 필기/텍스트를 문서에 확정한다. 확정이 불가능하면 시작을 중단하며 미확정 입력을 조용히 누락하지 않는다. 72번 연결 시 이 경계를 함께 확인한다.
- 같은 동기 실행 구간에서 대상 목록·순서·페이지 내용·제목·규격·시각을 깊게 복사한다. 선택 모드는 다음과 같다: current는 존재하는 currentPageId 한 개, pages는 비어 있지 않은 중복 없는 selectedPageIds, range는 문서 안의 정수 start/end(양끝 포함, start<=end)를 요구한다. 대상이0장인 요청은 오류다. 일부 페이지 ID가 중복되거나 규격이 잘못된 문서도 시작하지 않는다.
- 생성 호출자는 캔버스의 실제 width/height를 전달한다. 최신 develop의 편집기는1280×800이며1188×840은 이전 규격/기존 함수 생략 기본값이다. PDF 스냅샷 API는 규격을 생략할 수 없다. 임의 DB/API 필드를 만들지 않는다.
- 생성 중 편집·페이지 이동·정렬·자동 저장이 발생해도 스냅샷은 바뀌지 않는다. 재생성은 같은 스냅샷, 최신 편집 반영은 닫고 새로 내보내기다.
- 스냅샷이 참조하는 미디어는 작업 동안 유지한다. 명시적 원본 삭제/GC가 도입되면 해당 ID를 보호하는 수명 계약을 연결해야 한다. 조회 실패 시 출력은 중단한다.

## 4. 생성 파이프라인과 자원 소유권

```text
공유 → 네 가지 내보내기 옵션 → 페이지/영역 선택 → 파일 형식 → 입력 확정·대상 스냅샷 → 한도/지원 요소 사전 검사
→ [한 페이지 준비 → 전용 영역 렌더링·로드 대기 → PNG 캡처
   → 종이 배경에 RGB 합성·삽입용 인코딩 → PDF 면 삽입 완료 → 해당 이미지·준비 자원 해제] × N
→ PDF 직렬화·최종 용량 검사 → 저장 가능 상태 → 파일 저장/공유
```

109번은 PageExportPreview의 렌더링·로드 대기·캡처를 UI에서 분리한다. React 전용 surface의 마운트와 플랫폼별 캡처는 유지한다. DOM/화면 스크린샷으로 대체하지 않는다.

```js
renderPageImage(snapshot, { signal })
// -> { uri, blob?, width, height, dispose() }

generatePdf(snapshot, { renderPageImage, signal, onProgress })
// -> { uri, blob?, byteLength, pageCount, fileName,
//      mimeType: 'application/pdf', dispose() }
// progress -> { phase: 'rendering' | 'assembling', completedPages, totalPages }

savePdfFile(result, { fileName })
// -> { status: 'saved' | 'download-started' | 'share-finished' | 'cancelled',
//      destination: 'files' | 'download' | 'share', fileName }
```

- 한 번에 한 페이지의 준비·렌더링·캡처만 실행한다. PDF 면 삽입이 끝나야 다음 페이지를 시작한다.
- 페이지 작업이 준비 자원을 소유하고, 최상위 작업이 조립기 및 최종 PDF 결과를 소유한다.
- 공통 렌더러는 소재 로드와 레이아웃 완료 후 캡처한다. 요소의 onError와 지원하지 않는 요소는 전체 실패다. 기존 해상도 선택 및 GIF 디코딩 제한은 완화하지 않는다.
- GIF/같은 이미지 중복 변환 회피는 페이지 내부에서 기존 방식을 유지한다. 전체 문서의 디코딩 결과를 무제한 캐시하지 않는다.
- PDF 조립기가 삽입용 이미지를 복사하거나 소비했다는 보장이 생긴 뒤 dispose한다. 지연 참조만 지원하면 페이지 임시 파일을 작업 끝까지 유지하고 원시 픽셀/표시 URL은 순차 해제한다. 선택한 라이브러리의 소유권을 110번에서 검증한다.
- 준비 자원·surface·PNG·PDF 최종 파일의 소유자를 구분한다. 취소/오류/닫기/새 시도 시 해당 작업 소유 자원만 해제하며 문서·원본·다른 작업의 캐시는 삭제하지 않는다.
- 취소할 수 없는 네이티브 캡처/조립이 늦게 완료되면 결과를 정리하고 jobId가 바뀐 UI에 반영하지 않는다. dispose는 여러 번 호출해도 안전해야 한다.

### PDF 내부 이미지 압축과 알파

- 사용자에게 JPEG 파일을 주는 기능은 범위 밖이지만 **PDF 내부 JPEG 압축은 허용**한다. JPEG가 사용자 선택 형식으로 추가되는 것은 아니다.
- 공통 캡처는 PNG를 유지한다. PDF 삽입 전 페이지 전체를 종이 배경색에 합성하고 최종 삽입 데이터는 알파 채널 없는 불투명 RGB로 인코딩한다. 불투명 RGBA를 그대로 넣는 방식으로 대체하지 않는다.
- 기본은 무손실 RGB PNG다. 사진이 포함된 페이지는 JPEG 품질 0.92를 초기 후보로 두고 110번에서 글씨·스티커 경계·사진 화질과 용량을 비교한다. 품질 판정 기준을 검증하기 전에는 무손실 경로를 유지한다. 무손실만으로 한도를 넘으면 조용히 압축 품질을 낮추지 않고 중단한다.
- 110번은 RGB 인코딩 경로와 조립기에서 불필요한 알파 마스크(`/SMask`)가 생성되지 않는지 확인한다. 페이지 배경 합성 후에도 내부 이미지의 알파가 남는 라이브러리 경로는 사용하지 않는다.
- 한도는 실제 PDF 삽입용 인코딩 바이트의 합계에 적용한다. PNG/JPEG 선택은 PDF 물리 크기·페이지 순서·원본 파일을 변경하지 않는다.

## 5. 상태와 실패 처리

```text
idle → preparing → rendering(i/N) → assembling → ready → saving
생성 중: cancelled / error → 같은 스냅샷으로 다시 만들기
저장 후: saved / download-started / share-finished / cancelled / error
저장 실패·취소: ready 결과를 유지 → 다시 저장
```

- 생성 중에는 취소를 제공하고 중복 시작을 막는다. 저장/공유의 OS 작업이 진행 중이면 이중 실행과 앱 내 닫기를 막는다. OS 자체 취소는 허용한다.
- 사전 검사에서 지원하지 않는 요소가 하나라도 있으면 페이지 번호를 안내하고 시작하지 않는다. 생성 중 페이지 하나라도 필수 소재/폰트/로드/캡처/조립에 실패하면 부분 PDF를 저장하지 않는다.
- 오류는 `{ code, phase, documentPageNumber?, cause? }`를 보존한다. 사용자에게 내부 경로/스택을 노출하지 않는다.

| 신규 제안 코드 | 처리 |
| --- | --- |
| EXPORT_PDF_INPUT_INVALID | 페이지/범위/규격을 확인하도록 안내 |
| EXPORT_PDF_LIMIT_EXCEEDED | 페이지/픽셀/용량 중 초과 항목과 제한 안내 |
| EXPORT_PDF_TIMEOUT | 해당 페이지 또는 전체 생성 시간 초과, 다시 만들기 |
| EXPORT_PDF_ASSEMBLY_FAILED | PDF 조립 실패, 다시 만들기 |
| EXPORT_PDF_SAVE_FAILED | 파일 저장 실패, 다시 저장 |
| EXPORT_PDF_SHARE_UNAVAILABLE | 공유 불가, 지원 가능한 파일 저장 경로 안내; 없으면 지원 불가 명시 |

기존 EXPORT_MEDIA_FAILED, EXPORT_MEDIA_MISSING, EXPORT_ELEMENT_UNSUPPORTED, EXPORT_GIF_DECODE_FAILED, EXPORT_GIF_TOO_LARGE, EXPORT_RASTER_TOO_LARGE 등은 원인 코드를 유지하고 PDF 단계/페이지 번호를 덧붙인다. 취소는 오류 코드로 만들지 않는다. 공간 부족은 식별 가능한 경우에만 따로 안내하며 모든 오류를 공간 부족으로 추정하지 않는다.

## 6. 파일명·웹·모바일 저장

- 현재 페이지: `DIO_<제목>_p01_<YYYYMMDD_HHMMSS_mmm>.pdf` (p01은 문서 내 1부터 시작하는 번호, 최소 두 자리).
- 전체 선택: `DIO_<제목>_all_<YYYYMMDD_HHMMSS_mmm>.pdf`.
- 일부 개별 선택: `DIO_<제목>_selected03_<YYYYMMDD_HHMMSS_mmm>.pdf` (03은 선택 개수).
- 연속 범위: `DIO_<제목>_p02-p06_<YYYYMMDD_HHMMSS_mmm>.pdf`.
- 같은 페이지 집합이어도 진입 모드의 파일명 접미사를 유지한다. 단 pages에서 전부 고른 경우는 all을 사용한다.
- PNG와 같은 제목 정규화(경로/제어문자 제거, 48자 제한, 빈 제목 대체값)와 기기 현지 시각을 사용한다. 이름은 스냅샷 생성 시 고정하고 재시도에서도 유지한다. OS가 최종 이름/중복 처리 방식을 바꿀 수 있다.
- 웹 저장 버튼의 동기 클릭 구간에서 파일 선택기를 호출한다. PDF는 미리 생성된 ready 결과만 넘기고 write/close 완료 시 saved로 안내한다. 파일 대화상자 취소는 cancelled다.
- 웹 미지원 환경은 Blob 다운로드 후 download-started로 안내한다. 완료/취소를 확인할 수 없으므로 저장 완료로 표시하지 않는다. 다운로드용 URL은 별도 소유하고 기존 PNG와 같은 60초 유예 후 해제한다.
- 모바일 기본 버튼은 **PDF 파일 저장·공유**다. MIME은 application/pdf, UTI가 필요한 경우 PDF 식별자를 사용한다. 준비한 캐시 파일로 OS 공유 시트를 열고 iOS의 파일에 저장 등 OS 제공 대상을 이용한다. 앱이 별도 폴더 선택기를 강제하지 않는다.
- 공유 API가 반환됐다는 이유로 최종 파일 저장/상대 앱 전달 성공을 단정하지 않는다. 확인 가능한 취소는 cancelled, 최종 결과가 불명확하면 share-finished와 “공유 창을 닫았어요. 선택한 앱에서 결과를 확인해 주세요”로 안내한다. 파일 쓰기 완료를 실제로 확인하는 경로만 saved로 표시한다.
- 모바일 공유 동안 캐시 파일을 유지한다. OS 소비 완료를 API가 보장하지 않으면 공유 반환 직후 삭제하지 않고 전용 폴더에 24시간 유예한다. 앱 시작/다음 작업 때 활성 작업을 제외한 24시간 초과 파일만 정리한다. 앱 강제 종료 시 남은 파일도 같은 방식이다. 원본/PNG 캐시와 폴더를 분리한다.
- 형식별 버튼을 명확히 구분한다: PNG는 **사진첩에 저장**(74번에서 이미 구현), PDF는 **PDF 파일 저장·공유**. 같은 메뉴 구조와 진행/실패 안내는 공유하되 서로 다른 OS 목적지에 맞춘다. PNG가 폴더 선택기를 사용한다는 이전 리뷰 전제는 현재 구현과 다르다.
- PDF에 사진첩 권한을 요청하거나 PNG 사진첩 API를 사용하지 않는다. 공유 기능의 실기기 지원 여부는 112·113에서 검증한다.

### 메타데이터

- Title: 스냅샷 시점 다이어리 제목. 빈 제목은 파일명과 같은 대체 제목을 사용한다.
- Author: 비움. 사용자 이름·계정·기기명·위치·원본 사진 EXIF를 복사하지 않는다.
- Creator / Producer: `DIO`. 라이브러리 기본값을 그대로 노출하지 않도록 명시적으로 설정한다.
- CreationDate / ModificationDate: 스냅샷의 `now`와 같은 실제 시각. PDF 날짜에는 해당 시각의 UTC 오프셋을 포함하거나 동등한 UTC로 기록한다. 현지 시각 숫자를 UTC로 오인해 저장하지 않는다. 재시도에서는 시각을 유지한다.
- Subject / Keywords: 비움. PDF 열람기에서 제목·날짜·생성 도구를 확인하고 다른 값이 자동으로 삽입되지 않는지 113번에서 검사한다.

## 10. 공유 버튼의 네 가지 내보내기 옵션

| 공유 메뉴 | 선택 단계 | 허용 형식 |
| --- | --- | --- |
| 현재 페이지 내보내기 | 현재 페이지 확인 | PNG(기본) / PDF |
| 페이지 골라 내보내기 | 썸네일 체크박스·전체 선택/전체 해제 | PDF 한 파일 |
| 페이지 범위 내보내기 | 시작/끝 페이지 입력, 양끝 포함 | PDF 한 파일 |
| 영역 선택 내보내기 | 현재 페이지 직사각형 선택·비율 조절 | PNG 한 장 |

공유 → 방식 → 대상 선택 → 형식 → 미리보기·저장 순서다. 형식이 하나뿐이면 고정 형식으로 안내해 불필요한 선택을 줄인다. 공유 메뉴 자체가 OS 공유를 즉시 실행하는 것은 아니다. 여러 PNG·ZIP 저장은 이번 범위에 추가하지 않는다.

- 현재 페이지 진입은 현재 한 장으로 고정한다. 페이지 골라 진입은 처음 현재 페이지만 체크하고 전체 선택을 제공한다. 1개만 선택해도 PDF를 유지한다. 이전 선택은 새 내보내기 진입에 자동 복원하지 않는다.
- 페이지 범위는 현재 페이지~현재 페이지로 초기화하고 1부터 문서 페이지 수 이내 정수만 허용한다. 시작>끝, 빈값, 소수, 범위 초과는 생성 불가로 안내한다. 순서를 자동 뒤집거나 범위를 잘라내지 않는다.
- 선택 개수와 최대20페이지/80MP를 함께 표시한다. 문서가21페이지 이상이거나 전체 출력 픽셀 합계가80MP를 넘으면 전체 선택을 비활성화하고 이유를 표시한다. 일부 페이지 선택은 두 상한 이내에서 계속 허용한다. 문서 전체가21장이라고 개별 선택까지 금지하지 않는다.
- 개별 선택 입력은 중복 ID·존재하지 않는 ID·빈 배열을 오류로 처리한다. 체크 순서와 무관하게 문서 순서로 출력한다. 전체 선택 역시 20페이지/80MP/50MiB 제한을 그대로 적용하며 자동 분할·일부 저장하지 않는다.
- 대상 선택 화면은 문서 페이지 목록이 바뀌면 현재 목록으로 갱신하고 삭제된 선택/범위를 사용자에게 알려 재확정받는다. 생성 확정 시 ID·페이지 번호·내용을 함께 고정하고 이후 문서 변경은 무시한다.
- 오류 문구의 페이지 번호는 출력 순번이 아니라 스냅샷의 문서 페이지 번호다. 진행률은 출력 순번/선택 페이지 수를 사용한다.
- 111번은 공유 버튼·네 진입점·개별/전체/범위 선택·형식/진행 UI를 담당한다. 영역 조작은116·117, 영역 생성/저장은118, PDF 조립은110, PDF 저장은112다. 113은 세 페이지 모드의 PDF를,119는 영역 및 공유 메뉴 복귀를 검증한다.
- 입력은3절의 current/pages/range 계약을 따른다. 물리 크기·2배·압축·RGB·메타데이터·실패 정책은 모든 페이지 선택 모드에 동일하게 적용한다.

## 부록: 과거 계약 검토 이력 (구현 기준은 본문)

- 초기 전체 페이지 기본안은 폐기하고 현재/개별/범위 모드로 정리했다. PDF 2배·A4 가로 contain 배치는 유지한다. PDF 면의 물리 크기와 래스터 이미지 밀도를 분리했다.
- 20페이지를 유지하면서 누적 픽셀 예산을 80MP로 변경했다. 순차 처리·50MiB 제한은 유지하고 용량 합산 대상을 삽입용 인코딩 이미지로 명확히 했다. 메모리 안전성 보장은 아니다.
- 무손실 RGB 우선, 내부 JPEG 후보 및 화질 검증, 알파 마스크 제거를 명시했다. JPEG 파일 다운로드 기능과 구분한다.
- PNG 사진첩/PDF 파일 공유의 목적지 차이, 메타데이터, 56번/PNG/PDF 문서의 책임 경계를 정리했다.
- 문서 정책만 바뀌며 현재 PNG 구현과 저장 데이터에는 영향이 없다. 109~113에서 구현·검증한다.

- 리뷰 반영 중 develop의 88번 병합(`1706b2e`)을 통합했다. 색인 충돌은 두 문서 링크를 보존해 해결했으며 기본 stroke 연결 현황을 갱신했다. 팀원 코드의 동작은 수정하지 않았다.

## 11. 고해상도 소재 정책 (122)

- 필요 픽셀을 충족하는 표시본 → 안전 상한(800만 화소) 이내 원본 → 안전한 표시본 확대 순으로 선택한다.
- 큰 원본에 충분한 표시본이 없더라도, 800만 화소 이하의 표시본이 있으면 이를 확대해 출력을 계속하고 생성 중 및 저장 전 화질 경고를 표시한다. 해상도 복원이나 인쇄 품질 보장을 뜻하지 않는다.
- 표시본이 없거나 손상되었으면 출력은 중단한다. GIF 원본 첫 프레임 제한, 한 페이지 및 문서 출력 상한은 그대로 유지한다. 원본 파일·문서 저장 스키마는 변경하지 않는다.
- 큰 원본 축소 디코딩·추가 파생본 저장은 후속이다. 합성 12MP 테스트는 실제 카메라 사진·기기 메모리 검증을 대신하지 않는다.
