# 일반 로그인

> 최신 develop 통합: 새 V1 initial schema 이후 인증 V2·V3, 사진 V4·V5와 만료 세션 인덱스 V6를 적용한다. 아래 예전 V2~V6 설명은 기존 배포 이력의 기록이며, 이전 SQL 원본과 전환 주의사항은 [인증 마이그레이션 이력](./legacy-auth-migrations/README.md)을 참고한다. 기존 DB를 자동 초기화하거나 Flyway repair하지 않는다.


이메일 인증으로 가입한 `EMAIL` 계정의 BCrypt 비밀번호를 검증한다. 소셜로그인·비밀번호 재설정·프론트 연결·내 정보 조회·다이어리 소유권 변경은 포함하지 않는다. 회원가입은 계속 로그인 토큰 없이 완료되며, 가입 후 아래 로그인 API를 호출한다.

## API

| 도메인 | 기능 | Method | Endpoint | 인증 |
|---|---|---|---|---|
| 인증 | 일반 로그인 | POST | `/api/v1/auth/login` | 불필요 |
| 인증 | 토큰 재발급 | POST | `/api/v1/auth/refresh` | 본문의 Refresh Token |
| 인증 | 현재 기기 로그아웃 | POST | `/api/v1/auth/logout` | Bearer Access Token |

로그인 요청:

```json
{"email":"member@example.com","password":"DioMember123!","deviceName":"내 휴대폰"}
```

`deviceName`은 선택, 최대 100자다. 이메일은 공백 제거·소문자로 변환한다. 비밀번호는 공백 없는 ASCII 8~32자를 받는다. 등록 시와 같은 BCrypt 알고리즘으로 검증하며, 가입하지 않은 계정·비밀번호 불일치·비활성/탈퇴·이메일 비밀번호가 없는 계정은 동일한 401 `INVALID_CREDENTIALS`를 반환한다.

로그인/재발급 성공 응답(200):

```json
{
  "tokenType":"Bearer",
  "accessToken":"서명된 JWT",
  "expiresIn":900,
  "refreshToken":"일회용 43자 토큰",
  "refreshExpiresIn":2592000,
  "user":{
    "userId":"1",
    "email":"member@example.com",
    "nickname":"디오사용자",
    "profilePhotoUrl":null
  }
}
```

로그인 성공 시 `last_login_at`을 갱신한다. 사진이 있으면 기존 `/api/v1/auth/profile-photos/{photoId}` 상대 URL을 반환한다. 별도의 내 정보 조회 API는 만들지 않았다. 응답에 생년월일·프로필 색상·비밀번호/해시가 포함되지 않는다.

재발급 요청:

```json
{"refreshToken":"로그인 또는 직전 재발급 응답에서 받은 토큰"}
```

성공 응답의 Access Token과 Refresh Token을 함께 저장한다. 정상 회전 시 세션 만료일은 갱신 시각 + 기본 30일로 연장하되 최초 생성 시각 + 90일을 넘지 않는다. 이미 만료·폐기된 세션은 되살리지 않는다. 교체 후 30초 동안 직전 토큰 재시도는 동일한 후속 Refresh Token으로 복구한다. 이 시간에 현재 토큰으로 갱신해도 같은 Refresh Token을 반환해 응답 순서에 따른 토큰 불일치를 막는다. 유예 밖 이전 토큰이나 두 단계 이상 이전 토큰의 재사용은 해당 기기 세션을 종료한다. 프론트의 갱신 요청 합치기는 유지한다. 형식 오류는 400, 알 수 없는/만료/종료/재사용 토큰은 401 `INVALID_TOKEN`이다.

로그아웃은 요청 본문 없이 `Authorization: Bearer {accessToken}` 헤더를 보낸다. 성공 204이며 해당 기기의 Access/Refresh Token만 무효화한다. 다른 기기는 유지한다. Access Token이 이미 만료된 경우 재발급 후 로그아웃하거나 클라이언트의 로컬 토큰을 비우고 로그인 화면으로 이동한다. JWT 검증은 알고리즘 HS256, issuer dio, audience dio-api, token_use access, 만료와 DB 세션/회원 활성 상태를 확인한다.

Swagger에도 로그아웃 성공을 `204 No Content`로 명시하며 응답 본문 스키마를 제공하지 않는다. 로그인 API 호출만으로 Swagger 인증이 자동 등록되지는 않으므로 Authorize에 응답의 Access Token 값만 입력한다.

## 설정

- `AUTH_JWT_SECRET`: 무작위 32바이트 이상을 Base64로 변환한 서버 전용 키. `SIGNUP_VERIFICATION_SECRET`과 별개이며 원문을 Git/로그/프론트로 보내지 않는다.
- `AUTH_ACCESS_TOKEN_SECONDS`: 기본 900(15분). 60~86400초.
- `AUTH_REFRESH_TOKEN_SECONDS`: 기본 2592000(30일)의 갱신 시 유휴 기간. Access TTL보다 길고 최대 90일. 별도로 최초 로그인 기준 90일 상한을 적용한다.

local 프로필은 루트 .env를 읽는다. 이 컴퓨터에는 로그인용 키를 별도로 생성해 추가했고 기존 설정을 보존했다. 다른 개발자는 각자의 .env/실행 환경에 키를 설정한다. **같은 공용 DB/로그인 세션을 쓰는 서버들은 같은 로그인 서명키**를 사용해야 한다. 키 변경 시 기존 Access Token의 서명 검증이 실패하므로 운영 키 교체는 별도로 계획한다. 설정 누락·잘못된 키/TTL은 로그인 시 503 `LOGIN_NOT_CONFIGURED`로 실패하며 기존 공개 기능의 시작 자체를 막지 않는다.

구형 Windows PowerShell에서도 가능한 생성 명령(출력값은 .env에만 저장):

```powershell
$loginBytes = New-Object byte[] 32
$loginRng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$loginRng.GetBytes($loginBytes)
$loginRng.Dispose()
[Convert]::ToBase64String($loginBytes)
```

Swagger의 일반 로그인 그룹에서 로그인 후 응답의 Access Token을 Authorize에 입력하고 로그아웃을 호출한다. 재발급은 Authorization 없이 본문의 최신 Refresh Token을 사용한다. 토큰 응답/인증 오류에 Cache-Control no-store를 적용한다. 실제 전송은 배포 시 HTTPS를 사용한다.

## DB와 기존 기능 경계

V6는 `refresh_tokens`, `refresh_token_history`만 추가한다. 기존 users/다이어리/사진 테이블과 V1~V5 파일은 변경하지 않는다. 같은 V6 번호를 사용하는 다른 작업이 있으면 병합 전 번호를 조율하고, 적용된 파일은 수정하지 않는다. 적용 전 `pg_dump -Fc`로 DB를 백업하고, 백업 파일은 Git 외부의 팀 승인 보관 위치에 둔다.

Refresh Token 원문 대신 SHA-256 해시만 저장한다. 고정된 세션 행의 비관적 잠금으로 재발급·로그아웃·재사용 처리를 직렬화한다. 사용된 해시 이력으로 재사용을 탐지하고, 인증 오류 응답을 보내더라도 재사용 시 세션 폐기는 커밋한다. DB 쓰기 실패나 JWT 설정/서명 실패 때문에 유효한 토큰을 잃지 않도록 처리한다. 회원 물리 삭제 시 세션/이력도 FK CASCADE로 삭제된다. 만료된 세션/이력은 갱신된 최종 만료일 이후 최대 500개 배치로 주기적으로 정리한다.

현재 SecurityFilterChain의 JWT 보호 대상은 **새 로그아웃 경로만**이다. 기존 회원가입/이메일 인증/공개 사진/Swagger/다이어리 경로에 인증을 강제로 추가하지 않았다. 이는 기존 팀 작업 보존을 위한 단계적 적용이며, 다이어리는 여전히 공개 API다. 사용자별 데이터 보호가 완료된 상태로 해석하지 않는다. 향후 보호할 API의 매처·회원 식별·다이어리 소유권은 해당 기능 담당자와 함께 연결해야 한다. [Spring Security JWT 검증 문서](https://www.springframework.org/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

로그인 실패 제한은 한 서버의 메모리에서 동작한다. 이메일/IP 조합당 15분 내 오답 5회 이후와 IP당 오답 100회 이후 429 및 Retry-After 900을 반환한다. 캐시는 최대 2만 키이며 성공 시 해당 이메일/IP 실패 횟수를 초기화한다. 다른 IP의 실패나 동일 IP의 전체 실패 예산은 초기화하지 않는다. 재시작/다중 서버/캐시 축출에 걸친 공통 제한은 프록시·Redis 등 인프라에서 추가해야 한다. servlet remoteAddr를 사용한다. dev/prod에서는 아래 신뢰 프록시 설정으로 실제 클라이언트 주소를 반영한다.

프론트는 `authService`로 로그인·재발급·로그아웃을 연결한다. Access Token은 메모리에만 두고 Android·iOS의 Refresh Token은 보안 저장소에 보관한다. 재실행 시 기존 재발급 API로 복원하며 로그아웃·비밀번호 변경/재설정·회원 탈퇴 성공 시 저장 정보를 지운다. [모바일 로그인 유지](./persistent-login.md)를 참고한다.

## 검증 결과 (2026-10-26)

로그인·브라우저 테스트의 JWT 키는 `@DynamicPropertySource`에서 컨텍스트별 임시 무작위 키로 생성한다. 고정된 테스트 키 문자열로 인한 비밀정보 검사 감지를 없애며, 실제 `.env`나 운영 키에는 영향을 주지 않는다.

- 전체 테스트 142개 중 133개 통과, 기존 PostgreSQL 전용 9개 제외, 실패 0개. 정상 로그인·이메일 정규화·BCrypt 검증·마지막 로그인 시각·민감 정보 미노출·실패 제한·토큰 교체·재사용 세션 종료·만료/변조/비활성 계정 거절·기기별 로그아웃·동시 재발급을 확인했다. 기존 다이어리/회원가입/사진 회귀 테스트도 통과했다.
- 실제 PostgreSQL에서 V1~V6/Flyway·JPA 검증에 성공했다. 임시 테스트 계정으로 API 가입 201 → 로그인 200 → 재발급 200 및 토큰 교체 → 로그아웃 204 → 종료된 토큰 재발급 401을 확인했다. 테스트를 위해 가입 전 인증 행만 합성했고 실제 메일은 발송하지 않았다. 테스트 회원·약관·인증 계정·토큰/이력·인증 행은 정리했으며 기존 회원 데이터는 보존했다.
- 검증용 서버는 자동 포트로 실행 후 종료했다. 기존 실행 중이던 서버·공용 DB·프론트는 변경하지 않았다. Spring Security 의존성이 추가됐으므로 기존 서버는 재시작해야 한다. 프론트/실기기 연동과 실제 S3는 이 로그인 검증에 포함하지 않았다.

### 인증 배포 설정 보완

개발/운영 Compose는 JWT·이메일 인증 비밀키, SMTP 설정과 발신 주소를 컨테이너에 전달한다. 필수 값이 없으면 Compose 단계에서 중단한다. 실제 값은 서버의 배포 환경에만 설정하며 Git에 올리지 않는다. dev·prod의 S3 기본값을 유지하므로 MEDIA_S3_BUCKET과 IAM 역할 권한도 필요하다. local 저장을 명시한 경우 이름 있는 signup-profile-photos 볼륨에 사진을 보존한다. 배포 시 볼륨을 삭제하지 않는다.

AUTH_TRUSTED_PROXY_REGEX에는 백엔드에서 보이는 실제 Nginx 출발지 IP만 일치하는 정규식을 넣는다. 예를 들어 출발지가 172.20.0.2라면 `172\.20\.0\.2`이며, 이는 예시이므로 서버의 실제 네트워크 주소를 확인해 설정한다. 모든 IP에 일치하는 식은 사용하지 않는다. Nginx는 외부 X-Forwarded-For를 덮어쓰고 Tomcat은 신뢰한 프록시에서 온 값만 remoteAddr에 반영한다. 따라서 로그인 실패 제한이 모든 사용자를 프록시 하나로 묶지 않는다. 프록시 IP 변경 시 설정도 갱신한다.

개발 Nginx의 Basic 접근 인증은 유지한다. dev 프로필 Swagger Authorize에는 Access Token 값만 입력하며 X-DIO-Access-Token 헤더를 사용한다. 이 값도 기존 JWT·활성 세션 검증을 거친다. 개발 도메인에 연결하는 프론트는 EXPO_PUBLIC_AUTH_TOKEN_HEADER=X-DIO-Access-Token으로 설정한다. Basic 접근 권한은 별도로 필요하며 비밀번호를 EXPO_PUBLIC 변수에 넣지 않는다. 로컬 직접 연결과 prod는 기본 Authorization: Bearer 방식을 사용한다.

보완 검증(2026-10-26): 백엔드 전체 149개 중 139개 통과·환경 조건에 따른 10개 제외·실패 0개. 실제 임시 HTTP 서버에서 프록시가 전달한 서로 다른 클라이언트 IP가 로그인 제한 키에 각각 반영되고 잘못된 보조 토큰은 401로 거절됨을 확인했다. 프론트 인증 테스트 28개 통과, 웹·Android export 성공. 개발/운영 Compose는 실제 비밀값 없이 설정 렌더링과 사진 보존 볼륨을 확인했다. 실제 배포 서버·SMTP·S3 및 모바일 실기기 사진 업로드는 이번 검증에 포함하지 않았다.

추가 재검토(2026-10-26): 개발/운영 Nginx의 요청 본문 한도를 Spring의 max-request-size와 같은 6m으로 맞췄다(사진 파일 자체는 기존 5MB 제한). 격리한 Nginx에서 구문 검사, 개발 Basic 미인증 401, Basic과 보조 토큰 동시 전달, 위조 X-Forwarded-For 덮어쓰기, 2MB 전송 성공·7MB 전송 413을 확인했다. TLS 인증서는 실제 서버 설정이므로 격리 테스트에서는 HTTP로 검증했다. 설치된 Expo multipart 인코더로 JSON Blob·사진 바이트의 Content-Type과 직렬화를 추가 검증했으며 프론트 인증 테스트 29개 통과. 최신 웹 번들·임시 H2 HTTP 서버·Edge로 로그인 실패/성공→프로필→로그아웃 204, 닉네임 확인 및 인증 없는 가입 차단을 재확인했다. 브라우저/프록시/헤더 관련 백엔드 테스트 6개 통과. 메일 인증 화면 추가, 실제 서버 환경변수 설정, 실제 SMTP·S3·모바일 사진 업로드 확인은 별도로 남아 있다.

## 동시 로그인 시도 제한 보완

비밀번호 검증 전에 이메일·IP 조합과 IP 전체 예산을 하나의 잠금 안에서 예약한다. 실패 횟수와 진행 중 검증 수의 합이 각각 5회, 100회이면 429로 거절한다. 실패는 예약을 실패 횟수로 전환하고, 성공은 자기 예약을 해제하면서 해당 조합의 누적 실패만 초기화한다. 다른 진행 중 요청과 IP 전체 실패 기록은 유지한다. DB·서명 오류는 예약만 환불한다. 같은 요청의 중복 해제는 무시한다. 인스턴스 메모리 기반이므로 재시작·캐시 축출 시 기록이 사라지며 다중 인스턴스 공통 제한은 인프라에서 별도로 적용해야 한다.

`dev`, `prod`에서는 `AUTH_TRUSTED_PROXY_REGEX`가 필수다. Compose뿐 아니라 Spring 설정에서도 루프백 기본값을 제거했다. 배포 담당자는 실제 Nginx 출발지 IP를 확인해서 주입해야 하며, 배포 후 서로 다른 클라이언트의 IP 구분을 확인한다. `local` 설정은 변경하지 않았다.

프로필 사진의 회원 삭제 후 외부 파일 정리는 [후속 작업](./profile-photo-cleanup-followup.md)을 참고한다.

## DB 트랜잭션 범위

로그인은 계정·해시 조회용 읽기 트랜잭션을 끝낸 뒤 BCrypt를 실행한다(open-in-view=false). 세션 저장용 짧은 트랜잭션에서 인증 계정 행을 잠그고 사용자 ID·비밀번호 해시가 검증 시점과 동일한지 재확인하며, 활성 회원의 세션 생성과 last_login_at 갱신을 함께 커밋한다. 검증 중 비밀번호가 바뀌면 401로 거절하고 세션을 만들지 않는다. 재설정 작업도 같은 인증 계정 행 잠금으로 직렬화해야 한다. 로그인 도중 실패한 트랜잭션은 세션과 최근 로그인 시각을 함께 롤백한다.

실제 배포 변수 목록과 Nginx 전달 계약은 [인증 배포 환경](../infra/auth-deployment.md)을 참고한다.

## 동시 재발급 정책과 클라이언트 범위

서버는 고정 세션 행 잠금 안에서 최초 교체와 직전 토큰 재시도를 직렬화한다. 기존 해시 이력의 가장 최근 rotatedAt부터 30초 미만인 경우에만 직전 토큰을 허용한다. 정확히 30초부터는 허용하지 않는다. 유예 중 현재 토큰도 재회전하지 않아 모든 응답이 같은 후속 토큰으로 수렴하며, 재시도로 rotatedAt·유효기간을 연장하지 않는다. 유예가 지난 정상 현재 토큰의 갱신은 다시 회전·30일 연장한다.

후속 토큰은 서버 키를 사용하는 별도 도메인의 HMAC-SHA256으로 직전 토큰·세션 ID에서 재구성한다. DB에는 현재/이전 토큰의 해시만 보관하며 원문·암호문을 새로 저장하지 않는다. 새 API·테이블·컬럼·환경변수 없이 기존 createdAt·expiresAt·rotatedAt을 사용한다. 서버 인스턴스는 기존 JWT 키를 동일하게 사용해야 한다. 키 변경은 인증 키 교체 정책을 따르며, 이전 배포가 무작위로 발급한 토큰의 유실 응답까지 소급해 복원하지는 않는다.

createAuthApi는 refreshing Promise로 동시 요청을 합친다. 기존 응답 스키마와 저장 경로는 그대로다. 서버 커밋 뒤 응답이 유실돼도 30초 안에 직전 토큰으로 재요청하면 복구할 수 있지만, 30초를 넘겨 앱을 다시 실행하면 재로그인이 필요할 수 있다. 모든 응답 유실을 무기한 복원하는 기능은 아니다. 로그아웃·비밀번호 변경·탈퇴·비활성 계정·만료는 유예보다 우선한다.
