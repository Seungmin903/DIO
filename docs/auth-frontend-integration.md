# 기존 인증 화면 API 연결

기존 화면·입력칸·버튼만 연결했다. API 실패 시 체험 계정으로 대체하지 않는다.

| 기존 UI | 연결 |
| --- | --- |
| 이메일·비밀번호 로그인 | POST /api/v1/auth/login, 응답의 사용자 이름·사진을 기존 마이페이지에 표시 |
| 이메일 인증 | 발송 전 POST /api/v1/auth/email-availability → POST /api/v1/auth/email-verifications → POST /api/v1/auth/email-verifications/verify |
| 인증 화면의 다음 | 같은 서비스 인스턴스의 인증 토큰을 확인하고 가입 초안을 준비한 후 프로필 화면으로 이동 |
| 사진 선택·약관 체크 | 가입 요청으로 전달할 데이터 연결. SERVICE/PRIVACY 필수, MARKETING은 실제 선택값, 현재 버전 v1 |
| 가입 완료 | 인증된 signupToken이 있어야 POST /api/v1/auth/signup. 최종 가입 API 통합 검증은 S15P31F106-310 범위 |
| 마이페이지 로그아웃 | POST /api/v1/auth/logout, 만료된 accessToken은 refresh 후 재시도. 실패해도 기기 메모리의 토큰 제거 |
| 마이페이지 회원정보 불러오기 | GET /api/v1/me, 내 공간에 들어올 때 현재 로그인 토큰으로 조회해 로그인 시점 닉네임·사진을 서버 값으로 갱신. 401이면 refresh 후 1회 재시도하고, 실패하면 기존 값을 그대로 표시 |
| 마이페이지 회원정보 저장 | PATCH /api/v1/me, 현재 로그인 토큰으로 본인 `nickname`을 전송하고 응답 사용자 정보로 마이페이지를 갱신. 새 사진은 `profile` JSON 파트와 `photo` 파일을 multipart로 전송하며, 기본 이미지로 되돌릴 때는 `removeProfilePhoto: true`를 보냄 |
| 마이페이지 회원 탈퇴 | DELETE /api/v1/me, 확인 문구 입력 후 본인 Access Token으로 요청. 성공하면 계정은 WITHDRAWN 처리되고 모든 로그인 세션을 폐기한 뒤 앱은 로그인 화면으로 돌아감 |
| 소셜 로그인 | 백엔드 미구현 안내. 가짜 로그인 금지 |
| 게스트로 시작 | 제공하지 않음. 로그인한 실제 계정만 다이어리 기능에 진입 |

## 프론트 담당자에게 요청할 작업

1. 이메일 인증 UI(308)와 발송·확인 연결(309)을 구현했다. 실제 앱은 `authService.verificationService`를 주입한다. 서버의 `resendAfter`를 화면의 `retryAfter`로 변환하고 `expiresIn`으로 유효 시간을 표시한다. 검증 결과 signupToken은 메모리에만 보관하며 다른 이메일·만료된 토큰은 사용할 수 없다. 이전 화면으로 나가면 진행 중 응답을 무효화하고 인증 상태를 초기화한다.
2. 실제 약관 본문/보기 연결과 운영 약관 버전 연동이 필요하다. 현재 보기 안내는 UI 체험용이며 법적 약관 문서가 아니다. 서버의 약관 버전을 바꾸면 어댑터의 v1도 함께 변경해야 한다.
3. 소셜 로그인, 아이디 찾기, 비밀번호 재설정은 별도 구현이 필요하다. 기존 버튼만으로 동작한다고 안내하지 않는다.
4. 재실행 시 자동 로그인은 아직 없다. 토큰은 메모리에만 보관하며 AsyncStorage에 저장하지 않는다. 추후 네이티브 보안 저장소·세션 복원 정책이 필요하다.
5. 다이어리/편집기 데이터는 기존 로컬 저장 흐름을 유지한다. 계정별 데이터 분리·서버 다이어리 인증 연동을 완료한 것으로 간주하면 안 된다.

## 실행 설정

`frontend/.env`의 `EXPO_PUBLIC_API_BASE_URL`을 서버에 맞춘 후 Expo를 재시작한다. 웹 `http://localhost:8080/api`, Android 에뮬레이터 `http://10.0.2.2:8080/api`, 실제 기기는 개발 PC의 LAN IP를 사용한다. 서버 포트를 변경했다면 여기도 변경한다. `/api/v1` 또는 서버 origin 형식도 지원한다.

웹 CORS는 인증 경로에 한해 localhost:8081/127.0.0.1:8081을 허용한다. 다른 웹 주소는 백엔드 `AUTH_ALLOWED_ORIGINS`에 쉼표로 구분해 설정한다. 기존 다이어리 API 보안/CORS 정책은 바꾸지 않는다.

사진은 웹에서는 PNG Blob, 네이티브에서는 PNG 파일로 변환한다. 가입은 multipart의 `signup`(application/json), `photo`(image/png)로 보내고, 회원정보 사진 변경은 같은 파일 처리 방식으로 `profile`(application/json), `photo` 파트를 `PATCH /api/v1/me`에 보낸다. 네이티브 가입 JSON은 메모리 Blob으로 전송하며 비밀번호가 담긴 임시 파일을 만들지 않는다. Expo File 사진 파트는 expo/fetch로 전송하고 변환 사진만 요청 종료 시 삭제한다. 실기기 사진 업로드는 별도 확인이 필요하다. 서버의 local/S3 선택과 DB 저장 방식은 변경하지 않았다.

체험 계정·메모리 회원정보 서비스는 제거했다. 실제 App의 계정 기능은 authService만 사용하며, 게스트는 계정 기능에 진입할 수 없다.

- 서버 로그인·CORS: `cd backend`, `./gradlew.bat test --tests "com.f106.DIO.auth.integration.EmailLoginTests"`.
- 실제 HTTP와 브라우저: 먼저 frontend에서 `pnpm exec expo export --platform web --output-dir .expo/auth-api-export`를 **완료한 뒤**, backend PowerShell에서 `$env:DIO_AUTH_BROWSER_QA='true'`, `./gradlew.bat test --tests "com.f106.DIO.auth.integration.AuthBrowserTests"`를 실행한다. 끝나면 `Remove-Item Env:DIO_AUTH_BROWSER_QA`로 해제한다. Edge가 다른 위치라면 PLAYWRIGHT_BROWSER_PATH로 실행 파일 경로를 지정한다.

브라우저 검증은 포트 18081의 정적 파일 서버와 임시 H2 서버를 사용한다. 번들의 개발 API 주소는 테스트 프록시로 임시 서버에 연결하며 응답을 mock하지 않는다. 테스트용 사용자만 만들고 실제 메일 발송·개인 PostgreSQL 변경·기존 서버 종료는 하지 않는다. CORS 허용/차단은 서버 테스트로 별도 확인한다. 실기기 업로드·실제 S3 업로드·메일 인증 UI 전체 흐름을 검증한 것은 아니다.

2026-10-26 확인: 프론트 인증 테스트 26개, 서버 로그인/CORS 테스트 13개, 실제 HTTP 브라우저 테스트 1개 통과. 브라우저에서 로그인 실패·성공, 내 공간의 서버 닉네임 표시, 로그아웃, 닉네임 확인, 이메일 인증 없는 가입 요청 차단을 확인했다. 최종 웹·Android export도 성공했다. 실기기 실행 결과와는 구분한다.

## 이메일 인증 UI 후속 연결 경계

실제 앱은 개발·배포 모드 모두 서버 인증 서비스를 사용한다. 인증 서비스를 제공하지 않는 별도 화면/fixture에는 기존 배포 진입 게이트가 남는다. 임시 인증은 명시적 개발용 화면에서만 사용한다. 발송 제한 응답의 Retry-After를 적용하고, 비정상 응답은 오류로 표시한다. SMTP 실제 수신과 최종 가입·로그인은 팀 개발 서버에서 별도 확인한다.

개발 서버 접근 인증(2026-10-28): 개발8443의 이메일 확인·발송 API POST 요청은 접속 정보 없이 Nginx 401 Basic 인증 요구를 반환했다. 제공받은 접속 정보로 빈 요청을 보내면 백엔드 입력 검증400까지 도달하는 것을 확인했다. 브라우저의 Swagger 접근 인증은 Expo 앱과 공유되지 않는다.

Expo 개발 모드에서 발송 요청이 Basic401로 막히면 기존 입력칸으로 개발 서버 ID·비밀번호를 입력한다. ‘접속 인증 후 다시 시도’는 같은 요청을 재시도한다. 비밀번호 입력값은 제출 후 비운다. 입력한 접속 정보(Basic 헤더 값)는 네이티브 앱의 현재 실행 중에만 서버 origin별 메모리에 둔다. 앱을 종료·강제 종료하거나 OS가 프로세스를 회수한 뒤에는 다시 입력해야 하며, `load`가 비어 있으면 기존 개발 접속 입력 UI가 정상적으로 재입력을 받는다. 웹과 배포 모드는 개발 접속 저장소를 만들거나 읽지 않는다. 소스·EXPO_PUBLIC 환경변수·AsyncStorage에는 저장하지 않는다. 인증 이후 JWT는 Basic Authorization과 충돌하지 않도록 기존 백엔드가 지원하는 X-DIO-Access-Token으로 전달한다. 서버 접근 정책·백엔드 코드는 변경하지 않았다.

309 검증: frontend에서 `pnpm test:auth`를 실행한다. Android 태블릿에서 개발 서버 접근 인증 → 실제 메일 수신 → 받은 번호 인증 → 프로필 화면 진입을 확인했다. 초기 검증 때 사용한 신규 Java 통합 테스트와 그 전용 프론트 QA 스크립트는 프론트 작업 범위를 지키기 위해 MR에서 제외했다. 기존 팀원의 백엔드 파일·테스트는 변경하지 않는다.

## 309 리뷰 확인 및 프론트 작업 범위

- 초기 MR에 추가했던 Java 통합 테스트도 제외했다. 리뷰 중 시도한 개발 Nginx 설정·배포 문서 변경은 원복했다. 제품의 프론트 인증 연결·프론트 단위 테스트·관련 문서만 유지한다.
- Spring은 이미 Retry-After를 노출한다. 개발 Nginx의 웹 교차 출처 OPTIONS·401 응답 헤더 제한은 프론트만으로 해결할 수 없으므로 미해결 제약으로 기록한다. 서버 설정은 변경하지 않는다. Android Expo Go에서 확인한 직접 API 호출과 웹 CORS는 구분한다.
- `authService.js`의 accessTokenHeader는 이미 export 선언되어 있다. 선언을 중복 추가하지 않고 실제 모듈 초기화 테스트로 주소·헤더 전달과 개발/운영 모드를 검증한다.
- 고정 포트 리뷰가 달렸던 신규 Java 테스트와 전용 Node QA 스크립트는 함께 제외했다. 해당 파일을 실행하는 재현 명령도 제거했다. 기존 팀원의 QA·백엔드 검증 경로는 유지한다.

## 310 회원가입 완료·닉네임 API 검증 (2026-10-29)

기존 `POST /api/v1/auth/signup` 연결을 유지하고 프론트의 실패·재시도 처리를 보완한다. 백엔드·인프라는 변경하지 않는다. 서버 계약은 기존 SignupController·SignupRequest·SignupResponse·UserService를 읽어 확인한다.

- 이메일 가용성 응답은 boolean만 허용한다. 닉네임 형식·필수 약관 검증을 통과해야 가입 요청을 보내며 정규화한 닉네임과 SERVICE/PRIVACY/MARKETING의 실제 선택값(v1)을 전송한다. `INVALID_SIGNUP_TOKEN`이면 재인증을 안내하고, 다른 오류에서는 입력을 유지한다.
- 사진이 있으면 기존 네이티브 multipart 변환을 재사용한다. 변환 중 이탈·토큰 만료 시 가입 전송을 막고 임시 사진을 정리한다. 가입 요청 연타를 차단하며, 늦은 이전 가입 결과로 새 인증·가입 초안을 지우지 않는다. 이미 서버에 전송된 가입은 화면 이탈로 취소되었다고 보장하지 않는다.
- 가입 응답의 사용자 ID·이메일·닉네임·사진 필드를 확인한 뒤 완료로 처리한다. 성공하면 자동 로그인하지 않고 이메일만 남긴 로그인 화면으로 돌아간다. 임시 사진 정리 실패가 서버 가입 성공을 실패로 바꾸지 않는다.

### 실기기에서 한 번의 가입으로 확인하는 순서

1. Expo Go를 리로드한 뒤 회원가입에 진입한다. 잘못된 이메일·짧은 비밀번호·다른 비밀번호 확인값을 입력해 안내를 보고 올바른 값으로 고친다. 아직 가입하지 않은 수신 가능한 이메일을 사용한다.
2. 인증번호를 받고 오답은 한 번만 입력해 오류를 확인한다. 메일의 올바른 번호로 인증을 완료하고 다음으로 이동한다. 발송 직후 재전송 대기 표시도 확인한다.
3. 프로필 사진 선택 → 사진 선택 취소(기존 사진 유지) → 사진 삭제(기본 이미지 복원) → 다시 선택 순서로 확인하고 최종 사진을 남긴다.
4. 닉네임에 `dio`를 입력하고 중복 확인하면 사용 불가여야 한다(서버 예약어). 다른 닉네임을 확인한 뒤 한 글자 수정하면 중복 확인 완료가 해제되어야 한다. 최종 닉네임을 다시 확인한다.
5. 필수 약관 하나만 동의했을 때 가입 완료가 비활성인지 확인한다. 두 필수를 동의하고 선택 수신 동의는 끈다. 필요하면 전체 동의도 켰다가 선택 동의를 다시 끈다.
6. 통신 실패를 확인하려면 가입 완료를 누르기 **전에** Wi-Fi·모바일 데이터를 모두 끈다. 실패 안내 뒤 사진·닉네임·약관이 유지되는지 보고 다시 연결한다. 전송 중에 통신을 끊으면 서버 가입 여부가 불명확할 수 있으므로 이 시점에는 끊지 않는다.
7. 인증 성공 뒤 10분 안에 가입 완료를 누른다(서버 signupToken 유효기간). 처리 중 버튼이 비활성화되고 완료 뒤 로그인 화면에 이메일만 남는지 확인한다.
8. 같은 계정으로 로그인하여 실제 서버 닉네임·사진이 표시되는지 확인한다. 로그인은 311 후속 검증에도 포함되며, 실패하면 가입 실패로 단정하지 말고 오류 문구를 기록한다.
9. 가입 이메일 중복을 확인하려면 로그아웃 후 같은 이메일로 회원가입 → 인증번호 받기를 시도한다. 이미 가입된 이메일 안내가 나오고 추가 메일은 발송되지 않아야 한다.

사진 없는 JSON 가입·같은 닉네임 가입 허용·토큰 만료·변환 중 화면 이탈·지연 응답·잘못된 서버 응답은 프론트 자동 테스트로 확인한다. 한 번의 실기기 가입으로 이 모든 서버 상태를 재현했다고 간주하지 않는다. 실제 계정 생성·SMTP·사진 저장 결과는 위 수동 검증으로 별도 확인한다. 새로운 테스트 계정은 자동 생성하지 않는다.

검증 결과: `pnpm test:auth` 86개, `pnpm test:member-diary` 29개 통과. `pnpm exec expo export --platform all --no-bytecode --output-dir .expo/signup-api-check`로 Android·iOS·웹 JS 번들 생성 성공. 프론트 테스트의 HTTP 응답은 대체하므로 실제 개발 서버 가입 완료·사진 업로드·로그인 성공을 의미하지 않는다. 해당 실기기 결과는 확인 후 기록한다.


이번 브랜치는 회원가입 요청·상태·오류 처리 및 관련 테스트만 변경한다. 실기기 확인 중 추가한 프로필 사진 조회·보관함·알림 인증 전달 수정은 작업 폴더에서 분리했다. 분리 후 인증 테스트 86개와 회원 다이어리 회귀 테스트 29개가 다시 통과했고, 백엔드·인프라 변경은 없다.

## 311 이메일 로그인 API 연결 보완 (2026-10-29)

기존 `POST /api/v1/auth/login` 연결을 재사용한다. 서버 LoginResponse·LoginUserResponse와 개발 서버의 별도 JWT 헤더 계약을 읽어 프론트에 반영한다. 백엔드·인프라·회원가입 전송 계약은 변경하지 않는다. 로그인 유지·토큰 영구 저장·갱신 정책·로그아웃 기능 추가는 별도 태스크다.

- 이메일은 정규화하고 비밀번호는 원문으로 보낸다. 서버 자격 증명 오류와 통신 오류를 구분하고 입력을 유지해 재시도한다. 연타는 한 요청으로 처리하며 화면 이탈 후 이전 결과는 진입에 사용하지 않는다.
- 로그인 응답의 요청 이메일 일치, 사용자 ID·닉네임·토큰·유효 시간·사진 URL을 검증한 뒤 세션을 채택한다. 화면에 넘기는 사용자 정보에는 비밀번호·토큰·개발 접근 인증을 넣지 않는다.
- 개발 모드의 Basic401이면 로그인 카드에 기존 공용 입력칸으로 개발 서버 ID·비밀번호와 ‘접속 인증 후 로그인’을 표시한다. 계정 입력은 유지하고 제출한 개발 비밀번호 입력은 비운다. 잘못된 접속 정보는 다시 입력할 수 있고 Android 뒤로가기는 입력 화면을 정리한다. 배포 모드는 이 입력칸을 제공하지 않는다. 개발 접속 정보는 위 개발 서버 접근 인증 정책대로 현재 앱 실행 중에만 유지하므로, 앱 재실행 뒤에는 같은 입력칸에서 다시 인증한다.
- 로그인 후 보관함·기존 알림 transport도 같은 서비스의 현재 인증 헤더를 사용한다. Basic Authorization과 JWT의 X-DIO-Access-Token을 분리한다. 설정한 서버의 API 경로 밖으로 인증 헤더를 전달하지 않는다. 기존 401 갱신·재시도 정책은 유지한다.
- 내 공간의 프로필 사진은 같은 서버의 프로필 사진 경로에만 개발 Basic 헤더를 붙이며 회원 JWT는 보내지 않는다. 이미지 로드 실패 시 기존 기본 프로필을 표시한다. 사진 선택·기본 이미지 복원 모두 로그인한 본인의 `PATCH /api/v1/me` 응답으로 화면 상태를 갱신한다.

실기기 확인 순서:

1. Expo Go를 리로드하고 이미 가입한 계정으로 로그인한다. 개발 서버 접근 인증이 나타나면 제공받은 정보를 입력한다. 회원가입을 다시 할 필요는 없다.
2. 계정 비밀번호를 잘못 입력하면 로그인 실패 안내가 나오고 입력을 고쳐 재시도할 수 있는지 확인한다.
3. 네트워크를 끈 상태에서 로그인해 통신 오류를 확인하고 다시 연결하여 재시도한다.
4. 올바른 정보로 로그인 버튼을 연속으로 눌러도 한 번만 보관함으로 진입하는지 확인한다. 보관함에서 개발 서버 인증 누락으로 인한 ‘로그인이 필요해요’가 나타나지 않아야 한다.
5. 내 공간에 가입한 닉네임과 사진이 표시되는지 확인한다. 사진 없는 계정은 기본 프로필을 표시한다.
6. 로그인 응답 대기 중 회원가입으로 이동하면 이전 로그인 응답이 나중에 화면을 바꾸지 않는지 확인한다.

자동 테스트는 대체 HTTP 응답으로 검증하며 실제 개발 서버·실기기 성공을 대신하지 않는다. 검증 명령: `pnpm test:auth`, `pnpm test:member-diary`, `pnpm test:notifications`, `pnpm exec expo export --platform all --no-bytecode --output-dir .expo/login-api-check`.

311 초기 구현 당시 검증(후속 리뷰 보완 전): 인증 93개·회원 보관함 30개·알림 82개(합계 205개) 통과. Android·iOS·웹 JS 번들 생성 성공. 로컬 HTTP 테스트는 샌드박스 연결 제한을 벗어나 재실행했다. 당시 실기기 확인은 대기 상태였으며 이후 결과는 아래에 기록한다.

### 311 리뷰 계약 확인

- 보관함 HTTP transport도 알림과 동일하게 `redirect: 'error'`, `credentials: 'omit'`을 사용한다. API가 리다이렉트를 반환하면 자동 이동하지 않고 기존 네트워크 오류로 처리한다. 명시적으로 생성한 Basic/JWT 인증 헤더는 유지한다. 프론트 로컬 HTTP의 서로 다른 두 출처로 302 응답을 구성하여 원래 요청 1회·이동 대상 요청 0회·NETWORK_ERROR를 확인했다. `pnpm test:member-diary` 32개 통과(로컬 연결 제한 밖 재실행). 이 검증은 Node fetch 기준이며 Android/iOS 네이티브의 리다이렉트 동작을 직접 검증한 결과는 아니다. 백엔드·인프라는 변경하지 않았다.

- 백엔드 `EmailLoginService.response`는 사진이 없는 회원의 `profilePhotoUrl`을 `null`로 반환한다. 빈 문자열은 현재 서버 계약에 포함되지 않는다.
- 로그인과 갱신은 동일한 `LoginResponse`를 사용하며, 두 응답 모두 사용자 정보와 새 토큰을 포함한다. 사용자 정보가 없는 갱신 응답을 허용하도록 계약을 완화하지 않는다.
- 인증 헤더 생성 실패는 요청을 보내기 전에 보관함의 `DiaryApiError`, 알림의 `NotificationError`로 변환한다. 코드는 `API_NOT_CONFIGURED`이며 인증 정보나 내부 예외 메시지는 노출하지 않는다.
- Android 태블릿 Expo Go에서 실제 계정 로그인·닉네임·프로필 사진 표시를 확인했다. 사진은 `expo-image`로 표시하며 임시 진단 요청·로그는 제거했다.

### 최신 develop 병합 후 재확인 (2026-10-29)

사진 캐시 리뷰 보완: `cachePolicy="memory"`로 네이티브의 같은 사진 재방문 시 메모리 재사용을 허용한다. 계정 ID와 사진 URI로 캐시 키를 분리하며 인증 헤더는 캐시 키·로그에 넣지 않는다. 디스크 캐시는 사용하지 않는다. 실패는 계정·사진·접근 인증 조합에만 적용하여 사진 주소 또는 인증 정보가 변경되면 다시 표시를 시도한다. 화면 재마운트 때도 실패 상태가 초기화된다. 별도 재시도 버튼·자동 반복 요청·진단 fetch는 추가하지 않는다. 사진을 같은 URI로 교체하는 경우의 즉시 갱신은 사진 수정 API 후속에서 별도 확인한다.

설치된 expo-image의 웹 `useHeaders`는 source.headers를 포함해 fetch한 뒤 Blob URL로 표시한다. 별도 웹 fetch 구현은 추가하지 않는다. 웹의 브라우저 캐시·CORS는 네이티브 메모리 캐시와 구분하며 개발 서버 웹 성공을 확인한 것으로 기록하지 않는다. 캐시·실패 후 사진/계정/인증 변경 회귀를 포함한 인증 테스트 95개 통과. 사용자는 이 보완 후 실기기에서 사진 표시·내 공간 재진입이 정상 동작함을 확인했다. 진단 stash는 복원하지 않았다.

- 사용자가 `feature/fe/login-api`에 origin/develop `63264ce`를 병합했다(병합 커밋 `aa1dc3f`). App.js와 디자인 가이드는 자동 병합됐으며 충돌 보고는 없었다.

- 기존 로그인 응답 검증·개발 접근 인증·보관함/알림 인증 헤더 전달·expo-image 사진 표시와 팀원의 회원/로컬 보관함 진입 흐름을 현재 코드에서 확인했다. 사진 재시도·캐시·임시 진단 stash는 적용하지 않았다.
