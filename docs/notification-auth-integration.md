# 알림 로그인 연결과 남은 공유 QA

## 실제 로그인 연결

알림 기본 4개 API는 기존 loginJwtDecoder와 loginBearerTokenResolver를 재사용한다. 서명·issuer/audience·access 용도·만료와 활성 refresh 세션·회원 상태를 검증한 Authentication만 NotificationUserPrincipal로 변환한다. 요청 userId·헤더·커서로 수신자를 선택하지 않는다. 기존 로그아웃 및 다른 기능의 보안 범위는 바꾸지 않는다.

허용 출처는 기존 AUTH_ALLOWED_ORIGINS를 사용한다. 알림 경로에만 GET/PATCH/DELETE/OPTIONS를 허용하며 쿠키 인증을 추가하지 않는다. 개발 보조 헤더 X-DIO-Access-Token도 기존 로그인 설정이 명시된 경우에만 동일한 JWT 검증을 거친다.

DTO/SQL 계약 테스트는 필터를 끈 별도 계약 검증이다. NotificationAuthenticationHttpTests는 실제 loopback HTTP 로그인·JWT 필터·활성 세션·수신자 SQL을 통합 검증하므로 두 결과를 구분한다.

## 프런트 세션과 기본 앱

일반 로그인 사용자는 AuthenticatedNotificationProvider의 공통 모델을 보관함·편집기 알림 진입점에서 공유한다. 받은 알림은 실제 서버 패널로 열고 목 공유 수락 화면으로 보내지 않는다. 일반 로그인에서 공유 진입을 누르면 미연결 안내와 실제 받은 알림을 제공하며 목 공유 생성·수락 동작은 노출하지 않는다. 방문자·미리보기 모드는 기존 공유 목을 유지한다. 서버가 지원하지 않는 모두 읽음은 숨기며 실제 초대 상세가 없으면 이동을 제공하지 않는다.

createAuthenticatedNotificationSession은 로그인 서비스의 정규화 주소·헤더 설정을 사용한다. 토큰은 메모리 안에 유지한다. getAccessToken은 생성 당시 사용자·로그인 세션을 확인하고 만료 최대 30초 전(짧은 수명은 절반 시점)부터 기존 refresh 동시 실행 방지를 재사용한다. expiresIn은 양의 정수·최대 86400초가 아니면 로그인 응답을 거부하며 갱신 루프를 만들지 않는다. 갱신 후에도 세션을 재확인한다. 로그인 화면 해제의 cancelPending은 활성 로그인 세션 키를 바꾸지 않는다. 로그아웃·다른 계정·같은 계정 재로그인은 이전 알림 세션을 무효화한다. refresh만으로는 UI 모델을 재생성하지 않는다.

401 뒤 알림 쓰기를 자동 재전송하지 않는다. 서버가 거부하거나 갱신이 실패하면 로그인 안내를 표시한다. 기본 앱의 로그인 화면 복귀와 세션 종료는 기존 로그아웃 흐름을 사용한다.

## 공유 연결에 필요한 계약

현재 저장소에는 실제 공유/초대 백엔드와 ID 기반 수신자 초대 상세 gateway가 없다. 공유 화면은 메모리 미리보기다. notifications와 diary_invites를 임의의 diary_id나 payload_json 필드로 연결하지 않는다. 알림 ID→초대 ID의 명시적인 참조 계약이 필요하다.

공유 담당의 구현에서 다음을 제공해야 한다.

1. InvitationLookup.findForRecipient(recipientUserId, notificationIds)의 일괄 구현. 수신자 권한·만료·취소·기존 참여 상태를 현재 시각 기준으로 확인하고 없는/권한 없는 결과는 제외한다.
2. invitations.get(inviteId, {signal})가 사용할 실제 수신자 상세 경로와 DTO. 같은 inviteId·PENDING·canOpen===true를 이동 직전에 다시 확인할 수 있어야 한다. 링크 token을 inviteId로 추측하거나 알림에 노출하지 않는다.
3. 수락·거절 결과와 공유 다이어리 열기/닉네임 설정의 최종 화면 연결. 알림 읽음·삭제는 초대 원본을 변경하지 않는다.
4. 초대 이벤트(248)의 생성·중복 방지와 알림 참조 저장 계약. 이 MR은 이벤트를 만들거나 신규 migration을 추가하지 않는다.

이 계약·구현 전에는 invitation=null과 이동 불가를 유지하며 Draft를 해제하지 않는다.

## 재현 명령

backend에서 알림과 기존 로그인 테스트를 실행한다.

```sh
./gradlew test --tests 'com.f106.DIO.notification.*' --tests 'com.f106.DIO.auth.integration.EmailLoginTests'
```

Windows는 gradlew.bat을 사용한다. frontend에서 test:notifications와 test:auth, test:notifications:contract를 실행하고 웹/iOS 번들을 확인한다. 현재 실행 결과·SHA·CI는 MR !164에 기록하며 번들 성공을 실기기 성공으로 해석하지 않는다.

backend의 `notificationBrowserQa` Gradle 작업으로 실행하는 NotificationBrowserQa는 명시적인 DIO_NOTIFICATION_BROWSER_QA=true일 때만 loopback 포트 18565와 일회성 H2를 사용한다. 테스트용 계정만 생성하며 외부 DB·실제 메일·제품 계정을 쓰지 않는다. QA 웹 번들은 127.0.0.1:18566에서 제공하고 API 주소는 http://127.0.0.1:18565/api로 빌드한다. 검증 후 해당 서버만 종료한다.

## 남은 QA

- 공유 구현 후 실제 초대 도착→목록→상세→수락/거절→다이어리 진입, 만료/취소/이미 참여/권한 회수·재시도·중복 이벤트를 확인한다.
- iPad/Android에서 로그인·앱 복귀·더 보기·읽음·삭제·회전·로그아웃/재로그인과 VoiceOver/TalkBack을 확인한다.
- 실제 개발 서버의 JWT 설정·CORS·Nginx Basic 인증/보조 헤더와 두 기기 동시 사용을 확인한다. 로컬 H2/격리 PostgreSQL 결과로 대체하지 않는다.
- 사용자 외 리뷰 승인, 현재 필수 CI·충돌 확인 후 Draft 해제·병합 여부를 결정한다.

## 초기 상태와 전송 정책

네이티브 AppState가 미확정(null)으로 시작하면 초기 조회를 한 번 수행하되 active 확인 전에는 polling하지 않는다. inactive/background와 웹 숨김 시작은 조회·polling을 하지 않는다. 실제 기기의 초기 상태·복귀 조합은 실기기 QA에서 확인한다.

알림 Bearer 전송은 기본 HTTPS와 localhost/127.0.0.1/[::1]/10.0.2.2의 개발 HTTP만 허용한다. 그 밖의 HTTP는 __DEV__에서만 허용한다. 운영 원격 HTTP 설정은 토큰 조회 전에 API_NOT_CONFIGURED로 처리한다. 실제 배포의 로그인 서버와 프록시 TLS 설정은 별도 QA 대상이다.

## 토큰 갱신 실패 복구와 TTL 계약

알림의 만료 전 토큰 갱신이 네트워크 또는 서버 오류로 실패하면 메모리 세션을 보존하고 원래 오류를 재시도 가능한 안내로 전달한다. 실패한 갱신 뒤에는 알림 요청을 보내지 않으며 다음 조회·재시도에서 갱신을 다시 시도한다. 401/403 인증 거부와 잘못된 갱신 응답은 세션을 무효화한다. 동시 갱신은 하나로 합치며 계정 변경 후 옛 요청에는 새 토큰을 전달하지 않는다. 응답 유실로 서버에서 이미 회전된 토큰이 거부되는 경우에는 재로그인이 필요할 수 있다.

서버 LoginJwt는 access-token-seconds를 60~86400초(기본 900초)로 제한한다. FE expiresIn의 양의 정수·최대 86400초 검사는 이 서버 계약과 호환된다. 설정 범위를 벗어나는 TTL은 서버에서 LOGIN_NOT_CONFIGURED로 거부하므로 FE 상한은 완화하지 않는다. 유효하지 않은 응답은 저장하지 않으며 서버 세션은 기존 만료·정리 정책을 따른다.
