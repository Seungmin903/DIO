# 알림 전체 읽음

로그인 사용자가 전체 읽음을 누르면 서버는 그 시점에 보이는 모든 미읽음 알림의 스냅샷을 고정한다. 이후 커밋된 알림은 읽음 처리하지 않는다. 알림 읽음은 초대 수락이나 거절과 무관하다.

`POST /api/v1/notifications/read-watermarks`는 불투명한 `readWatermark`와 `expiresAt`을 201로 반환한다. `POST /api/v1/notifications/read-all`에 `{"readWatermark":"..."}`를 전송하면 해당 스냅샷을 읽음으로 표시하고 204를 반환한다. 사용자별 경계이며 발급 후 10분간 유효하다. 타인·없는 경계는 400 `INVALID_READ_WATERMARK`, 아직 정리되지 않은 만료 경계는 410 `READ_WATERMARK_EXPIRED`다. 만료 경계가 정리된 후에는 없는 경계와 같이 400을 반환한다. 두 오류 모두 새 전체 읽기 요청으로 새 경계를 발급해야 한다. 동일 경계 재시도는 유효 기간 내 멱등이며 처음 읽은 시각을 유지한다. 활성 경계는 사용자당 최대 20개다.

만료 정리는 한 배치에서 만료 경계 하나를 잠그고 대상 행을 최대 500개 삭제한다. 대상이 모두 지워진 후에만 경계를 삭제하며 한 실행에 최대 10배치를 각각 별도 트랜잭션으로 처리한다. 동시에 잠긴 경계는 건너뛰며 적체는 다음 실행에서 처리한다. 새 발급은 만료 경계를 동기 삭제하지 않고 만료되지 않은 경계만 한도에 포함한다. 실제 처리량은 대상 행 수와 DB 성능에 따라 달라지므로 정리 적체와 테이블 용량을 운영에서 관찰해야 한다.
정리 스케줄은 기본 활성화되며 `dio.notification.watermark-cleanup.enabled=false`로 비활성화할 수 있다. 실행 간격과 최초 대기는 각각 `delay-ms`, `initial-delay-ms`로 설정하며 기본값은 모두 60000ms다.
완료된 경계도 유효 기간 안의 멱등 재시도를 보장하기 위해 만료 전까지 20개 제한에 포함한다. 제한에 도달하면 429 `READ_WATERMARK_LIMIT`를 반환하며 만료 후 다시 발급할 수 있다.
전체 읽기 적용이 성공하면 대상 행은 같은 트랜잭션에서 삭제하고 완료 표식만 남겨 재시도의 멱등성을 유지한다. 미적용 경계는 만료까지 대상 행을 유지하므로 미적용 경계가 많거나 미읽음이 많은 경우 대량의 대상 행이 저장될 수 있다.

프론트는 읽음 요청 실패 시 발급된 동일 경계로 재시도하고, 만료되면 사용자가 새로 전체 읽기를 실행할 수 있도록 안내한다. 경계 발급 응답 자체가 유실되면 기존 경계를 알 수 없으므로 자동 재발급하지 않고 사용자의 새 요청을 기다린다. 목록을 다시 여는 것만으로 읽음 처리하지 않는다. 스냅샷 기준은 버튼을 누른 클라이언트 시각이 아니라 서버의 대상 확정 시점이다.

V15 마이그레이션은 watermark와 대상 테이블을 추가하며 기존 알림을 변경하지 않는다. 데이터베이스 롤백은 배포 운영 절차에 따라 백업을 확보하고 새 API 사용을 중단한 후 두 신규 테이블을 제거해야 한다. 이미 기록한 알림의 `read_at`을 되돌리지는 않는다. watermark 유효 기간은 공유 초대 유효 기간과 무관하다.
