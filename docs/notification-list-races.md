# 알림 연속 조회·동시 요청 경합 회귀


## 기존 검증과 추가 구간

기존 notification-api/integration/lifecycle 테스트에 기본 더 보기, 조회 실패 시 결과 보존, 빈 마지막 페이지, 취소를 따르는 목의 더 보기 중 새로고침, dispose, 복귀 후 조회는 이미 있었다. 이번에는 시간 지연 길이를 늘려 같은 테스트를 반복하지 않고, deferred Promise로 응답 완료 순서를 직접 제어했다. 취소 신호도 의도적으로 무시해 AbortController 외에 세대 검사 자체가 동작하는지 확인한다.

| 추가 사례 | 기존 대비 빈 구간과 확인 |
|---|---|
| 새로고침·카운트 역순 완료 | 최신 응답 이후 오래된 성공 또는 오류가 도착해도 목록·커서·카운트·성공 상태가 되돌아가지 않음 |
| 더 보기 취소 무시 | 이후 새로고침이 성공/실패한 두 경우 모두 이전 페이지 응답 무효. 실패 시 기존 항목·커서 보존 |
| 연타·겹치는 페이지·종료 | 동시 더 보기3회가 요청1회, 겹치는 ID가 중복 표시되지 않음, 빈 마지막 응답의 null 커서 반영 후 추가 요청 없음 |
| 읽음/삭제와 복귀 조회 | 쓰기 반영 전 복귀 조회의 늦은 미읽음/삭제 전 목록과 카운트가 쓰기 후 상태를 덮어쓰지 않음 |
| 최종 삭제 후 지연 페이지 | 삭제 후 빈 첫 페이지가 확정된 뒤 이전 더 보기의 항목·커서가 다시 나타나지 않음 |
| 새 도착·경계 삭제와 연속 조회 | FE 서버 어댑터가 불투명 커서를 그대로 전달. 새 도착을 기존 페이지 중간에 섞지 않고 기존 범위를 이어가며, 명시적 새로고침 때 최신 알림 표시 |

키셋 사례의 서버 동작은 테스트 transport로 모사한다. 커서 경계가 가리킨 행이 서버에서 외부 삭제돼도 앞서 받은 캐시는 새로고침까지 유지된다. 이 테스트는 삭제 사실을 알리지 않은 상태에서 FE가 자동으로 삭제를 감지한다는 뜻이 아니다. 사용자 삭제 후 빈 응답이 확정된 경우의 복원 차단은 별도 사례에서 확인했다. 실제 Spring/PostgreSQL 커서 구현·격리 수준 검증으로 간주하지 않는다.
